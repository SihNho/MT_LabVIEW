## 무엇이 틀렸나
- 제가 제안하고 사용자가 승인한 옵션 A의 문구: "원본 복사본에서 프레임 루프를 그대로 두고 정지/종료 + 파일 저장만 먼저 붙인 버전".
- 측정 결과 원본에는 이미 정지(`stop (end)` 컨트롤 2개, 프레임 루프 본체 Diagram 639에서 읽음)와 파일 저장(`save N xyz traces.vi`, 루프가 끝난 뒤 diagram 19에서 루프 출력 터널로 한 번에 저장)이 있음. 즉 "원본 복사본에 정지·저장을 붙인다"는 실제로는 아무것도 만들지 않는 정의였음.
- 그래서 제가 cycle15-plan.md에 쓴 D1은 "원본 복사본에서 트래커 호출만 교체"로 바뀌어 있었는데, 이것은 `docs/decisions.md:19`의 확정 결정 — "구조 변경은 원본 복사본 안에서, **hot-path만 바꾸는 방식은 아님**, 빈 VI 재작성도 아님" — 과 정면으로 어긋남. 선행연구 리뷰(cycle15-d1, $3.28, 12개 지적, novel 0)가 이것을 잡음.
- 성과 리뷰가 "정지/저장을 먼저"라고 한 대상은 원본이 아니라 **새 7루프 VI**였음: 지금 있는 두 replay VI에는 정지도 저장도 없다는 뜻.

## 확정 결정(decisions.md, 재논의 대상 아님)
- 수용 기준 C: 카메라 획득·트래킹·모터 읽기·스케줄러·데이터 저장이 각각 자기 루프. 프레임 루프(diagram 43)를 비워 7루프로.
- 구조 변경은 원본 복사본 안에서. 방법은 이미 검증됨(probe_migrate v2 3/3, v3 5/5). 검증 안 된 것은 규모와 실행 시간.
- GPU 상위 VI를 먼저, 기본으로. CPU 병렬은 그 다음, 별도 VI.
- 카메라는 free-run, PC는 읽기만. 프레임 전달은 사전 할당 이미지 풀 + 슬롯 인덱스(20슬롯).
- MAP이 먼저 — 사용자의 지시.

## 정정된 D1 제안
- D1 = 원본 복사본 안에서 마스터 플랜 Phase 1의 **첫 슬라이스**: 획득 루프(1.1, 원본 프레임 루프에서 트래커를 뺀 것) + 트래킹 루프(1.2, GPU 커널 — GPU 우선 결정) + 결과 큐를 소비하는 저장 루프(1.7) + 정지·종료 프로토콜(1.9). 모터·스케줄러 루프(1.3~1.6)는 D2.
- 이것이 성과 리뷰의 "획득 → 트래커 → 저장 → 정지/재시작" 슬라이스와 같고, decisions.md의 방법과 일치함.
- 수용 게이트는 그대로: N1 픽스처 수치 동일(GPU 커널이면 10,043 프레임 전체 실행이 먼저 필요 — 200프레임 기록만 있음), F1 카메라 라이브 5분 + 파일, F2 깨끗한 정지·재시작, F3 로터 signed(D2에서).
- 규모: 옵션 A로 제가 말한 것보다 큼. 리뷰어의 원래 슬라이스임.
