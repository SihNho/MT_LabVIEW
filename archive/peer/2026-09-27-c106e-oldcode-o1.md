## Answer

**Verdict:** the claim is right about why O1 failed, but wrong about which input should replace it. I didn't run anything: every result below comes from reading the code against the Python docs.

**What is right.** The HEAD copy the diagnostic fetched (`%TEMP%\c106e_old_cm2v047a\stage_prerun_head.py:1292-1317`) splits a command only on `&& || ; |`. It then tokenises each piece with `shlex.split(posix=False)`. Python's docs say shlex whitespace "includes space, tab, linefeed and carriage-return" (https://docs.python.org/3/library/shlex.html). So in `wc -l x<NL>py -u R`, the newline is just whitespace, `py` becomes an ordinary token, and HEAD finds R. O1 predicted the wrong thing; the edit did not cause the failure.

## 1. Strongest reason the claim is wrong: HEAD finds the archived shape too

The archived shape is `wc -l \"x<NL>py -u R<NL>\"` (`archive/peer/2026-09-27-c103d-hooks-before.md:53-62`). Those quotes are **backslash-escaped**: to bash they are literal characters, so the newline ends the first command and line 2 runs R (line 59 of that file says so).

Python's docs, same page, on non-POSIX mode: "Quote characters are not recognized within words (`Do"Not"Separate` is parsed as the single word)" and "Escape characters are not recognized". So `\"x` starts with `\`, and the `"` inside it is literal. It opens no quoted span. HEAD tokenises the command as `\"x`, `py`, `-u`, R, `\"` and finds R.

That review's own line 64 says "I expect the stage launch gate to miss this … **I have not run this**." The claim relies on a prediction that was never measured.

HEAD only misses the plain-quote form, `wc -l "x<NL>py -u R<NL>"`. There the quote opens a token, so shlex groups everything up to the closing quote into one token. But in that form bash does **not** run R: the newline sits inside a double-quoted argument to `wc`. PowerShell treats a multi-line double-quoted string the same way.

So the proposed replacement is a command that launches nothing. HEAD's miss on it is correct. The new code finds R there only because the first piece, `wc -l "x`, raises "No closing quotation" and falls back to `str.split()`. That is a false positive, harmless for a gate, but it doesn't test the hole.

## 2. Alternative explanation of the same evidence

HEAD's real blind spot is **not quoting**. It is the token walker running past the end of a line. A flag-only first line swallows the `py` on line 2 as its "script":

- `py -V<NL>py -u R` is tokenised as `py -V py -u R`.
- The walker skips `-V`, takes `py` as the script, sees it doesn't end in `.py`, and skips ahead. It never looks at R again.

This fails on HEAD, and bash really does launch R. The self-test on disk already uses this input (`tools/bench/selftest_stage_prerun_c106e.py:70-74`), not the quote-spanning one the claim proposes. So the claim's proposed fix contradicts the file it is meant to fix.

## 3. What would falsify the claim

HEAD's `launched_py` **finding** R in the archived backslash-quote command. From the shlex rule quoted above, I expect exactly that.
