## Answer

**Verdict: C1 is wrong. C2 is unproven, and 137-7 as planned cannot prove it. C3 is right but understates the loss: the Error List read that crashed was already on disk.** The data that refutes C1 was saved by 137-5 before the KeyError.

## 1. Strongest reason the claims are wrong

**C1 says the Select break is a conflict between `t` and `f`. LabVIEW's own Error List says the break is at `s` itself.** 137-5 read the Error List at script line 108, before the crash at line 109, and saved it as `tools/bench/errorlist_c137_5_routes_20261002_154406_raw.json`. Entry index 20 (`:598-600`) reads: *"The type of the source is 1D array of boolean. The type of the sink is boolean."*
- The `s` input of Select only accepts a single Boolean. NI's help says `t` and `f` "must be of the same type, but they can have different numeric representations" and says nothing about an array at `s` ([Select help mirror](https://rajsite.github.io/unofficial-lvdocs/glang/Select.html)).
- The NI Idea Exchange request "Select … accept array for its Select input" is still status **New**, never built ([idea 1062760](https://forums.ni.com/t5/LabVIEW-Idea-Exchange/Select-Comparison-Function-accept-array-for-its-Select-input/idi-p/1062760); also [forum thread 3244048](https://forums.ni.com/t5/LabVIEW/Select-function-for-arrays/td-p/3244048)).
- So C1's idea that "array-`s` Select needs `t`/`f` both arrays or both scalars" assumes an element-wise Select that LabVIEW does not document. The draft's "Select with a Boolean-ARRAY `s`" (`diag_c136_1_routes_plan.json:2`) can probably never be built as drawn, whatever `t` and `f` carry.
- **137-7's own prediction that C1 and C2 will read Is Broken? False (`diag_c137_7_types.py:9`) is already contradicted by this.**

**U3b did not fail because of the break. It failed on a wrong name.** The plan looks for the Select output as `"s? t: f"` (space after the colon, `diag_c136_1_routes_plan.json:19`). The measured name is **`'s? t:f'`, no space** (`diag_c128_2_donors.log:62`).
- This exact bug was already caught by review `peer_c128_1_errsel.log:9-11`, so it is a repeat of a known class of failure.
- The dry pre-run cannot catch it: it "passes" against uid #0 (`diag_c136_2_prerun.log:83`).
- **137-7 repeats it.** `diag_c137_7_types.py:65` looks up `N["sel_out"]` for all five Selects. That gives 5 lookup failures and no output types at all.

## 2. Other explanations of the same evidence

- **U3d (Less?.y ← KMX) did not cause a new break.** It joined wire 29708, the existing `f` net of Select. That net plausibly broke at U1c already: `t` got an I32 array while `f` held a DBL single value.
  - The new "Polymorphic terminal cannot accept this data type" entry (`raw.json:250`; not in the base list, total 51) fits that.
  - 29708's Is Broken? was never read before U3d. 137-5 only read its value and type (log:75, 104).
- **The "source is void → sink is DBL" entry (`raw.json:222-224`) is not tied to any wire.** C2 assumes it is the U6 exit wire. It could equally be wire 29740, Less?.x ← Array Max & Min `min value`. That `min value` has no type because the Array Max & Min input was never wired (U3b failed). Wiring KMX (DBL) into Less?.y at U3d could have broken 29740 *after* its U3c read of False (log:122). 29740 was never re-read.
  - The Error List read used no double-clicks and carries no uids (`ring-p4.md:369`-class gap), so the attribution is open.
- **U6:** a defect in the exit route and a source with no type both predict "outer wire broken". Only a source that does have a type separates them (see §4).
- **A failed prediction the brief leaves out:** the plan expected KMX to be an **I32** constant (`diag_c136_1_routes_plan.json:2`). It came back **DBL** (log:75). On its own this is harmless: I32 and DBL convert with a coercion dot, and 2147483647 is exact in DBL. But it shows the "constant on `f` before `t` is wired" route cannot produce I32.

## 3. What would falsify each claim

- **C1:** already contradicted by the bool-array → bool entry. In 137-7 it is refuted if combination C1 (`t` and `f` both Num arrays) still reads `s` broken, or if `s` reads as a single Boolean on the bare Select (SEL0). C1 survives only if C1's `s` wire comes back unbroken.
- **C2:** refuted if an exit from frame f0 whose source does have a type still gives a broken outer wire after RemoveLooseEnds. For example, wire IAN's `array` input to an array constant inside f0, then make the same crossing.

## 4. What 137-7 cannot tell apart, and the cheapest test

What 137-7 cannot tell apart:
- **No single-Boolean `s` control.** All four combinations feed `s` an array, so it cannot separate "`s` rejects arrays" from "`t`/`f` mismatch". If all four break, the matrix adds nothing.
- **A confound in C1, C2 and C4.** GT2, GT3 and GT4 have `y` unwired (`diag_c137_7_plan.json:17-19`); only GT1 has `y` wired. Wire `y` from km1 on all four.
- **U6 keeps the source with no type.** It will read void on the tunnel faces whichever cause is true. So it can never produce the *passing* exit crossing that PD309(b) requires before the simulator models the FS exit (`ring-p4.md:213-215`).
- **Types are read only after all wiring.** Neither run records when 29708 or 29740 broke.
- **Select output types will not be read** because of the name bug.
- **Error List entries are still not tied to wires.**

**Cheapest test that separates the claims (one scratch copy, about 6 wiring operations):**
1. Select A: `s` ← a **single** Boolean constant, `t`/`f` ← two I32 array constants.
2. Select B: `s` ← a Boolean **array** constant, `t`/`f` ← the same two arrays.
3. Read Is Broken? on each `s` wire. If A is unbroken and B is broken, `s` rejecting arrays is settled and C1 is refuted.
4. U6′: inside f0, wire IAN `array` ← an I32 array constant, then make the same exit wiring and run RemoveLooseEnds.
   - Unbroken: C2 holds and this is the passing U6 that PD309(b) needs.
   - Still broken: the cause is the exit route, not the type.

Also fix `sel_out` to `'s? t:f'` before 137-7 runs, and re-read 29708 and 29740 between wiring steps.

**C3:** agreed that it is a plain script bug, and 137-7 already reads the `total`/`expected` keys (`diag_c137_7_types.py:81`). But the Error List data was not lost; only the comparison was. The raw file should be cited as evidence instead of being treated as missing.

**What would change my mind on C1:** a measured unbroken `s` wire carrying a Boolean array into Select in LabVIEW 2026. That would mean NI added element-wise Select after the 2015 idea, which I found no record of.
