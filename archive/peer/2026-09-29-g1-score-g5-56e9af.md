QUESTION:
In Windows PowerShell 5.1, which character encoding does Get-Content use by default when it reads a text file that has no byte-order mark?

KNOWN ANSWER (verified on the machine / vendor files):
The system's legacy ANSI code page ('Default', e.g. Windows-1252 or cp949 on a Korean system), not UTF-8; UTF-8 without BOM must be read with -Encoding UTF8.
KEY POINTS: ANSI / system default code page; not UTF-8; -Encoding UTF8 needed

When it reads a file with no byte-order mark (BOM), Windows PowerShell 5.1's `Get-Content` uses the **`Default` encoding: the system's active ANSI code page.** The Microsoft docs say this directly, so the evidence settles the question.

- **Get-Content reference page for 5.1:** the `-Encoding` parameter's default value is `Default`, which "Uses the encoding that corresponds to the system's active code page (usually ANSI)."
  https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-content?view=powershell-5.1

- **about_Character_Encoding page for 5.1:** under "For cmdlets that read string data in the absence of a BOM," it says: "`Get-Content` and `Import-PowerShellDataFile` uses the `Default` ANSI encoding. ANSI is also what the PowerShell engine uses when it reads source code from files." It also defines `Default` as "the encoding specified by the active system locale's ANSI legacy code page."
  https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1

The actual code page depends on the machine's system locale. For example, US English systems usually use Windows-1252, and Korean systems usually use CP949. This means a UTF-8 file without a BOM that contains non-ASCII characters will be misread unless you pass `-Encoding UTF8`. The same page notes that `Import-Csv`, `Import-Clixml` and `Select-String` behave differently: they assume UTF-8 when there's no BOM. The code-page examples are general Windows knowledge, not taken from these pages.
