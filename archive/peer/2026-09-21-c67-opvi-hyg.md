## Answers to the four numbered questions

**Q1 — byte-identical rewrite, or a change after the `after` probe?**

*Byte-identical:* I found no documented mechanism, and one good reason against — recompiled object code is written **into** the VI on save ([NI](https://forums.ni.com/t5/LabVIEW-Development-Best/Why-does-LabVIEW-give-all-my-VIs-dirty-dots-when-I-only-changed/ba-p/3484087)), and a save by a newer LabVIEW re-serialises the format (CLAUDE.md rule 1's own `19 00 80 00` / `26 00 80 00` check). So a real save should always move md5. **Inferred, not measured** — I could not find NI stating the file is *always* byte-different after a redundant save. Honest position: md5 identity is strong evidence of no save; it is not proof of no *write*, because an identical-content write moves only mtime.

*After the probe — yes, and this is the live one:*
- Running a VI compiles it if needed; the recompiled object code marks it modified with no source edit ([NI forum](https://forums.ni.com/t5/LabVIEW-Development-Best/Why-does-LabVIEW-give-all-my-VIs-dirty-dots-when-I-only-changed/ba-p/3484087)). Unless separate-compiled-code is on, that dirt lives in the `.vi`.
- Closing a VI Server reference to a modified VI is a documented save-**prompt** trigger; the thread's participants found no flag that suppresses it and fell back to the private `App.UnattendedMode` ([NI forum](https://forums.ni.com/t5/LabVIEW/LabVIEW-prompts-to-save-the-vi-when-closing-the-reference/td-p/980820)). In an unattended run, a modal save dialog is precisely what this project's dialog-dismissal machinery might answer.
- When the last reference to a dynamically loaded VI closes, LabVIEW unloads it ([NI](https://www.ni.com/en/support/documentation/supplemental/13/closing-references-in-labview.html)) — which here happens after `[Y]`.

*Ruled OUT, plainly:* **auto-save**. It writes to `…\LabVIEW Data\LVAutoSave\`, never over the original ([NI forum](https://forums.ni.com/t5/LabVIEW/Autosave-file-location/td-p/1445524)). Also inapplicable: the save-prompt thread's "saved in a previous version" cause — these were built 2026-09-14 in LV2026 and opened in LV2026.

*A mitigation the claim could have cited and didn't:* `tools/lv_restart.py:13` force-kills LabVIEW (`Stop-Process -Name LabVIEW -Force`). A force-killed process cannot prompt and cannot save. So the quit-time hazard is mechanically closed **provided every teardown goes through that path**. The residual window is between this run's `[Y]` and the next `fresh()` kill, with LabVIEW alive holding a dirty, four-times-run op VI.

**Q2 — is md5+size sufficient? does ignoring sha256 weaken it? should mtime be in the check?**

Ignoring sha256 **does not** weaken the conclusion — md5 collisions need crafted input, LabVIEW is not an adversary, and size is compared too. But it is already computed (`tools/hash_probe.py:33`), so comparing the whole parsed dict costs one `==` and retires the question; there is no reason to compare a hand-picked subset.

mtime **should** be in the AFTER check and is the more sensitive of the two: md5+size is blind to an identical-content rewrite, mtime is not, and it costs a `stat`. The run already reads it — at `[L0d]` only (`diag_c67_opvi.py:520-526`). Reading it again at `[Y]` and comparing both against the *2026-09-14 constants* rather than a within-run baseline is what turns this gate from a tautology into a tripwire, and puts the op VIs on the same footing as `PINS` at `:164-166`.

**Q3 — does running the op VI over ActiveX put it in a state where LabVIEW may later write the file? Cheapest READ to detect it?**

Yes, plausibly — but separate two things:
- **Changed indicator values are not themselves at risk.** A `.vi` stores *defaults*, not current values, so `UID 2` going 0 → 23561 → 23693 → 23561 → 23498 does not by itself put bytes on disk.
- **The recompile-on-run path is what dirties the file**, per the NI result above, independent of panel values.

So: dirty-dot yes (documented); *write* only on an actual Save — prompted at reference release/unload (documented), or triggered by anything saving dependents. Whether LabVIEW 2026 raises that prompt for a VI loaded via ActiveX `GetVIReference` into the full IDE I have **not** measured, and the cited thread concerns `Open VI Reference` in application code. Treat as plausible, not established.

Cheapest READ to detect such a write after the fact: **mtime, re-read at the start of the next batch against a pinned constant.** One `os.stat` per file, no LabVIEW, no lock, and it catches every write including a byte-identical one. Second cheapest, for a format question, is the 4-byte saved-version check rule 1 already specifies.

## Where the evidence does not settle the question

Whether the post-`[Y]` window has *ever* produced a write is unmeasured — nobody has re-read these mtimes since the run. T2 answers it in seconds. And I cannot tell from outside whether these op VIs have separate-compiled-code enabled; if they do, a recompile lands in the `.lvobjcache` and never touches the `.vi`, which would make the whole dirty-file hazard moot for them. That is checkable in one property read and is worth knowing before anyone hardens this gate.

The gate's name overstates what it checks — in the same `finally` block as the two gates under review, and it is those 8 references that keep the dirty op VI resident past `[Y]`.
