## Answer

**The claim is refuted.** The failures are an addressing defect in the recipe, as the claim says, but not the one it names. Diagram[21] is the correct diagram. The recipe clears the two fields `address()` needs to handle a tunnel, so the lookup could never succeed.

**1. Strongest reason the claim is wrong.** All five sinks are `SelectorTunnel` **OuterTerminals**, not node terminals.
- `graph_k_80_owners.json` lists them as `{"uid":5825,"class":"SelectorTunnel","owner":"CaseStructure"}`, and the same for 5702, 10750, 5725 and 5967.
- Their terminal rows (5883, 6038, 10760, 5741) all read `owner_class:"SelectorTunnel", term_class:"OuterTerminal"`.
- A tunnel is owned by its Case structure, not by the diagram, so its uid is never in `Diagram[k].Nodes[]`, whichever diagram is named.
- `Stage.address` already handles this. `tools/stagekit.py:728-739` maps a tunnel's outer terminal to its structure node, but only when `owner_class`/`term_class` say so.
- The recipe hard-codes `"owner_class": "", "term_class": ""` (`tools/recipes/stage_d1_l2a1.py:90`), so that branch is skipped and the lookup fails at `stagekit.py:740-741`.

**2. The diagram is correct.**
- The tunnels share their x position with the Case structures that were moved: 5825, 5702 and 5725 sit at x=3771, the same x as CaseStructure #5540, which was moved to (3771,1033). #10750 sits at x=3305, the same x as #10445, which was moved to (3305,972).
- Those moves landed on "Diagram[21]" (`stage_d1_l2a1_86-5.log:43,100`), which is dest #23166 (`stageplan_l2a1.json:19`).
- So Diagram[21] holds the owning structures, and `frame_diagram` names the right diagram. The claim's first sub-hypothesis ("wrong diagram / pre-move location") is not supported, and neither is its second (uid→index picks a different diagram).
- The competing explanation ("the build left the sinks elsewhere") is also not supported. The owners are where the plan put them, and E1 42/42 plus PB extra/missing [] agree.

**Second latent defect.** `cfw_second_pass` calls `self.address(dst, False)` without `objs` (`stagekit.py:853`). Even with the class fields restored, the geometry lookup `pos[uid]` at line 730 would raise KeyError. There is a further question: `wired_terminals(dst["uid"])` (line 855) and `node_terms(dd, dn)` would then address the structure node, so the terminal must be matched by `verify_term_uid` on the structure. Only the uid path at line 750 can do that reliably. The recipe's own comment "tunnel/register **node** sinks" (line 9) and its filter (line 84, which excludes only ControlTerminal) show the classification was assumed, not read.

**Alternative explanation.** The P2 row filter picks the wrong set of rows. Rows whose sink is a tunnel's outer face should have been skipped under PD184, like the register-face rows at log 686-688, or routed through the structure path. They were sent down the plain node path instead.

**3. What would falsify my reading (and support the claim).** A live read of `D1_l2_a1_20260925_235224.vi` showing that CaseStructure #5540 or #10445 is *not* in Diagram[21].Nodes[] (Diagram[21] uid ≠ 23166 at P2 time), or that a SelectorTunnel uid *does* appear in some diagram's Nodes[].

**4. Your question (3), PD184 coverage.** PD184(a) lists "register face" among the E1 + RBW (+CT) only rows. These five sinks are a Case tunnel's outer face, the same kind of structure face. The recipe skipped the SR faces (log 686-688) but not these, so either the filter should skip them or it needs the structure-addressing path. That is a judgement call and I have not settled it. The artefact itself shows no fault: E1, PB and RBW all passed.
