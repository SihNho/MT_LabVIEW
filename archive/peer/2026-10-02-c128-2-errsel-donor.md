## 1. Strongest reason the claim is wrong
**Unbundle By Name:** the bed graph `tools/bench/graph_ring_p3a_20261001_190155.json` contains several `owner_class: "NamedUnbundler"` nodes. Some have both terminals unwired and are clean copy sources:
- #10764 (input t10806 unwired, output "Source" t10790 unwired, diagram 10213)
- #32083 (t32085 / t32089, diagram 32067)
- #32194 (t32200 / t32212, diagram 32166)
- Wired ones too: #27462, #15145, #15364, #15355

The copy function accepts any donor file under claudeDev, not only registered ones (`tools/gscript.py:4801-4803`). The bed file `D1_ring_p3a_20261001_180540.vi` is listed in claudeDev (`diag_c127_5_errsel.json:55`). So an Unbundle By Name donor is reachable today.

Caveat: none of these donors has a `status` output (`result_127-5.json:10`). After it is re-wired to an error cluster, the selected element may not re-bind ("Source" vs the error cluster's `source`). That is a re-wiring question, not a missing donor.

## 2. Your framing points, answered from the files
- **Identity of the nodes (point 1).**
  - `NamedUnbundler` is the class name our reader really reports (bed rows above), so that test was right.
  - Primitives report as class `Function`, `GrowableFunction` or `Comparison` (`diag_donor_census.log:19-81,131`; `allterms_bed_20260923.json:433`), never "Select". Matching by terminal names was the right idea. Primitive terminal names do come back in the Context Help form (`x*y`, `x+1`, `size(s)`: `allterms_bed_20260923.json:1877-1993`).
  - **But the Select signature `["f","s","s? t: f","t"]` has never been measured in any of our files.** `s? t: f` appears only in scripts and peer briefs. It was typed by hand in `diag_c123_ring_p3_routes.py:27` and copied into the plan (`diag_c127_5_errsel_plan.json:18`). The bed shows no `s`/`t`/`f` terminal at all, so we have never seen a real Select row. The spacing (`s? t: f` vs `s?t:f`) is unchecked.
  - 1,355 bed terminals have an empty name (`allterms_bed_20260923.json`, count). The rows I sampled belong to subVIs, tunnels, constants and diagrams. Whether a primitive can report empty names is not measured. If one does, an exact `sorted(names) == sig` match (`diag_c127_5_errsel.py:42`) misses it silently.
  - NI's public sources only describe the terminals as s/t/f ([LabVIEW Wiki: Select function](https://labviewwiki.org/wiki/Select_function), [NI forum](https://forums.ni.com/t5/LabVIEW-Idea-Exchange/Swap-T-F-Terminals-in-Select-Function/idi-p/1007147)). Nothing I found confirms the exact string VI Server returns.
- **Empty read (point 2).** Yes, `read_terms` can return `[]` without raising. It raises only on the op's error out (`allterms.py:80-82`). If the indicator arrays come back empty, `n = min(len…) = 0` and it returns `[]` (`allterms.py:83-85`). The script never logged `len(rows)` (`diag_c127_5_errsel.py:39-43`).
  - The only sign the copies were in memory is indirect. `close_panel` failed with "panel not open" for every copy (`diag_c127_5_errsel.log:35-41`), and references opened/closed were 11/11. That shows the VIs were opened, not that any terminals were traversed.
- **Were the 7 files plausible holders (point 3)?** Weakly.
  - The earlier working donor search (`diag_c103_wait_donor2.log:4-9`) found its node by **node label**. This run switched to an untested terminal-name signature.
  - Only `Comparison Functions.vi` is a strong Select candidate by name.
  - The census also skipped donor-type files already in claudeDev: `DONOR_Ex3_PrimitiveFunctions.vi` ("Example 3 - Primitive Functions", `docs/REFERENCES.md:134`) and `DONOR_arrayops.vi`.
  - I could not find a primary source that names a shipped VI containing both nodes. NI does not publish block diagrams. The error-handling VIs in vi.lib (General Error Handler, Simple Error Handler, Merge Errors) are likely holders of Unbundle By Name on `status`, but that is my unsourced guess.
  - A copied vi.lib VI finds its vi.lib subVIs through LabVIEW's `<vilib>` path. That is my recollection, not verified. If wrong, the copy would load with a "Find the VI" dialog.
- **Select in the bed (point 4):** none. No term named `s`, `t`, `f` or any `?…:` pattern in `graph_ring_p3a_20261001_190155.json`. This matches the earlier "Select 0 hits" result in `result_127-5.json:10`. But because the signature itself is unmeasured, this is not independent evidence.
