## 1. Strongest reason the claim is wrong

**The claim says "with both fixes the rest of run 2 already passed", but nothing has run since the fixes.** That sentence is an inference.

- `tools/bench/sim_k_split.log` has only two runs (lines 1–6 and 7–70). The A0 label in the log (`:10`, "offset == L7's") differs from the current source (`sim_k_split.py:47`, "within 1 px"), so the source was edited after the last run.
- The rows file on disk is still run 2's output. `plan_k_rows.json:93` reads `"#5058 Bead is good? array in": "(e) in"`. After the fix it should also say "(e) out via Bead is good? array out".
- **The claim's account of run 2 does not match the log.** Line 34 lists four unused terminals: `'Bead is good? array in'`, `'Bead is good? array out'`, `'Image In'` and `'x,y,z array'`. The claim says t0's row was credited to t0 "only", which would leave t0 used. But t0, Image In and x,y,z array (all (e) inputs) were never counted as used at all. So run 2's code never added the (e) inputs to `used`. That is a second defect the claim does not mention, fixed by the `own` line (`sim_k_split.py:112-114`). Either the diagnosis describes code other than what ran, or the log was misread. Both are the "inference over measurement" pattern.

## 2. Alternative explanations of the same evidence

**(a) The fixed P3 can no longer fail for t3.** Credit comes from S1's effective sources of the broken sink (`sim_k_split.py:109-110`), not from what happened to t3 in the end graph. t3 is in S1's source set for t0, so t3 is "explained" whether t3 is open, wired straight to t0, or misrouted. The gate went from failing on an artefact to passing by construction. That is not the same as being correct.

**(b) The missing t3 row is a property of the diff, not a relay bug.** `computation_diff` produces rows keyed by sink terminal (`tools/vigraph.py:744-753`). An output shows up only at its consumers. The relay collapse did *not* hide the t3 edge: t3 is in t0's effective sources, and the graph confirms it. In `graph_k_s4_20260925.json`:
- #5796's outer terminal (term_uid 5815) is unwired (`wire_uid 0`), so nothing after the loop consumes t3.
- #5805 has one inner consumer, #5702, via w6041.
- #5702 feeds #5680 via w5710, and #5680 feeds t0.

So the competing explanation as framed is **not supported for stage K**. The claim's measurement (t3's only consumer is t0) holds.

**(c) A real blind spot, but in a later stage.** t0 is fed through Case-structure selector tunnels:
- In frame 5582 the path is #5702, which carries the shift-register value.
- In frame 5592 it is #5967, fed through LoopTunnel #5569 by FSIT #5818 (w5812), the same wire that initialises the register. That is the "initialized array" source.

`effective_sources` merges both frames and ignores the selector. So a reconnection that swaps which frame gets the register value and which gets the initial value gives an identical set, {t3, init}, and a computation diff of 0. This is the same class as the cycle-74 blind spot. It does not affect stage K, because 177(b) deliberately leaves the mixed pair #5796/#5805 for L2-A1 (`docs/d1-loop12-17-split-plan.md:489`). **L2-A1 must not use a computation diff of 0 as its acceptance test for this pair.**

**(d) The A0 relaxation weakens an identity check.** A0 is the only thing tying BODY #23166 to LOOP #10170. `par(BODY)==par(l7_body)` only compares the diagram one level up, and the pixel offset was acting as a stand-in for "this body belongs to this loop". Allowing ≤1 px turns an unexplained (10,1) vs (9,1) difference into a pass without explaining it. The right fix is to check structurally that #23166's owner is #10170, from the contract's diagram tree, not to loosen the pixel tolerance.
