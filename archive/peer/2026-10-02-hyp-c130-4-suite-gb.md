## 2. Alternative explanations of the same evidence
- **A — the failing run is not a valid result at all.** The code changed while it ran. The suite runner also threw away all output on timeout: `except TimeoutExpired: out, rc = "", "TIMEOUT"` (`diag_c130_2_suite.py:40-41`). Python's `TimeoutExpired` does carry the partial output (`.stdout`/`.output`; https://docs.python.org/3/library/subprocess.html). So we cannot tell which of the 13 sub-tests had passed or failed by 240 s. A sub-test failure that happened before the kill would be hidden behind "TIMEOUT".
- **B — something kept running after the timeout.** On Windows, `kill()` calls `TerminateProcess` on the direct child only. Python's docs say this, and Microsoft's documentation describes the call as ending "the specified process and all of its threads", with nothing about its children (https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess). So whichever sub-test was running at 240 s was left running on its own. Applying the 600 s run's timings, that was probably `selftest_stamp_window`, which mostly sleeps (`selftest_stamp_window.py:75,87,107`). It overlapped `c100_v5wrap` … `stoprecord_*`. `selftest_guard_peer_jev` writes fake failing logs into `tools/bench` and appends to the real `jev_gate.log` (`selftest_guard_peer_jev.py:285-309`). If it had been the one cut off, other tests would have seen extra state. The timing estimate makes that unlikely, but it is not proven.

## 3. Q2: is ~250 s normal, or a sign of a hang?
It is normal, not a hang. The 600 s run measured each of g6's 13 sub-tests on its own, and they add up: 27+7+14+1+0+0+2+1+10+3+115+44+23 = **247 s**, against 250 s measured (`suite_all.log:5,6,11,32-42`). The time goes on two things:

- **`selftest_logclass_cmd` (115 s).** It surveys every `tools/bench/*.log` (`selftest_logclass_cmd.py:82-88`), and that folder only grows. It also re-runs 7 other self-tests (`:100-104`), several of which g6 already runs (audit_c4c_split, stamp_window, guard_peer_jev, failre).
- **Fixed sleeps in `stamp_window`.** About 22 s of its 23 s.

No peer is called. So the runtime grows with project history, and the 240 → 250 s overrun was predictable rather than a fluke. It will keep growing toward the 300 s per-test cap inside g6 (`selftest_g6_peerset.py:24`). The 600 s ceiling only postpones the next timeout.

## 4. Q3: could the timeout have hidden a real failure?
Yes. Explanation A applies: the output was discarded and the code was mid-edit, so a sub-test failure on the intermediate code is possible and unrecoverable. Those intermediate files no longer exist.

What does settle the question for the **current** code is the 600 s run. It ran every g6 sub-test again individually, and all passed (`suite_all.log:5,6,11,32-42`). That covers the current code even without g6's own pass. The correct conclusion is: the failing run is invalid and carries no information about the code at either time, and the 600 s run is the only evidence. It is not "a timeout, therefore the code was fine".

- a failure in `selftest_g6_peerset` itself, or in any of its sub-tests, when the guard_bash group is rerun on files matching the md5s in `result_130-2.json`;

2. Rerun only `py -u tools/bench/selftest_g6_peerset.py` under bgrun (about 250 s) and compare its per-sub-test times with `suite_all.log`.
