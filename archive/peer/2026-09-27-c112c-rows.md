## Answer

The bug diagnosis holds, but the claim cites the wrong register as evidence, and the T1 row the bed does offer doesn't reproduce the situation B2a needs to test.

**1. Strongest reason the claim is wrong: the register it cites is bare, not a T1 candidate.**
- Register 9603→10544 on loop #10170 (the example in the `base_registers` docstring, `tools/stagexec.py:841`) has `wire_uid 0` on all four faces in `graph_l2b1_20260927.json`: terminals 25579, 25588, 22281 and 25587.
- `diag_c112b_addr.log:44` shows R #9603 is **SRB1**, a register B1 created and left bare. So the evidence that "the bed has usable WhileLoop registers" points at an unwired register.
- The same goes for 25545→25582 (SRB2): inner wire uids are 0.
- The shape of the log does fit the bug. It has no `LOOPS` line, and the script on disk prints one (`diag_c112c_rows.py:18`), so the log came from the unpatched script.
- But the **patched scan has not been run**. "The bug caused FAIL" is so far an inference, not a measurement.

**2. Other explanations, from the graph file:**
- **Registers with branched wires fail the test, as you suspected.** On 23508→23792 (loop #10170), R.inner's wire w23807 has 7 ends: source 5171 plus IndexArray, Function, two ControlTerminals and the register. So `len(rw)==2` fails and the row is correctly unusable.
- **One register does pass by hand:** 24083→24133 on WhileLoop #23041.
  - R.inner t24139, wire w24264: 2 ends, fed by SubVI #376 'error out' t3934.
  - L.inner t24190, wire w24285: 2 ends, feeding #376 'error in' t5683.
  - So I expect the patched scan to report at least one usable T1. That supports the claim. I have not checked 10850, 25339 or 25371 on loop #10170.

**3. The fidelity question: this row does not faithfully test B2a.**
- **The data type is already fixed on the candidate.** 24083 and 24133 have both outer faces wired (w9610, w4969). After you delete the inner wires, the outer wires still set the register's type.
- **SRB1 and SRB2 have no type at all.** Every face is unwired, so the type is Void, and whichever wire lands first sets it. [NI forum](https://forums.ni.com/t5/LabVIEW/Problem-with-un-initialized-shift-register-datatype/td-p/1599074) confirms both points: a new shift register is Void, it takes the type of the first object wired to it, and removing the only wire returns it to Void. Wiring into a Void register (does `wire_sr` succeed, and does the type propagate?) is exactly the case the fixture must cover, and 24083 does not cover it.
- **Index addressing is not exercised the same way.** 24083 is Shift Registers[0] of a loop with 2 registers. SRB1 and SRB2 are [4] and [5] of the 6 on #10170 (`diag_c112b_addr.log:44`). If `wire_sr` finds the register by index, index 0 cannot expose an ordering or off-by-one fault.
- **"Made in an earlier session" does not separate anything.** In a byte copy, every register is loaded from disk. Uids do not show creation order either: 9603 is a low uid, yet it is a B1 register.

**4. What would falsify the claim:** the patched scan still printing 0 usable ROW-T1 lines, given that 24083→24133 passes the test by hand.

**5. Cheapest discriminating test, offline:**
- Run the patched `diag_c112c_rows.py` once.
  - A `ROW-T1 … R #24083 … usable True` line confirms the bug claim.
  - No such line means a second bug in the patch.
- Then fix the fixture, since this is the gap the claim does not cover. Pick a register on **#10170** (10850, 25339 or 25371). Delete **all** of its wires, inner and outer, so it goes back to Void. Then re-wire through `wire_sr` RightIn/LeftIn. That reproduces SRB1's state: bare, Void, index greater than 0.
- Otherwise, run `wire_sr` directly on SRB1/SRB2 in the scratch copy.

Summary of my verdict:
- **Bug claim:** probably right, not yet measured.
- **"A usable T1 row exists":** true, but only 24083 is confirmed by hand.
- **"T1 faithfully checks B2a":** not supported. The typed register on a 2-register loop leaves both the Void-type case and index addressing untested.
