## Answer

Part (1) of the claim holds, and the alternative you asked me to test is refuted: OpNodeLabels_v0 does not filter. What fails is part (2), because the "fit" is a class blacklist tuned to three diagrams and the check only compares set membership. Part (3) is half right.

## 1. The strongest reason the claim is wrong: part (2)

- **The fit was tuned to the data that tests it.** `NOT_NODE_CLASSES` and the `endswith("Constant")` rule (`tools/stagexec.py:279-284`) were written from the only-SimReader lists in `parity_l2a1_82.log:40-42`. Re-running A1 on the same `parity_l2a1_82_real.json` will score 0 almost by construction, so it proves nothing about other diagrams.
- **The list is incomplete.** In LabVIEW's class hierarchy, Tunnel is its own branch, and it has subclasses the list does not name. For example, `ConditionalTunnel` sits beside LoopTunnel under `gobject/tunnel/` in NI's docs ([Linked Input Tunnel page, under conditionaltunnel](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/tunnel/conditionaltunnel/linktun.html)). The only tunnel names excluded are `LoopTunnel`, `FlatSequenceOuterTunnel`, `SelectorTunnel`, `Tunnel`, the two shift-register classes and `FlatSequenceInnerTunnel` (`stagexec.py:52,259-264,279`). Any other tunnel class on a diagram the plan has not touched yet will be listed as a node again. A whitelist would carry over to new diagrams: list only Node-branch classes.
- **`loop_parent()` can return `None`** when a loop's parent is ambiguous or unknown (`stagexec.py:299`). That loop is then listed on no diagram, which would produce the first real-only entries this check has ever seen.
- **Matching sets is not seeing what LabVIEW sees.** `reader_parity` compares sets (`stagexec.py:347`). But ops address nodes by position in `Nodes[]`, and `Nodes[]` is in creation order (`gscript.py:2501-2504`). SimReader builds its list in a different order: terminal-table order, then routed owners, then loops appended at the end (`stagexec.py:1014-1024`). Every index SimReader predicts may still differ from LabVIEW's even with zero set differences. Whether any offline gate uses those index values, not just membership, is not settled by this run.

## 2. Alternative explanations of the same evidence

**(a) The one you asked me to test: OpNodeLabels_v0 drops entries. Refuted.**
- The recipe feeds `Nodes[]` into a For loop through an indexing tunnel (index mode 1) with no conditional tunnel, and auto error handling is off (`tools/recipes/build_opnodelabels_v0.py:17-23`). That design outputs one element per `Nodes[]` entry. A node whose Label read failed would come back as uid 0 or an empty string, not be dropped.
- The real listing has no uid-0 entries and no "?" classes (`parity_l2a1_82_real.json:8-374`).
- NI's documentation puts Constant, Tunnel and Terminal outside the Node branch, while loops sit under Node → Structure. NI's URL paths show it: `gobject/constant/…`, `gobject/tunnel/looptunnel`, `gobject/node/structure/loop` ([NumericConstant](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/constant/numericconstant-p.html), [LoopTunnel](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/tunnel/looptunnel.html), [Loop](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/node/structure/loop-p.html), and the [LabVIEW Wiki Constant class page](https://labviewwiki.org/wiki/Constant_class)).
- **Caveat:** I could not fetch NI's text for the `Nodes[]` property itself (the page renders client-side). That `Nodes[]` returns only Node-branch objects is therefore inferred from the hierarchy plus this project's own measurements. None of the documents I fetched states it outright.
- The project's own records agree: `tools/bench/diag_queue_donor.log:15`, `tools/bench/priorart_c68_m4a.log:24`, `tools/recipes/build_d1_v0.py:246`. ControlTerminals are also absent from `Nodes[]`, which fits the same "Node-branch only" pattern.

**(b) Part (3) is only half right.** The prediction was written in the wrong order, but SimReader also had a real defect before the fit:
- It appended all 23 loops to every diagram (`parity_l2a1_82.log:36-38`). That is a bug, not a mis-ordered expectation.
- The claim's phrase "not a reader defect" holds only for the real reader.

**(c) Your evidence from run 3 is weaker than it looks.** Thirty ops with diff 0 only prove the indexes of the nodes those ops touched. A node missing after them in creation order would not have shifted anything.

## 3. What would falsify the claim

- Any diagram of D1_k outside the fitted three (#639, #686, #23166) showing a one-side-only entry after the fit. Likely candidates are an unlisted Tunnel subclass, or a loop that `loop_parent()` returns `None` for.
- A Style/Label read that shows a constant inside `Nodes[]`, for example "Numeric Constant" among OpNodeInfo_v0's Style names (`gscript.py:2659`) on the top-level diagram.
