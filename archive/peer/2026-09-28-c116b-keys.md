## Answer

**Verdict: the core claim holds.** The key sets differ because two different readers wrote the dumps, not because the two VIs differ. Your three consequences are weaker than you state them, though.

**1. Strongest reason the claim is wrong**
The claim itself survives the attack; the weak part is what you plan to do next. Your rev-2 contract compares record field names only (`tools/bench/diag_c116b_keys.py:13`, `:32`). Both dumps come from the same `wiki_build.read_live`:
- B3: `tools/bench/diag_c114c_b3graph.py:33`
- R1: `tools/bench/diag_c115d_graph.py:81`

So the field names are identical by construction, and the test cannot fail. Passing it says nothing about whether the two dumps can be compared object for object, which is what STEP 0b needs. Two further gaps:
- **`fs_tunnel_pairs` was never measured on either file.** R1's copy comes from the B3 dump (`diag_c115d_graph.py:84`, `:81`). B3's copy comes from the B2b dump (`diag_c114c_b3graph.py:15`, `:48`). `read_live` skips its own flat-sequence read whenever `fs_pairs` is passed in (`tools/wiki_build.py:252-253`). The field is B2b's data under both names. `vigraph` uses only `term_a`/`term_b` (`tools/vigraph.py:520`, `:539`), so this stays harmless while those terminal uids survive. The `wire_a`/`wire_b` values in the pairs are stale, and nothing should read them as R1 facts.
- **(c) "a fresh dump is needed because loops/owners are missing" is overstated.** Stagesim can take `loops` and `owners` from separate files (`tools/stagesim.py:247-259`). The real reason for a fresh dump is that R1 deleted 6 shift-register pairs on #637. B3's `loops` table (`left_of`/`right_uids`) is therefore stale for #637, and card P1 asks for the saved R1 file to be dumped anyway (`tools/bench/cards/task_116-2.json:34`). State that as the reason, so nobody patches B3's loops table by hand instead.

**2. Alternative explanation**
The two readers might also have walked different sets of objects, not just written different keys. If so, the object and terminal lists would not be comparable either. The log argues against this. Every class-count difference matches R1's planned retire set (`diag_c115d_graph.py:18-19`):

| class | B3 | R1 | change |
|---|---|---|---|
| Wire | 1956 | 1945 | −11 (the 11 stub wires) |
| Left/RightShiftRegister | 43 / 43 | 37 / 37 | −6 / −6 (12 SR uids) |
| InnerTerminal / OuterTerminal | 853 / 501 | 841 / 489 | −12 / −12 |
| LoopTunnel | 151 | 151 | 0 |
| **objs total** | 10185 | 10138 | **−47** = 12+11+12+12 |
| terminal rows | 5851 | 5827 | −24 |

Source: `tools/bench/diag_c116b_keys.log:14`, `:25`, `:7-8`, `:19-20`. Counts are not identities, though. The same counts could hide different uids (a removed object offset by an added one of the same class).

**3. What would falsify the claim**
Any of these would show a real difference between the files rather than between the readers:
- The uid-set difference B3 − R1 is not exactly the 12 SR uids, the 11 stub wires and their SR terminals.
- R1 − B3 is not empty.
- An object kept in both files has a different `owner` or class.

**4. Cheapest discriminating test (offline, about 10 lines)**
Load both JSON files and compare `{uid}` of `objs` and `{term_uid}` of `terminals`:
- Assert R1 − B3 = ∅.
- Assert B3 − R1 = SR ∪ STUBS ∪ {terminals whose `owner_uid` is in SR}.
- Assert `owner` and `class` are equal for every uid in both.

Make that the rev-2 prediction instead of the field-name check. It can actually fail, and it is the precondition for the P0 "kept object" table.

**On (b)**
It is correct that neither dump carries property values; the `objs` fields are uid/class/pos/owner only (log lines 13 and 24). The c115e review says the same (`archive/peer/2026-09-28-c115e-sel.md:103`, `:131`). No new tool is needed for the indexing-mode part. `stagexec` already reads it through `g.tunnels(...)["index_mode"]` (`tools/stagexec.py:2101-2103`). NI documents the property as LoopTunnel's `Index Mode` ([NI: LoopTunnel Index Mode](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/tunnel/looptunnel/indexmode.html); `docs/NAMES.md:75-79`). Constants and other node properties do still need a read on byte copies of both files.

**What would change my mind:** the uid-set test above coming out non-empty in R1 − B3, or showing an owner change on a kept object.
