## Answer

The claim holds. I tried to refute it and could not. Three things are wrong or missing in how it is framed, and the fix has never been run.

**1. Strongest reason it could be wrong: the fix is asserted, not observed.**
`tools/bench/selftest_sr_init_c123.py:101-102` already passes `{"uid": "900", "term_uid": 901}` and `{"uid": "311", "term": "outer"}`. The only log, `selftest_sr_init_c123.log:10`, is the failure. So the file was changed after the run, and no run of the changed file exists. The self-test is untracked, so git cannot show the old bare `"901"` form. The only evidence for that form is the error text. That evidence is good: `parse_addr` returns a dict unchanged (`tools/stagesim.py:327-328`), so a dict source cannot raise the message at `:330`. Until a rerun passes, "the bug is in the self-test" is an inference.

I traced the changed T8 through the code by hand. It should pass:
- **Source:** `resolve_uid("900")` gives 900 (`stagesim.py:299-300`).
  - `node_rows` uses `vigraph.node_of`, which is `owner_uid` for any row that is not a `ControlTerminal` (`vigraph.py:52,60`). That gives one row, 901.
- **Destination:** `cond_target` returns `None`, because the terminal name is not `cond` (`stagesim.py:950`).
  - Owner 311 has rows 3111 and 3112. No row is named `"outer"`, so `side="outer"` keeps only 3111, which is an `OuterTerminal` and a sink (`stagesim.py:349-357`).
- **Diagram and wire:** both ends are on frame diagram 1, and both wire uids are 0.
  - So the result is `how="new"`, and the new wire carries exactly [901, 3111] (`stagesim.py:1016-1019`).
  - The test copies the rows into `st` before the call, and `op_wire` changes those copies, so the gate's check at line 103 sees the change.

**2. Alternative explanation: the gap is in the simulator, not the test.**
`connect_route` and the LabVIEW connect both work in bare terminal uids (selftest lines 44 and 89). One could argue the simulator's `op_wire` should accept the same form. The code does not support that reading:
- The plans the executor runs, in `stagexec.py`'s own tests, use owner-based addresses: `{"uid": 2, "term_uid": 1024}` at `stagexec.py:3082` and `"new:T1.outer"` at `:3958`.
- The executor converts plan addresses to real terminals through `SS.resolve_addr` (`stagexec.py:1442, 1557`).
- `parse_addr`'s error message names exactly the two accepted forms.

So a bare terminal uid is not a valid plan address, and the self-test was wrong to use one.

**3. A worry I checked and ruled out: the fixture's ownership might not match a real graph.**
The fix assumes a left shift register's outer face is a row owned by the register (311), not by the loop (300). The same session wrote that fixture, so T8 could pass without that matching a real VI.
- The real graph `tools/bench/graph_k_s4_20260925.json` has `"owner_class": "LeftShiftRegister" … "term_class": "OuterTerminal"` rows, so ownership matches.
- The simulator's own register creation also does this (`stagesim.py:796`).

**What T8 does not show, even when it passes.** T8 runs the simulator's generic "new wire" rule. Nothing in it is specific to this route. Whether LabVIEW actually makes exactly one new wire with both ends when it wires a constant to the register's outer face is unmeasured. T10 says the model file `opmodels/sr_init_const.json` "not written yet". The test also wires a constant that already exists in the base graph, while a real plan would wire one made earlier in the same plan (`new:<alias>.value`). A passing T8 checks the simulator's structure only, not the function.

**What would prove the claim wrong:** the rerun fails T8 with any `SimError` from `resolve_addr` (0 or 2 matching terminals), or `how != "new"`, or a wire that does not hold exactly [901, 3111]. Then either the fixture or `resolve_addr`'s rule for picking the outer face is wrong, and the self-test is not the only problem.

**Cheapest test (offline, about 1 s, no LabVIEW):** rerun the file as it now stands:
`py tools/bgrun.py --material --max-min 3 --log tools/bench/selftest_sr_init_c123.log -- py -u tools/bench/selftest_sr_init_c123.py`
