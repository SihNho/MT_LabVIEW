## Answer

**Verdict: the claim is probably right, but run 1 cannot prove it.** On the recorded evidence, t6/t7 were `site`, and a 3-D DBL wire into an I32 scalar is a broken wire. That alone gives ExecState 0. But at least two other faults in the same run would also give ExecState 0, and nothing run 1 recorded tells them apart. The fix (t8/t9, already in `tools/bench/diag_c99b_bench.py:160-161`) is the right next step. "No other change" is only safe because the re-run now prints the terminal table when it fails.

**The layout itself checks out:**
- The measured layout is at `tools/bench/build_harness_gpu2.log:92-105`: t2/t3 error, t4/t5 return value (param 0), t6/t7 the first real parameter. `diag_c90_t0stamp_scratch.py:94,106` agrees.
- T1 in this run produced a control named `ring` on the temporary node's t6 (`diag_c99b_bench.log:28`), with parameters (return value, ring). The same position rule makes t6 = `site` on the stamp node.

## 1. Strongest reason it could be wrong
Run 1 has no reading of any terminal, wire or error after the two `wire_sr` calls. The diagnosis is inferred from indices, not read from LabVIEW (`diag_c99b_bench.log:31-33`: only ExecState, no wire uids).

The layout evidence also comes from a different node configuration. Both earlier measurements used either a Constant Adapt-to-Type `any` (c90 `FLAT_STAMP`, `const=1`) or no Adapt-to-Type parameter at all (gpu2). This build used `F_STAMP_NC`, a non-constant `any` (`diag_c99b_bench.py:63`). No one has measured whether `Node.Terminals[]` order stays the same for that configuration. The claim assumes it does.

## 2. Other causes that give the same ExecState 0

- **The `any` input was left unwired in run 1.** It has no data type until something is wired to it. I could not confirm from NI sources whether an unwired Adapt-to-Type input breaks the VI. The search found only the generic "a required input is not wired" diagnosis for broken CLFNs ([NI forum](https://forums.ni.com/t5/LabVIEW/Can-not-get-Call-Library-Function-Node-working/td-p/3848330), [NI CLFN reference](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/functions/call-library-function-node.html)). If it does break, run 1 would fail even with `site` wired correctly. The t8/t9 fix removes this cause too, so a passing re-run would not prove the claim.
- **`wire_sr` may have made no wire at all.** It raises only on the op's error cluster (`tools/gscript.py:808-811`). The docstring says to check the wire uid on both ends with `shift_reg_left`, and this script never does (`gscript.py:782`). A shift register left unwired breaks the VI by design (`gscript.py:732-736`). So a silent no-op on LeftIn/RightIn gives the same ExecState 0.
- **The wires may have gone to a different node.** `wire_sr` indexes body `Nodes[]` through the loop's own Diagram (`gscript.py:776`). `kS` came from `node_terms_uid(W, body, …)` against a Diagram index taken from `report("Diagram")` (`diag_c99b_bench.py:93-96`). Nothing checks that those two index spaces are the same.
- **Ruled out for now:** the For-loop N constant and the move into the body (as you said). The shift register's type is set by the `ring` wire made first, which is correct. The unwired `ring 2` indicator is harmless.

## 3. What would falsify the claim
- Reading run 1's scratch VI shows the stamp node's t6 is not `site`, or t6/t7 have no wire.
- Or: the re-run with t8/t9 still reads ExecState 0 and the printed table shows `any` in/out wired to the shift register. The cause would then be elsewhere: shift-register typing, the non-constant `any`, or `wire_sr` on a For loop.

## 4. Cheapest discriminating test
Run 1's scratch file is still on disk (`diag_c99b_bench.log:47`). The next run deletes it at start (`diag_c99b_bench.py:345-347`), so the read has to come first. Before re-running, use one read-only `node_terms_uid` call on that file's For-body stamp node. You need each terminal's `name`, `is_source` and `wire` (or `shift_reg(…, class_name="ForLoop")` for the register ends). It needs LabVIEW, so it is the manager's step, not mine.
- t6 = `site` with a wire, t7 = `site` with a wire, t8 = `any` unwired: the claim is confirmed.
- t6/t7 unwired: `wire_sr` failed silently, and t8/t9 won't fix it.
- t6 is not `site`: the layout assumption is wrong for a non-constant `any`.

If run 1's file is gone, the only evidence left is the table the re-run prints when it fails. A passing re-run confirms the fix, not the diagnosis.

**What would change my mind to "confirmed":** that terminal read showing wires on t6/t7 labelled `site`.
