## 3. Your three questions

**(1) Does the per-entry structure matter? No, on the measured data.**
- All 24 loose-ends rows in P3a's read have raw text `Wire: Wire has loose ends.` or `Wire:Wire has loose ends.` Both normalise to `wirewirehaslooseends` (`errorlist_D1_ring_p3a_…_181801.json:590–2393`).
- Their detail text is "This wire segment is not connected to anything…". No row of any other class contains `wirehaslooseends` in its raw or detail text (`:126–2394`).
- The merged entry sits at `li[0]`, after every other class's entry, so the order in which entries claim rows is unchanged.

**(2) Could the merged key license different rows? Only in a direction that drops a false failure.**
- The old entries 12 and 13 used the stricter key `wirewirehaslooseends`.
- An OCR read that dropped the "Wire:" prefix would have failed under the old file only if that row fell in the last two loose-ends positions. Under the merged file it passes. That position-dependence was noise, not location meaning.
- The merged key cannot pick up a row of another class, because none of their texts contain the substring.

**(3) Can the class-total debit hide a real mismatch? Yes.** This limitation was inherited, not introduced by the merge.
- Neither the old file nor gate C (`:117`, which compares per-class counts) can see a swap inside the class.
- Two cases would pass both:

  - Remove-loose-ends clears two old loose ends and leaves one new one elsewhere.
- The re-pin at `:122-126` then writes whatever count the read shows into the P3b-2 baseline. That is exactly the "53 for the wrong reason" risk the earlier review raised (`hyp-c131-5-el53.md:81`).
- PD274(a) excuses this on the computation side only: loose ends execute nothing. It does not cover the inherited expected count.
