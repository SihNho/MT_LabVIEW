## 1. The single strongest reason the claim is wrong

**`Wire` did not move across the seven moves.** The bed reads `Wire 1907` cold (`tools/bench/diag_c66b_s3b_m3.log:30`); after all seven `move_in` calls it reads `Wire 1907` again (`:284`); only the seven rows take it to 1914 (`:441`).

The pre-move terminal tables in the same log say what was cut: #3529/#3560/#3447 one wired terminal each (`:107,132,157`), **#48 seven terminals, 7 WIRED** (`:182`), **#10407 seven terminals, 7 WIRED** (`:207`, full table `:53-59`), both Locals one each (`:232,257`) — **19 wired endpoints across 12 distinct wires** (7 internal to the move set, 5 crossing to Diagram #639). Twelve wires were severed and **zero wire objects disappeared.**

Those twelve objects are still on the diagram with at least one end attached to nothing. That is LabVIEW's *"Wire has loose ends"* condition, a wiring error in its own right ([NI error list](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/errors/wire-has-loose-ends.html) — page title only; the body did not render for me), and NI ships two separate methods to clear it: [`VI.Block Diagram:Remove Bad Wires`](https://www.ni.com/docs/en-US/bundle/labview/page/lvscript/vi_block_diagram058remove_bad_wires.html) and [`AbstractDiagram.Remove Wire Loose Ends` (6375409)](https://labviewwiki.org/wiki/AbstractDiagram_class/Remove_Wire_Loose_Ends_method), which "traverses the referenced diagram and removes all wire ends that are not connected to anything."

So `ExecState` 0 has **at least two sufficient causes present simultaneously**, and the claim names only one. This project has already measured the same signature and read it the other way: `tools/recipes/build_d1_routeb_v0.py:64-66` — *"five structures moved with no intervening Remove Bad Wires left `Wire 1902 -> 1902` … so nothing died."* Nothing died is true; nothing was **cleaned up** is the other half, and it was never tested.

**Second, the inventory is wrong.** #10407 t6 `'position [internal units]'`, `is_source=True`, wire 9113 (`log:59`) was wired before the move and is re-wired by nothing: it is not in `INTERNAL_JOBS` (`diag_c66b_s3b_m3.py:200-210`) and **not in `NOT_ATTEMPTED`** (`:213-223`, log `:434-437`). Five endpoints on the moved objects are un-re-wired (#48 t3, #48 t4, #10407 t1, #10407 t4, **#10407 t6**); the run names four. A claim whose form is "what is missing is exactly *these*" is falsified by one unlisted item.

The sibling op carries the identical warning (`build_opconnectfromwire_v0.py:51-55`).

## 3. On the seams you named

1. **Is the inference valid?** No — and this is the part you most need in writing: **`ExecState` saturated at the first move.** It reads 0 at step 02, after `move_in #3529` and before any row existed (`log:130`), and 0 at all fourteen subsequent reads through step 16 (`:440`). A one-bit signal already pinned cannot distinguish one fault from twenty. **No measurement in this run would have read differently if three of the seven rows were wrong.** Counts cannot separate "unfinished" from "wrong": a branch onto an existing net, a wire landing on a legal-but-wrong terminal, and a coerced connection all move the same counts by the same amounts.
2. **Do the "passed" gates constrain anything?** A2 is a *pre-flight* check on three wires read **before** the first move (`log:84-100`) — it constrains nothing about the post-edit state, and the run says so itself (`:101`): `wire_source_owner`'s branch detection "has never been exercised on a wire known to have two sinks", and its terminator error 1055 cannot separate "no third endpoint" from "an endpoint that failed to resolve". So the pre-flight is weak *and* it is aimed at the wrong point in time.
3. **`move_in` on a CaseStructure.** The measured prior (`build_d1_routeb_v0.py:47-52`, `diag_moved_structure_terminals.log`) says after a `GObject.Move` **every** terminal of a moved structure reads `is_source` FALSE, output tunnels included. This run contradicts it: #10407 is addressed post-move as "5 sink terminals / 2 source terminals" (`log:350,371`). One of those two measurements does not generalise, and neither was re-checked. That is unresolved, not settled.
4. **Would `ExecState` 0 be what LabVIEW reports for the missing rows?** Yes — and equally for loose ends and for a type conflict. `ExecState` is one bit; the *reasons* live in the Error List, reachable only via `VI.Get Errors` (452), which your own record puts outside the exported ActiveX interface. There is no "specific error code" available to you on this path today. That is precisely why this question cannot be settled with the verbs used.
5. **Ordering.** There is no ordering that rescues this stage: **no subset of the seven is wire-closed** (every candidate subset has at least one wire crossing to #639), so no boundary inside this stage can read `ExecState` 1. That is why `unit_boundary()` (`diag_c66b_s3b_m3.py:559-572`) never fired and the run left **no file at all** (`log:459-460, 480`) — the save condition is unreachable by construction, which collides head-on with the 2026-09-19 "every step leaves a file" rule. Note `move_in` is not reversible — `build_d1_routeb_v0.py:39-40`: *"a move CUTS the wire and moving back does not restore it"* — so a `move_out` round-trip is **not** a usable control.
