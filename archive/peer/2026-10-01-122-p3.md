## 1. Strongest reason the framing is wrong
The question is not settled at "Property #35869". `tools/bench/main_vi_node_labels.json:2844-2847` records #35869 as an implicit `Value` node of the main VI, bound to a panel object labelled **`IMAQimage`**. That panel object has one writer in the pool graph:

- The indicator terminal t34982 (diagram 26117) is fed by wire w26665.
- The chain back from it runs through FSIT 25651 (w26107), then FSIT 20930 (w25631), then FSIT 20143 (w20729).
- It ends at **IMAQ Create #20436 `New Image` t20439** on frame 20261. Each step is in `graph_qrt_pool_20260928.json` (`terminals[term_uid=34982|25653|20936|20145|20439]`).

So #6810's image buffer comes from **#20436**, not #13938. The draft row list (`facts_c122_p3_rows.md:48`) still lists "which control #35869 belongs to" as OPEN, but the repo already has the answer. Draft row 4 ("IMAQ Copy 'Cam' →") rests on #13938 being the camera image, which the facts here do not establish.

## 2. Alternative explanation of the same evidence
#13938 and #20436 could be the same image under one name. NI Vision images are named, and a second IMAQ Create with the same name repoints to the same buffer without raising an error ([NI forum 637872](https://forums.ni.com/t5/LabVIEW/If-I-use-IMAQ-Create-twice-with-the-same-image-name-string-what/td-p/637872)). If both creates use the name `'Cam'`, the original prediction ("'Cam' feeds #6810") is true in meaning, and a wire trace simply cannot see it.

The only place #13938's own output went in the pool bed was w14741, into the Obtain Q_free/Q_work nodes as `element data type` (the X1 hit) and on to #15403. That looks like a queue template, not the camera image. #20436's `Image Name` arrives through FSIT 32955 ← FSIT 19598 (w20108), which I did not resolve to a constant. **The measurement does not tell these two cases apart.**

## 3. What would falsify the claim
- **N2 part:** a wire path from #13938 to t6857 in the P2a end state (`sim/ring_p2a/step_08_delete_object.json`), or a node other than #35869 at the end of the back-trace there.

I checked both. None of these occur, so the X1 explanation stands: the pre-P2a binding only affects #13938's forward list and the pool facts, which the rows doc already corrected by hand.

Rerunning the trace on step_08 instead of the pool graph would also clear X1 by construction.

What would change my mind toward "refuted": the name trace showing that `IMAQimage` is written somewhere other than #20436 at run time, for example by a local variable missing from the graph census.
