## Answer

**Verdict: supported.** I couldn't refute the claim. The machine records show that the bed was built from the same script text now on disk, and that card 111-5's pin is simply an old hash. One piece of the story is wrong, though: nobody showed that the pin was copied from card 110-4.

**1. Strongest reason it might not be just a stale pin, and the record that settles it**

The file changed at least three times during cycle 110, not once:
- md5 `7a162a51…`, reviewed by prior-art review c110d (`tools/bench/peer_priorart_c110e_l2b1.log:9`)
- sha256 `0682c108…` in a dry run at 19:25 (`tools/bench/prerun_records.jsonl:246`)
- sha256 `725c4787…` in a dry run at 19:30 (`tools/bench/prerun_records.jsonl:249`)

So the real risk is that the bed was built by one version and then the file was edited again before being committed as `e13177d9`.

The stage log itself can't answer this. `tools/bench/stage_d1_l2b1_c110d.log` never prints its own script's hash; it only prints the input VI's and the saved VI's hashes (lines 20, 557, 756). Two other records do answer it:
- **Launch record:** `tools/bench/stage_runs.jsonl:47` shows the 19:31:00 launch that produced the bed ran script sha256 `725c47875a…`.
- **Prior-art review c110e (19:28:37, 43 s):** it reviewed md5 `e13177d9…` (`tools/bench/peer_priorart_c110e_l2b1.log:9`, `tools/bench/cards/review_priorart-c110e-l2b1.json:12`). The same run wrote "NOVEL RECORD … sha 725c47875a29" for those same bytes (`tools/bench/peer_priorart_c110e_l2b1.log:28`).

So md5 `e13177d9` and sha256 `725c4787` describe one set of bytes, and that is what launched. Later records keep `e13177d9`: the c110d review card at 20:04 (`review_c110d-errorlist-cap.json:20`) and result 110-4 (`result_110-4.json:6`). The pairing is inferred from two hash computations in the same 43-second review run, not measured side by side. That gap is what the test in section 3 closes.

**Alternative explanations**
- **Where the pin came from:** it's not proven that it was copied from 110-4. Four earlier records carry `4ef10fc4`: `task_110-3.json:18`, `task_110-4.json:18`, `result_110-2.json:7` and `result_110-3.json:15`. The session's own result says "4ef10fc4 from 110-2" (`result_111-5.json:18`). The conclusion is the same either way: the pin predates the cycle-110 edits.
- **Shared code:** the bed's build also depended on `tools/stagekit.py` and `tools/stagexec.py`. Card 110-4 was allowed to write both (`task_110-4.json:51-52`), and neither is hash-pinned in 111-5 (`task_111-5.json:27-29`). So "no input changed unexpectedly" only covers the pinned inputs. It says nothing about whether those shared files match what the bed was built with.

**What would falsify the claim:** the current file's sha256 is not `725c4787…`. Or git history shows a commit touching the file after 19:31 with content other than `e13177d9`.

**2. The check that would have caught it before dispatch**

None exists. `tools/protocol.py` does nothing with `inputs[].md5`:
- `validate_obj` checks the schema and goal-map ids only (`tools/protocol.py:181-203`).
- `requires` checks that a file exists, not its hash (`_req_file`, `tools/protocol.py:656-660`; `check_requires`, `:684-690`).
- `requires_refusal` compares only the card's own md5 (`tools/protocol.py:707`).

A search for `inputs` across `protocol.py`, `tools/hooks/*.py` and `cycle_runner.py` found nothing. Pins are checked only after the fact, by hand-written diagnostics like `diag_c111e_md5.py`, which copied the stale pin into its own table (`tools/bench/diag_c111e_md5.py:11`).

The missing check is a hash comparison of every input when a card is written or bound: in `validate`, or in `bind` next to where it already records the card's md5 (`tools/protocol.py:473`). It would refuse any input whose pin doesn't match the file on disk. It would also have caught 110-4's own pin going stale once 110-4 edited the file.

No web search was needed: the question is entirely about this project's own records, and it raises no claim about an external tool or API.

- `git log --format=%H %ci -- tools/recipes/stage_d1_l2b1.py` — expect a single cycle-110 commit, `2473868`.
- `git diff 2473868 --stat -- tools/stagekit.py tools/stagexec.py` — covers the shared-code alternative.
