## Answer

**Verdict: the G2 explanation is correct but not proven for this run. The G6 explanation is wrong where it matters: no string constant sits upstream of #20436, so "trace the name value upstream, offline" cannot give a value.**

## 1. The strongest reason the claim is wrong (G6)

The claim treats #20436's Image Name as a string that reaches the node through tunnels. The graph of the byte copy of the original says otherwise. Following wire 32944 upstream in `docs/wiki/subvi/D1_s1_copy.json`:

| step | object | where |
|---|---|---|
| w32944 → #20436 'Image Name' | from FSIT #32955 'Image Out' | :54215-54222, :88451-88455 |
| #32955 ← w20108 | from FSIT #19598 | :53695-53701, :53905-53911 |
| #19598 ← w19813 | from FSIT #14946 | :53035-53051 |
| #14946 ← w19567 | from LoopTunnel #15188 | :44675-44682, :52385-52391 |
| #15188 ← w19462 | from SubVI #15403 'Image Out' | :49195-49201, :52145-52151 |

- **SubVI #15403 is `IMAQdx Grab.vi`** (`tools/bench/main_vi_subvis.json:453-455`).
- **The same wire 19462 also feeds `IMAQ ImageToArray` #15442 'Image'** (:50815-50819 there, and `main_vi_subvis.json:463-465`).
- **So the wire into #20436 is an IMAQ Image, coerced to a string.** It is not a StringConstant behind a tunnel.

**Why the name 'Image Out' matters.** In this dump, tunnel terminal names follow the name of their source: #13167 'New Image' (`diag_c118_q.log:39`), #10673 'error out' (:22), and the StringConstant's own terminal 'Image Name' (:33). So 'Image Out' on the FSIT face points to an image-typed wire. It is not consistent with a string-typed name wire.

**What this means for the program.** An IMAQ Image wire's value is the image-name string given to IMAQ Create, and it coerces to or from that name ([NI forum](https://forums.ni.com/t5/LabVIEW/How-to-communicate-an-IMAQ-Image-Reference-between-applications/td-p/1649708)). Calling IMAQ Create with a name that already exists returns the existing image instead of making a new buffer ([NI forum](https://forums.ni.com/t5/LabVIEW/If-I-use-IMAQ-Create-twice-with-the-same-image-name-string-what/td-p/637872), [NI IMAQ Create doc](https://www.ni.com/docs/en-US/bundle/ni-imaq-vi-ref/page/niimaqvireference/imaq_create-vision.html)).

So #20436 most likely returns the grab buffer (probably "Cam", #13938's image) rather than a new one. This is not a harmless "wrong prediction about the graph":
- It is an aliasing fact covered by rule 1a.
- It is a run-time dataflow dependency on the grab output.

A loop split that moves #20436 or the grab can change behaviour.

**Alternative explanation for G6:** a build stage mis-wired an image into Image Name. This is ruled out: the same rows are already in S1 (`D1_s1_copy.json`) and in `graph_k_s4_20260925.json`, which is the earliest dump found. The wire is original.

The test `endswith("imaq create.vi")` at `diag_c118_p0.py:100` can never match.

- **Errors are thrown away.** `g.subvis(..., strict=False)[0]` (`diag_c118_p0.py:98`) drops the returned `err` (`gscript.py:683-684`). An error on the SubVIs[] node therefore prints no "subvis … raised" fact. Your reason for ruling that alternative out is invalid.
