## Answer

**The claim is wrong in its premise.** An empty While loop's body does have terminal rows in this project's own reader, and the real fault is in the simulator's model of a created loop, not in the binding rule.

**1. The strongest reason the claim is wrong**
- The binding check never reads `objs`. `real` is `dedupe(lv["terminals"])` (`tools/stagexec.py:1331-1335`). `bind_new` builds its new-object set only from terminal rows whose `term_uid` is new, grouped by owner (`tools/stagexec.py:451-455`).
- So `{'Diagram': 1} (real owners [23073])` means LabVIEW returned at least one new terminal row owned by Diagram #23073. The new body has terminals.
- The base read shows what they are. Every While loop body carries two Diagram-owned rows with `term_class "Terminal"`: one source and one sink, both with an empty name.
  - Body #639 has #644 (source) and #648 (sink).
  - Body #25392 has #25406 (source) and #25410 (sink).
  - For Loop body #27537 has only #27543 (source).
- These are the iteration terminal `i` and the conditional terminal. NI's own forum describes finding them by walking the objects inside the loop, not as terminals of the loop itself ([NI forum: locate loop iteration and conditional terminals](https://forums.ni.com/t5/LabVIEW/VI-Scripting-locate-loop-iteration-and-conditional-terminals/td-p/4344904)).
- The log's "0 terminal(s)" (`stage_d1_disp_r2.log:53`) is the loop's own terminal list, which is a different thing.

**2. Where the fault actually is**
- Card 100-3's simulator evidence counted rows owned by the WhileLoop/ForLoop object, found 0, and concluded that a loop "owns NO row" (`tools/stagesim.py:102-107`).
- It then carried that into "the conditional terminal owns no row in the terminal read" (`tools/stagesim.py:761-762`). That was measured against the wrong owner: the rows belong to the body Diagram, not to the loop.
- So the simulated `create` step leaves out 2 rows. `op_wire` to `new:DL1.cond` (`plan_disp.json:727`) is also mis-modelled: it assumes the sink is missing "in the real read alike" (`tools/stagesim.py:781-782`), but the real read will show it.
- There is also a smaller defect in the executor. `_bind_create` stores the body in `bind["diag"]` (`tools/stagexec.py:1237`). `bind_new` only excludes `bind["obj"].values()` (`tools/stagexec.py:454`).
- **Warning:** fixing only that exclusion, which is the natural "binding-rule gap" patch, would get past BINDING. But STEPX 02 would then fail on the 2 rows the simulator never created, and the `.cond` wire step would fail later. Treating it as a binding gap would buy another failed run.

**3. Your alternative: #23073 is not the new body**
- This is weak. `LVBackend.create` already refuses unless exactly one new Diagram appears (`tools/stagexec.py:1497-1500`), and it passed.
- #23073 is not in the base read. Its neighbours #23071, #23074 and #23077 are IndexArray terminals, so LabVIEW reused a free uid inside an old range. Uid reuse is only flagged for uids present both before and after, so this is harmless.
- It is not strictly proven, because `res['body']` was never logged (`stage_d1_disp.json` has no 2307x entries).

**4. What would falsify my reading**
- If Diagram #23073's new rows are not exactly 1 source and 1 sink.
- Or if `res['body']` ≠ 23073.
- Either would put the cause elsewhere, for example a stale read or a different structure producing the row.

**5. Cheapest test that separates the two explanations**
- **Offline, no LabVIEW:** in `tools/bench/sim/disp/step_00_base.json`, list the Diagram-owned `Terminal` rows of all three While bodies (#639, #25392, #15266). Expect exactly one unnamed source and one unnamed sink each.
- **On the next real run:** add `res['body']` and the new rows (`term_uid`, `is_source`, `term_class`) to the BINDING message. Expect body = 23073 with 1 source + 1 sink.
- If both hold, fix the simulator's create model and the `.cond` sink model, plus the `bind["diag"]` exclusion, before any rerun.
