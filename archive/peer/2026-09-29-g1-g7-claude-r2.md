## Question

In Windows PowerShell 5.1, if a string variable that contains embedded double-quote characters and spaces is passed as a single argument to a native executable (for example & prog.exe $s), does the program receive it as one intact argument?

Search the web and cite the URL of every source you used.

## Answer

**No, not reliably.** In Windows PowerShell 5.1, `& prog.exe $s` does not escape the double quotes inside `$s`. So the program either gets the argument with its quotes removed, or gets it broken into several arguments. Which one happens depends on where the quotes and spaces fall in the string.

**How it happens:**
- PowerShell does wrap an argument that contains spaces in quotes so it stays together. But "if the argument itself contains quotes, these are not escaped. Therefore, the corresponding element in `argv[]` has no quotes and depending on the actual string, the argument might be split into multiple `argv[]` elements." ([PowerShell RFC draft, "Improve generation of argument string for executables"](https://github.com/TSlivede/PowerShell-RFC/blob/a1f07b6648f9ab90d03dc5ba0d5a745a8af497f8/1-Draft/RFC%23%23%23%23-Improve-generation-of-argument-string-for-executables.md))
- Microsoft's docs issue on this says values with embedded `"` are passed incorrectly. PowerShell doesn't escape them, and it doesn't reliably add the surrounding quotes that would keep the value together. Its example is a value like `3" of snow`. ([MicrosoftDocs/PowerShell-Docs #2361](https://github.com/MicrosoftDocs/PowerShell-Docs/issues/2361))
- In the original bug report, the program expected `argv[1]` to be `"a"` but actually received `a`, with the quotes stripped. ([PowerShell/PowerShell #1995](https://github.com/PowerShell/PowerShell/issues/1995))
- In the Azure CLI example, passing `'{"key": "value"}'` to `python.exe` arrives as `{key: value}`. It stays one argument here, but only by accident, and the quotes are gone. ([Azure CLI: quoting issues with PowerShell](https://github.com/Azure/azure-cli/blob/dev/doc/quoting-issues-with-powershell.md))
- The fix came in PowerShell 7.3 with `$PSNativeCommandArgumentPassing` (`Standard`/`Windows` modes). `Legacy` is the old behavior, and it's the only behavior 5.1 has. ([about_Preference_Variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_preference_variables))

**What the sources don't settle:** none of them gives a complete rule for predicting the result for every string. The final result also depends on how the receiving program parses its command line. Most use the standard Microsoft C runtime rules, but some programs parse the raw command line themselves. So the reliable answer is "not guaranteed intact": with embedded quotes, you should expect quote loss or splitting.

**Workaround the sources mention:** in 5.1, escape each embedded `"` as `\"` yourself before the call ([#2361](https://github.com/MicrosoftDocs/PowerShell-Docs/issues/2361)). Or use the `ie` function from the `Native` module on the PowerShell Gallery, which corrects for this behavior ([sqlpey summary](https://sqlpey.com/powershell/powershell-argument-handling-fixes/), [#2361](https://github.com/MicrosoftDocs/PowerShell-Docs/issues/2361)).
