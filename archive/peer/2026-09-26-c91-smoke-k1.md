## 1. Strongest reason the claim is wrong

**The "known flake" precedent doesn't exist in the recorded runs, and the stamps sit inside the pick loop.**

- **No precedent.** I checked every v5-driver record in `tools/bench` (17 click files, plus the m8 logs). Every run where the picks registered short of the target was a leg whose target was itself short (1 of 1, 6 of 6, 8 of 8, 15 of 15). Two examples:
  - `m8_s1s3_77.log:98` is 1 marker from 1 pick, a 1-pick leg checked against a fixed contract of 3.
  - `drive_m8_replay_s1_78b.log:179` is 3 of 3.

  The smoke run is the only run that lost a delivered click (`diag_c91_t0_smoke.log:180`), and it is the only run on the stamped VI. The record is 1 lost click in 1 stamped run, against 0 in about 16 runs without stamps. If a 2-of-3 run exists elsewhere, it needs a file:line citation; otherwise that sentence has to go.
- **The "display loop" is the bead-pick loop.** `Done Picking \nBeads?` is wired to wire 19456 (`docs/main-vi-panel-map.md:359`). That wire is the stop-condition wire of While loop #15173 (`docs/main-vi-stop-and-save.md:65`). So #15173 is the loop that takes the clicks, and it carries 5 of the 12 stamps:
  - sites 10, 11, 12, 13 and 16 (`tools/bench/t0_sites_s1_step3c_r2.json:2546-2678`);
  - site 16 is the circle/text case tunnel, which is the branch that draws the markers.
- **Answer to your question (a): yes, this is a real mechanism.** LabVIEW's default setting for a Call Library Function Node (CLFN) is "Run in UI thread". A UI-thread CLFN in a loop forces a thread switch on every call and queues behind front-panel work.
  - Sources: [NI forum, slow front panel with a UI-thread CLFN](https://forums.ni.com/t5/LabVIEW/Slow-Front-Panel-update-with-Call-Library-Function-Node-Pico-USB/td-p/3756574), [NI forum, DLL slows a parallel while loop](https://forums.ni.com/t5/LabVIEW/dll-slows-down-parrellel-while-loop/td-p/3312649), and your own `docs/t0-instrumentation-plan.md:71`.
  - `build_clfn` passes `reentrant=True` (`tools/gscript.py:2968,2996`), which should mean "any thread". I found no readback of that setting on any of the 12 nodes, so the thread setting is unmeasured.
  - IMAQ's `Get Last Event` returns only the latest event on the display ([NI example](https://forums.ni.com/t5/Example-Programs/How-to-use-the-IMAQ-quot-Get-Last-Event-quot-property/ta-p/3503816)). A pick loop that stalls can therefore lose a click to a later event.

## 2. Alternative explanation, backed by a recorded fact nobody cited

**Another window held the mouse capture during click 1.** `m8_v5_replay_s1_r30_clicks.json:42,82` shows `hwndCapture = 109053432` on LabVIEW's GUI thread (tid 16608), both before focus and just before the button went down. The panel's own handle is 3082674, so this was a different window.

- This happened on click 1 and on no other pick click in any of the 17 click files. In every other file, the capture handle is non-zero only on the Done-button entry (line 525 and its equivalents).
- It had cleared by `gti_after_click` (line 99).
- In Windows, the window holding the capture receives the mouse input ([SetCapture](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setcapture)). The button-down most likely went to window 109053432. `WindowFromPoint`, which drove all four "delivered=True" checks, ignores capture, so those checks could not see this.

This is harness-side evidence, but it is a specific mechanism, not the claim's "clicked before the display redrew". It also leaves one question open: which LabVIEW window held the capture, and why only in this run? The measurement does not tell whether the stamped VI caused that window to exist.

**L3 and L8 are one event, not two flakes.** The VI really ran with 2 beads. The `.cal` size follows 96 + 57152·n bytes exactly for n = 1, 3, 6, 8 and 15 (57248, 171552, 343008, 457312, 857376 B). The smoke's `cal001` is 114400 B, which is n = 2. Two bandpass panels is simply what the VI does when 2 beads are registered.

## 3. What would falsify "harness only"

- **A stall in the pick loop.** `t0_site10_pid18276.bin` records one timestamp per pick-loop iteration: an int64 frequency first, then int64 counts (`tools/t0stamp/t0stamp.c:6-8`). An iteration gap longer than about 350 ms (a press takes 346 ms, `click_ms` at line 92) at click 1's time would point to the VI. It would count even more if the gap follows the loop's first stamp, which is when the stamp DLL starts being called.
- **A repeat without the capture anomaly.** A lost click in a later stamped leg with `hwndCapture == 0` would point to the VI.
- **An exonerating result.** A lost click on the unstamped S1 copy while a foreign capture is held would clear the stamps.

To count registered picks without relying on markers, use either of these:
- `.cal` size: n = (size − 96) / 57152.
- The `Bead Pos` indicator (#80, uid 11831, `docs/main-vi-panel-map.md:360`), read over VI Server after Done. Its array shows which click is missing.

Then change the step-4 card before running the four 120 s legs:
