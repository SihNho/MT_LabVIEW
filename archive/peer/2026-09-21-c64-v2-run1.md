## 1. The single strongest reason it is wrong

**`git show` did not return empty output. Fix (b) is a no-op, and run 2 will fail `C_1b` identically.**

The refutation sits four lines above the gate it explains, in the same log:

```
tools/bench/diag_c64_connect_v2.log:25-33
Exception in thread Thread-3 (_readerthread):
  File "...\subprocess.py", line 1499, in _readerthread
    buffer.append(fh.read())
UnicodeDecodeError: 'cp949' codec can't decode byte 0xe2 in position 12250
```

- A pathspec that does not resolve emits **zero** stdout bytes. A decoder cannot fail at **position 12,250** of a zero-byte stream. The decoder had already consumed ≥12,250 characters, so `git show HEAD:tools/gscript.py` **resolved and emitted the file**. Independently: `git diff --numstat -- tools/gscript.py` ran from the same `cwd=ROOT` and returned `56\t0` (`log:23`), so git resolves that path from that directory.
- The empty result is a CPython-on-Windows behaviour, not a git one. `subprocess.py:1506-1548`: the stdout reader thread appends to `_stdout_buff`; when `fh.read()` raises, nothing is appended, and line 1548 `stdout = stdout[0] if stdout else None` yields **`None`**. So `head.stdout is None`, `re.findall(..., head.stdout or "")` returns an empty set, every def looks "added", and **no exception reaches the `except` block** — precisely `defs lost []` at `log:34`. `text=True` with no `encoding=` decodes with `locale.getpreferredencoding(False)` = cp949 here; `tools/gscript.py` is UTF-8 (first non-ASCII at line 218, first unmappable around 236).
- **The current file still carries the defect.** `diag_c64_connect_v2.py:417-418` is `subprocess.run([...], cwd=ROOT, capture_output=True, text=True, timeout=120)` — pathspec changed, `encoding=` still absent.
- The new instrumentation makes it **worse**: `git_show_rc` will read `0`, `git_show_stderr` `''`, `git_show_bytes` `0`. A clean git call that returned nothing is a far more convincing false fact than run 1's visible traceback. The comment at `:412-416` — "an empty read can never again be mistaken for 'HEAD has no defs'" — becomes false the moment it runs.

**So yes, something REAL was caught, and widening/re-pathspecking papers over it**: every `text=True` subprocess call in this fleet silently returns `None` at the first non-cp949 byte, and that defect already manufactured one false fact inside this log.
