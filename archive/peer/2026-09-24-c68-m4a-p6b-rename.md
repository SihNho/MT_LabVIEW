## Answer

**Verdict: not established.** The rename half is plausible but rests on inference. The "reader artefact" half is probably right, but `q_m4a_diffuid.py` as written cannot confirm it, because it runs the same pairing code that produced the artefact.

## 1. Strongest reason the claim is wrong, or at least unproven: the uid re-diff cannot test the `sr` half

- **How pairing works.** The reader pairs shift registers by position only: same loop body diagram, then the same top y (`tools/vigraph.py:334-342`). The `loops` / `Shift Registers[]` argument is used only as a set check (`vigraph.py:351-361`). It never decides which right register pairs with which left one.
- **What that predicts.** Suppose the new left register #23796 landed at the same top y as #23880. Then #23868 finds 2 candidates and is dropped as unpaired, and #23469 finds 0. That is exactly the observation: both the old pair #23868→#23880 and the new pair #23469→#23796 lose their `sr` edge, while #23895→#23909 survives.
- **Why the discriminating read doesn't discriminate.** `q_m4a_diffuid.py:40-41` builds both graphs through `stagekit.live_graph` (`tools/stagekit.py:802-816`), which ends in the same pairing code. Keying edges by terminal uid fixes names, not pairing.
  - U3's expectation ("new 3") will come out lower for geometric reasons, whatever the VI actually contains.
  - U1 will fail on the missing #23868→#23880 `sr` edge. That failure will also be meaningless.
- **Consequence.** Calling it "a graph artefact" is itself a finding against the gate: for this loop, P6 cannot see shift-register membership.

## 2. Alternative explanations of the same evidence

- **(a) Unknown rename trigger.** The rename may not have been caused by adding the shift register. It could come from any recompile: the w23847 delete, the P4 second pass, or the save. Or the name-read order could be unstable. Here is what the log does show:
  - Both names belong to real, different sources in the same net: bed `#4194 'Outgoing Handle'` and new `#11263 'VISA out'` (`stage_d1_m4a.log:293-294`).
  - The rename also spread downstream to flat-sequence tunnel #7468, which is not part of loop #23032.
  - So the name follows *whichever* source LabVIEW picks. What changed that pick is unmeasured.
  - I found no NI or LabVIEW-wiki documentation of how a tunnel or shift-register terminal's `Name` is derived (searches below). "Name follows what is wired to it" is inference.
- **(b) A real change hiding inside the name churn.** The only computation-diff row sits on exactly this net: sink `#48 'VISA resource name'`, sources `['19093…VISA out','48…Outgoing Handle','5987…']` → `['5987…']` (`stage_d1_m4a.log:296`). #48 is fed by the renamed register #23880.
  - Either this row is a key-mismatch artefact of the rename, because the relay walk joins by name keys, or a source really left that sink.
  - The explanation does not address it.
  - `stage_d1_m3a4.log` contains no `VISA resource name` row. That run printed only diff counts (`:110`), so whether this row existed before M4a is unknown.

## 3. What would falsify the claim

- **The rename claim is falsified if:** under uid keying, any `wire` or `fs` edge (as terminal uid pairs) on #23868/#23880/#23895/#23909/#7468/#48 differs between bed and new, or #48's `VISA resource name` has a different set of incoming source terminal uids.
- **The artefact claim is falsified if:** the new file's #23796 sits at a top y different from #23880's, and #23868 still comes out unpaired. That would mean the pairing failed for some reason other than a y collision.

Even then, "adding a shift register caused the rename" stays unproven.
