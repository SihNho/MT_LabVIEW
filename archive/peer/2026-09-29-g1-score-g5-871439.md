QUESTION:
In Windows PowerShell 5.1, which character encoding does Get-Content use by default when it reads a text file that has no byte-order mark?

KNOWN ANSWER (verified on the machine / vendor files):
The system's legacy ANSI code page ('Default', e.g. Windows-1252 or cp949 on a Korean system), not UTF-8; UTF-8 without BOM must be read with -Encoding UTF8.
KEY POINTS: ANSI / system default code page; not UTF-8; -Encoding UTF8 needed

ANSWER 871439 TO GRADE:
<<<
In Windows PowerShell 5.1, `Get-Content` reads a file with no byte-order mark (BOM) using **`Default` encoding. That is the system's active ANSI code page**, which is set by the system locale. It does not default to UTF-8 or UTF-16. Microsoft's documentation states this directly, so the evidence is clear.

- **about_Character_Encoding (5.1):** "For cmdlets that read string data in the absence of a BOM: `Get-Content` and `Import-PowerShellDataFile` uses the `Default` ANSI encoding. ANSI is also what the PowerShell engine uses when it reads source code from files." `Default` is defined there as "the encoding that corresponds to the system's active code page (usually ANSI)."
  https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1

- **Get-Content reference (5.1):** for the `-Encoding` parameter it says "The default value is `Default`," and describes that value as "the encoding that corresponds to the system's active code page (usually ANSI)."
  https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-content?view=powershell-5.1

**What this means in practice:** the same page also warns that a UTF-8 file without a BOM that contains non-ASCII characters gets misread as the legacy ANSI code page. To read such a file correctly, pass `-Encoding UTF8`. In PowerShell 7 and later the default is different (`utf8NoBOM`).
