QUESTION:
In the LabVIEW NI-IMAQdx palette, what are the DEFAULT values of the 'Buffer Number Mode' input of IMAQdx Get Image2.vi and of the 'Wait for Next Buffer?' input of IMAQdx Grab2.vi when those inputs are left unwired, and what does that default mean for a display loop that runs slower than the camera?

KNOWN ANSWER (verified on the machine / vendor files):
Get Image2 defaults to Buffer Number Mode = Next and Grab2 defaults to Wait for Next Buffer? = Yes (TRUE); both wait for the next buffer in sequence. A loop slower than the camera therefore falls behind, the driver ring overwrites unread buffers and frames are missed; wiring Last (or No) returns the newest buffer without waiting and decouples the display rate.
KEY POINTS: Get Image2 default Next; Grab2 default Wait for Next Buffer = Yes; slow loop falls behind / buffers overwritten; Last decouples

The default for 'Buffer Number Mode' is **Next**. The default for 'Wait for Next Buffer?' is **TRUE**. Both came from NI forum posts and search-result summaries. I couldn't read NI's own reference pages to confirm them.

**IMAQdx Get Image2.vi, 'Buffer Number Mode': Next.** "Next" means the VI waits for the next acquired buffer. An NI forum answer says to use this default, leave 'Buffer Number In' unwired, and that 'Buffer Number Out' then counts up in order: 1, 2, 3, 4, … ([NI forum: Buffers output in IMAQdx](https://forums.ni.com/t5/LabVIEW/Buffers-output-in-IMAQdx/td-p/3644259)). 'Buffer Number In' is ignored in Next and Last modes ([narkive mirror of an NI forum thread](https://natinst.public.imaq.general.narkive.com/OyB8ZFv2/quot-buffer-number-in-quot-confusion-with-imaqdx-get-image)).

**IMAQdx Grab2.vi, 'Wait for Next Buffer?': TRUE.** When TRUE, it waits for the next buffer to be ready. When FALSE, it returns the last acquired buffer ([NI forum: Quick question about grab function in IMAQdx](https://forums.ni.com/t5/LabVIEW/Quick-question-about-grab-function-in-IMAQdx/td-p/3607125)).

**What this means for a display loop slower than the camera:**
- **Frames are dropped.** The camera fills a ring of buffers. If the loop is slower, buffers get overwritten before the loop reads them. An NI forum thread says the default Configure Grab uses 5 buffers, and only about 3 of them can actually be read, because the driver reserves the rest for incoming frames ([NI forum: Get Image Data not returning the correct buffer number](https://forums.ni.com/t5/Machine-Vision/IMAQdx-Get-Image-Data-VI-not-returning-the-correct-buffer-number/td-p/3764387)).
- **It doesn't wait on the slow loop.** Because Next goes through buffers in order, a slow loop asks for buffers that are already gone. The driver then gives back a different buffer instead of an error. The returned buffer number jumps, and comparing it with the last one shows how many frames were lost ([same Grab thread](https://forums.ni.com/t5/LabVIEW/Quick-question-about-grab-function-in-IMAQdx/td-p/3607125)).
- **Each call can also wait for a new frame.** With these defaults, a call waits until a frame it hasn't returned yet exists.
- **The sources disagree on which buffer comes back.** The later thread (3764387) says the default returns the **newest** buffer. An older post says the default returns the **oldest** buffer still available ([narkive mirror](https://natinst.public.imaq.general.narkive.com/OyB8ZFv2/quot-buffer-number-in-quot-confusion-with-imaqdx-get-image)). This setting decides how far the displayed image lags behind the camera, so I can't say which is right for your driver version.
- **You can make the loss visible.** Setting the overwrite mode to "Fail" makes the VI return an error instead of silently swapping in another frame ([NI forum: how IMAQdx buffers work](https://forums.ni.com/t5/Machine-Vision/Trying-to-understand-how-the-buffers-work-in-Imaqdx-aquisition/td-p/3986038)).
