The `from` fields in the usage list are null for the same reason (`:433`, `json:5444-5490`).

The usage list shows what was actually missing. Entry 10, "Wire has loose ends", was pinned at 22 in the file the recipe wrote (`..._recipe_stale.json:86-92`) and only 20 of those were used (`json:5487-5490`). So "missing 2" means **the VI has two fewer "Wire has loose ends" items than P3b-1 had**. That is a real change in the VI, measured, not a by-product of how the file was built.

The claim's description ("two NULL entries") also hides a reporting fault: every MISMATCH on a `norm_all` expected file gives a list of nulls that cannot be read. Cards 134-5 and 135-4 both repeated `[null, null]` without anyone resolving it (`result_134-5.json:26`, `result_135-4.json:18,22`).

## 2. Alternative explanation of the same evidence

The class counts cannot tell these two cases apart:

- **(b) Not by design.** A different combination gives the same net −2 per class: for example, three loose ends retired and one new loose end appears, or the planned losses retire none of them and something else does.

The range model allows anything from 18 to 21 loose ends (`errorlist_expect_p3b2ab.json:8,19`): one certain debit, three uncertain ones from 0 to 1, across four lost wires. An observed 20 is inside that range but does not identify which wires produced it.

The plan's own prediction was also not met. The recipe's file says "P3b-1's 53 + 0 new" (`_recipe_stale.json:5`). The class *range* passed, but the point prediction failed. Card 134-5 raised exactly this limit and recommended an item-level test before the launch (`result_134-5.json:26`). There is no sign that test was run.

Since then the expected file has been rewritten with loose ends at 20, measured from this same read (`errorlist_expected_D1_ring_p3b2b_20261002_130007.json:5,86-92`). The comparison file was fitted to the result it is supposed to judge, so a re-check against it is circular.
