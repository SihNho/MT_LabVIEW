## Question

In LabVIEW VI Scripting (VI Server), which property of a Wire object reports whether that wire is broken, and what is that property's unique ID string (the hex ID used when the property is set with Allow Alternate Names = FALSE)? Also say what kinds of wire problems that property does and does not flag.

Search the web and cite the URL of every source you used.

## Answer

I can answer the first part, but not the other two with sources. The property is **Is Broken?** (short name **Broken?**) on the Wire class. No source I found gives its hex ID or says exactly which wire problems it catches.

**1. The property.** The LabVIEW Wiki page for "Wire class/Is Broken? property" lists:
- **Name:** long name "Is Broken?", short name and data name "Broken?".
- **Type:** Boolean, read-only, VI Scripting only.
- **Owning class:** Wire, class ID 16439.
- **Description:** "Returns TRUE if the wire is broken or in a bad state."
- **Other listed facts:** not available in Real-Time or the Run-Time Engine, can't be set while the VI runs, and remote access is allowed.

Source: https://labviewwiki.org/wiki/Wire_class/Is_Broken%3F_property (the page and its edit-view template parameters)

**2. The unique ID.** The only ID I found is the wiki's **propertyid = 6371004**, written in decimal. Converted to hex, that is **0x6136BC**. The conversion is my own arithmetic. No source I found says that 0x6136BC is the string the Property Node shows or accepts when Allow Alternate Names = FALSE, and I couldn't find NI documentation that states the ID. So treat 0x6136BC as unconfirmed. You could check it by looking at the property in a Property Node on your own LabVIEW install.

**3. What it flags and doesn't.** No documentation spells this out. The wiki says only "broken or in a bad state," and its template gives no list of cases. Related facts from other sources:
- NI's NXG troubleshooting page says a broken wire means dataflow can't run across the wire, and code with broken wires can't run. That page covers LabVIEW NXG, not LabVIEW itself. https://www.ni.com/docs/en-US/bundle/labview-nxg-g-programming-api-overview/page/troubleshooting-broken-wires.html
- In older LabVIEW, one miswired branch broke the whole wire tree. Since LabVIEW 2020, only the bad branch is shown as broken. https://forums.ni.com/t5/LabVIEW-Idea-Exchange/Break-bad-wire-branches-not-the-entire-wire/idi-p/3190706
- Search result snippets describe "unwired or bad terminal" and "unwired front panel terminal" as errors or warnings on nodes and terminals, not on wire objects. That hints that problems with no wire at all wouldn't show up on a Wire's Is Broken? property. I haven't confirmed this, and I didn't open those pages to read them: https://forums.ni.com/t5/LabVIEW/Unwired-or-bad-terminal/td-p/2772804 and https://forums.ni.com/t5/LabVIEW/Unwired-Front-Panel-Terminal-Warnings/td-p/334343
- A search snippet about a scripting thread says wires can be left broken after nodes are deleted, with no error reported. I didn't open the page: https://forums.ni.com/t5/LabVIEW/Scripting-Wire-object-into-existing-wire/td-p/4014923

Three things remain unconfirmed: whether Is Broken? covers type mismatches, loose ends, cycles and several sources on one wire; whether it reports on a single branch or on the whole wire; and whether it flags unwired required inputs. Testing each case in LabVIEW would settle them.

I couldn't open NI's knowledge-base article "Wire Class Conflict and Broken Wires in LabVIEW" because of a certificate error, so I don't know if it helps: https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z0000019XS0SAM
