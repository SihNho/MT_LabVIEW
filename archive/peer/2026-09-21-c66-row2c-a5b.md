And this project has **already recorded a real wire whose SINK is a `SelectorTunnel`** (`docs/NAMES.md:1049`) — so it is not hypothetical here.

Concrete failure mode, object and property named: wire **#23556** is minted from `#10757:element` to the indicator's terminal **and also branches onto the existing outside terminal (`Tunnel.Outside Terminal`, property 6356001, `docs/NAMES.md:964`) of a structure already sitting on #639.** Why each listed gate is blind:

## 2. An alternative explanation consistent with a BAD artefact

`docs/NAMES.md:899-901` records, measured 2026-09-15 and cross-checked against `panel_wiring`: *"a control terminal's `Owner` is the diagram, not the control."* So A5's uid 34982 with `owner_of` = `('Diagram', 26117)` is **precisely what a genuine front-panel control terminal looks like.** The only thing separating it from "a real terminal of this VI" is the 23xxx band heuristic — which the claim's own uids refute (#639, #637, #10757 all sit outside it).

Alternative: **26117 is this VI's root block diagram and #639 is a sub-diagram.** Control terminals live on the top-level diagram ([NI: dynamic FP terminals cannot be inside structures](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/errors/dynamic-terminal-not-at-top-level.html); [a connector-pane terminal not on the top-level BD is inside a Case Structure](https://forums.ni.com/t5/LabVIEW/Control-terminals-on-connector-pane-not-on-top-level-block/td-p/3050747)). The claim's own arithmetic fits: **75 of 632 nodes = 12 %** — the size of one sub-diagram, not of a 632-node VI's root. On this reading "one sink = panel control 23525" is a cross-diagram assertion no single wire can satisfy, and the census covered 12 % of the VI.

Second branch, equally bad: 34982 belongs to **another VI in memory**, i.e. `report_all` is not VI-scoped — then 1907 / 632 / 116 / 10 / 135 are counts over an unknown population and none of them are evidence of anything.
