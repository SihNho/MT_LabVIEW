## Question

In Windows PowerShell 5.1, if a string variable that contains embedded double-quote characters and spaces is passed as a single argument to a native executable (for example & prog.exe $s), does the program receive it as one intact argument?

Search the web and cite the URL of every source you used.

## Answer

**No.** In Windows PowerShell 5.1, the native program does **not** receive it as one intact argument. Instead, the argument is split into multiple arguments, and the embedded double-quote characters are consumed and stripped.

---

### Reasoning & Mechanism

1. **PowerShell 5.1 command-line reconstruction:**
   On Windows, the underlying `CreateProcessW` API accepts a single command-line string (`lpCommandLine`), not an array of discrete arguments. When PowerShell calls an external binary (`& prog.exe $s`), it serializes the arguments into one string.
   - Because `$s` contains whitespace, PowerShell wraps the whole argument in outer double quotes: `"$s"`.
   - However, PowerShell 5.1 does **not** escape internal double-quote characters with backslashes (`\"`). It inserts them verbatim.
   - For example, if `$s = 'foo "bar baz" qux'`, PowerShell emits the raw command line:
     ```text
     prog.exe "foo "bar baz" qux"
     ```

2. **Target executable parsing (`CommandLineToArgvW` / MSVC CRT):**
   Standard Windows native executables parse the command line using the MSVC C/C++ runtime startup rules or [`CommandLineToArgvW`](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw). Under these rules:
   - Double quotes toggle whether spaces are treated as literal characters or argument delimiters.
   - The opening double quote added by PowerShell turns "in-quotes" mode ON.
   - The first unescaped embedded quote is interpreted as closing the quoted section, turning "in-quotes" mode **OFF**.
   - The space that follows is now unquoted, so the parser treats it as an **argument delimiter**, splitting the string into separate `argv` elements while stripping the quotes.

3. **Known defect & modern resolution:**
   This behavior is the long-standing defect tracked in [PowerShell Issue #1995](https://github.com/PowerShell/PowerShell/issues/1995). It was fixed in PowerShell 7.3 by introducing the `$PSNativeCommandArgumentPassing` preference variable (`Standard` / `Windows` mode), which properly escapes embedded quotes with backslashes (`\"`). The historical Windows PowerShell 5.1 behavior is designated as `Legacy` mode in Microsoft's documentation on [about_Parsing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing#passing-arguments-that-contain-quote-characters).

---

### Cheap Way to Check

Run this one-liner in Windows PowerShell 5.1:

```powershell
$s = 'foo "bar baz" qux'
& python -c "import sys; print(sys.argv[1:])" $s
```

**Result:**
```text
['foo bar', 'baz qux']
```
The receiving executable sees two separate arguments with the quotes stripped rather than one intact argument `<foo "bar baz" qux>`.
