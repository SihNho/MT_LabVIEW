**On your specific question — is there a read that proves a block diagram executed?** Over the ActiveX `VirtualInstrument` surface, no. There is no run counter, no last-run timestamp, no post-hoc "has executed" property. `Call Chain` is the *currently executing* VI's context and is read from inside a running VI; by the time you can call `GetControlValue` the op has finished and there is no chain to read. **The only proof is a front-panel value that differs from the value the same loaded instance held before the Run** — R5 — and the baseline must be the *loaded* value, not the saved default and not a value left by a previous call in the same process. R6 is the one exception, and it is a timing race rather than a fact.

Two things that look like proofs and are not: `_run` returning without raising (it proves `Run` did not error, not that dataflow reached the Invoke), and `_err` returning `''` (it conflates three states). And **do not** use `Make Current Values Default` as a comparison — it is a write, it dirties the op VI, and it destroys the baseline you are trying to measure. If R1's baseline has already been contaminated by a run in the same process, `g.revert(op VI)` reads the on-disk default without saving.

## 4. What makes `Run` return silently on a VI that did nothing

Not the VI's run-state — that is always loud. What *is* silent is the **diagram short-circuiting**, and all four mechanisms you asked about are real:

- **Error-in already set at a Property or Invoke node**: the node "does not perform anything inside", passes the error through, and outputs **default data** ([NI forum: Property Node error clusters](https://forums.ni.com/t5/LabVIEW/Property-Node-error-clusters-to-wire-or-not-to-wire/td-p/3331954)). This is the single most likely mechanism here.
- **`Index Array` out of range returns the default element with no error at all** — it has no error terminal ([LabVIEW Wiki, Index Array](https://labviewwiki.org/wiki/Index_Array_function)). For a refnum array that default is `0`, and the downstream Invoke then errors 1055. A traverse whose ordering differs from `report_all`'s makes `index=2` address nothing, silently.
- **Case structure on an error cluster, or a Diagram Disable structure** — the frame simply never runs.
- **`SetControlValue` on a name that does not exist**: *not settled*. NI documents it as returning an error, which over ActiveX surfaces as a COM exception pywin32 raises; I found no source saying it fails silently. But this project has never measured it, and the whole fleet depends on it raising. It is one line in a scratch process: `vi.SetControlValue("no such control", 0)`.

Also worth recording, since it is a live trap in this code: `gscript.py:403` invokes `Run` with **no arguments** — the `1` is pythoncom's `bResultWanted`, not a parameter. `Wait Until Done` defaults to **TRUE** ([LabVIEW Wiki](https://labviewwiki.org/wiki/VI_class/Run_VI_method)), so the call is synchronous and a read-before-finish race is **ruled out**. Explicit `DISPATCH_METHOD` also avoids the pywin32 trap where `vi.Run(1)` needs `_FlagAsMethod` ([NI forum](https://forums.ni.com/t5/LabVIEW/Trouble-running-a-VI-asynchronously-when-called-from-Python-via/td-p/4103346)).
