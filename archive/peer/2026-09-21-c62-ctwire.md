# Failed-prediction review — A_4, "a ControlTerminal's connected wire could not be read by uid"

**The premise is right and the conclusion does not follow — and the conclusion is the half that will drive the next cycle.** A `ControlTerminal` really is `Generic → GObject → Terminal → ControlTerminal` and really is not in a `Nodes[]` walk. But *"therefore the wire on #23541 is not readable by that uid with the verbs that exist here"* is refuted by this same run's own output, and one of the two "routes" it reports trying never executed.

## 1. The single strongest reason the claim is WRONG

**It conflates "no address" with "no reader". The run produced the address itself.**

- `report_all(target,'ControlTerminal')` returned `{'i': 70, 'uid': 23541}` and `{'i': 71, 'uid': 23576}` — `tools/bench/diag_c62_branch.log:82,:86`. That **is** a uid→handle route: Traverse class + index.
- That is exactly the addressing mode the fleet already uses to *act* on objects: `delete_object` = "the `index`-th object of Traverse class `cls`" (`tools/gscript.py:2275`), `move_object` (`tools/gscript.py:2334`). And `tools/gscript.py:1312-1313` records the measurement that **`ControlTerminal` is among the classes `delete_object` removes exactly one of**.
- This very run used that route to address and delete `Wire[715]` / `Wire[710]` by uid (`diag_c62_branch.log:118,:155`).

What is actually missing is an op that reads **`Terminal.Connected Wire` 634A000** off a Traverse-obtained reference. The project wrote that route down long ago: *"The correct route is `Traverse('ControlTerminal')` → `Terminal.Connected Wire` (634A000)"* — `docs/main-vi-startup.md:70`.

And the capability is not even absent from the fleet, only from that path: **`OpPanelWiring_v0` already walks `Panel.Controls[] → Control[Terminal] → Terminal[Is Source?, Connected Wire] → GObject[UID]`** (`tools/gscript.py:832-834`). It is holding a correctly typed Terminal reference and already reads a `GObject.UID` off that branch — of the *wire*. `tunnels()` likewise reads Terminal properties off a LoopTunnel's terminals (`tools/gscript.py:947`).

"This toolkit has no verb that maps one to the other" is false in a second, already-measured way too: the **by-effect resolver** (`tools/recipes/build_d1_routeb_v1.py:519-587`) maps ControlTerminal uid → control uid by moving the terminal and reading which `panel_wiring` row changed — run and recorded ("control uid 7 `stop (end)` as `ControlTerminal #642` in 14 s", `build_d1_routeb_v1.py:38`). Destructive, yes — but this run was already deleting wires on throwaway scratches, so the cost objection does not apply.

Finally, `ControlTerminal.Control` **6353000 exists and is documented**: *"Returns a reference to the control"*, read-only. `docs/d1-build-plan.md:909` says it is UNVERIFIED **in `docs/vi-server-ids.json`** — i.e. *we* have not measured it. The explanation upgrades "we never measured it" → "no verb maps one to the other" → "not readable". Only the first is supported. That is CLAUDE.md's own trigger sentence: absence in what you happen to be looking at is not evidence of absence.

## 2. Alternative explanation of the same evidence

**A toolkit-coverage gap plus a script-logic bug — not an interface limit.** Three local causes account for every observation:

1. `label = None` — `node_labels` walks `Diagram.Nodes[]` (`tools/gscript.py:589`), which a Terminal is not in. *(Agreed.)*
2. `wire = None` via `node_terms` — the script **chose not to look**: `terms_of_uid(..., allow_scan=False)` returns early with `how="SKIPPED"` (`diag_c62_branch.py:257-261`). A deliberate skip, not a machine refusal.
3. `panel_rows_with_that_label = []` — **route 2 never ran.** It filters `[r for r in prows if lab and r["label"] == lab]` where `lab` is *route 1's* output (`diag_c62_branch.py:455`). `lab` was `None`, so the guard short-circuits and the comprehension compares nothing. The `[]` at `:83,:87` is an unexecuted lookup, not a failed one.

So "None for both, by both routes it tried" is really **one route, plus a second route disabled by the first route's failure**. The post-hoc explanation then rationalises route 2's non-result with a *different* cause — "panel_wiring reports the CONTROL's uid, not the ControlTerminal's" — that the run never tested. That is an explanation fitted to the outcome afterwards.

**The measurement does not distinguish** "unreachable over ActiveX/COM" from "no op built + dead second route". The claim asserts the first; the evidence supports only the second.

## 5. The documentation question, answered explicitly

**NI documents a class and an owner, not a container — and those settle it.**

- **Class:** `Generic → GObject → Terminal → ControlTerminal`. The `Terminal` class carries `Connected Wire` (634A000), `Is Source?` (634A003), `Diagram` (634A002, *"Returns a reference to the owning diagram"*), `Name` (634A004); its children are `ControlTerminal, InnerTerminal, OuterTerminal, ParameterTerminal`. A ControlTerminal is therefore **not a Node** — which is why a `Nodes[]` walk cannot hold it.
- **Owner:** NI's own AE (Darren): *"Items that inherit from the 'Control' class are front panel objects. The 'ControlTerminal' class represents the terminals for those controls on the diagram"* and *"As far as why node Terminals are owned by nodes, and ControlTerminals are owned by diagrams, that's just the way it is."* That is the documented source of `owner_of` reporting `'Diagram' uid 639`.
- **Caveat, plainly:** I did **not** find any NI or Wiki page that enumerates what `Diagram.Nodes[]` contains. The Wiki's *Diagram class* page is a stub listing only `Functions[]`, `Is Break Point Set`, `Visible Bounds`, with inheritance `Generic → GObject → AbstractDiagram → Diagram`; `Nodes[]` lives on the parent **`AbstractDiagram`** (what this project's ops actually target — `docs/main-vi-startup.md:65`, `tools/gscript.py:589`). So "Terminal ∉ Nodes[]" rests on the hierarchy + NI's ownership statement + five local measurements, **not** on a documented enumeration. `Diagram.GObjects[]` is not documented there at all; I would not assume it exists.
