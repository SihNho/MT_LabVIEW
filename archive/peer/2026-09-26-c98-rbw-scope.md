## Answer

**The claim is right on its narrow point and wrong on what it concludes from it.** No single VI Server method removes broken wires on one diagram only. But a scoping to one diagram can still be built from methods that exist, so the phrase "otherwise to the VI" in Pre-decided 208(c) isn't forced. Whether `Remove Wire Loose Ends` deletes a wire with no terminals at all isn't documented anywhere, and nothing in the logs has measured it.

## (1) Is there a method that removes broken wires on one diagram?

There is no single one. The LabVIEW Wiki class pages list private members as well as public ones: AbstractDiagram shows the private `Get CodeWizRef`, `Build IGL` and `Gen Script Diagram`, and the VI page says outright that private items are included. Their contents:
- **AbstractDiagram** methods 6375400–6375409: the only wire method is `Remove Wire Loose Ends` 6375409.
- **Diagram** methods 6D17C800–804: object-from-point, clean-up and create-from-data-type. Nothing removes wires.
- **Wire** methods 6370C00–0D, including `Remove Loose Ends` 6370C08, `Get Error List` 6370C0A and `Disconnect Terminal` 6370C0D.
- **VI** class: `Block Diagram:Remove Bad Wires` 410 is its only method of this kind, and it takes no parameters.

The editor does have a narrower version. On NI's Idea Exchange, crossrulz (2025-03-10) says Ctrl+B has worked on a selection only since somewhere between LabVIEW 8.2 and 2021, and on a selected case structure it clears every case. Method 410 exposes no selection argument.

Caveat: the Wiki's snapshot may predate LabVIEW 2026, so "none exists in 2026" is likely, not proven.

## The strongest reason the conclusion is wrong

"Reachable only as a VI method" confuses *one method* with *being able to do it*. A cleanup limited to one diagram can be composed from existing members:

1. `AbstractDiagram.Wires[]` (6375805) on the source diagram and on the frame's diagram.
2. For each wire, read `Terminals[]` (6371003) and `Is Broken?` (6371004).
3. Delete a wire that has no terminals by uid (card 98-2 already does this, `selftest_c98_stage.log:364`).
4. Call `Wire.Remove Loose Ends` (6370C08) on a kept wire that has dangling branches, or `AbstractDiagram.Remove Wire Loose Ends` (6375409) once per diagram.

The project already builds property nodes that read 6371004 and 6371003 together (`tools/recipes/build_opallwires_v0.py:44`).

⚠️ Deleting a wire that has loose ends would sever a live data edge. Kept wires must be trimmed, never deleted.

## (2) Does `Remove Wire Loose Ends` delete a wire with no terminals?

**Unknown.** NI's text is only "Traverses the referenced diagram and removes all wire ends that are not connected to anything." A wire with an empty `Terminals[]` consists of nothing but loose ends, so deleting it whole is plausible. No source says so, and nothing says whether "traverses" includes nested sub-diagrams. The Wiki page's remarks section is empty.

## Other explanations of the same evidence

- **The loose-ends diagnosis for card 98-2 was never measured.** The 6 "Wire has loose ends" items come from card 98-1's Error List, read at stage E3 after both moves with the termless wires still present (`diag_c98_fgate.log:558-572`). Card 98-2's ExecState 0 after move A plus UseDefault (`selftest_c98_stage.log:383-384`) never had its Error List read. "After move A alone, Remove Bad Wires gives ExecState 1" is asserted in 208(d), not measured. The removal that gave 1 (`:469-479`) ran on the E3 file.
- **The count is off.** The Error List shows 9 "not connected" (items 4–11 and 14) and 6 "loose ends" (items 0–3, 12, 13), not the 8 and 7 in 207(a). The 9 matches the 9 termless wires exactly.
- **The uid fence can't see trims.** Remove Bad Wires took the wire count from 1918 to 1909, which is exactly the 9 termless wires. So the loose ends were trimmed on wires that kept their uids. Fence (2), "removed uids were present before", can't see a trim. Only the check "no source→sink pair lost" covers it, and `gscript.py:3531-3533` puts that check around the Remove Bad Wires call only, not around the move.
- **A known hazard is not fenced in advance.** `docs/NAMES.md:1194-1197` says: never run Remove Bad Wires while a node output is momentarily untyped, because every wire downstream then counts as broken and gets deleted. `move_into_frame` runs Remove Bad Wires *before* `tunnel_use_default`. The fences detect such a deletion only after the damage, so recovery means reloading the saved file.

## What would falsify the claim

On a scratch copy of the broken file, calling `Remove Wire Loose Ends` 6375409 on diagrams 7911 and 639 (w10908's owner) takes the wire count from 1918 to 1909 and ExecState to 1. Or, alternatively, the diagram-by-diagram composition above reaches ExecState 1 without method 410.

## The cheapest test that separates the two

1. Build one invoke op for 6375409. That is a new tool, so the judgement session has to approve it.
2. Run it on a byte copy of `claudeDev\D1_s1_fgate_BROKEN_20260926_175556.vi` (md5 `b114bb1b…`).
3. Read the wire count, whether the 9 uids are still there, ExecState, and the Error List.
4. Read the result:
   - All 9 gone and ExecState 1: scoping to the two diagrams is achievable; use it.
   - Loose ends trimmed but the termless wires remain: the method doesn't delete termless wires. Combine it with the uid deletion 207(c) already does, then read ExecState again.
   - ExecState stays 0: something else is breaking the VI.
5. At the same time, re-run move A alone on a scratch copy and read the **Error List after A**. That tests the loose-ends explanation directly.

If that test is not run, the whole-VI fallback is still defensible: it rests on the "ExecState 1 before the move" precondition, which means no break existed before the move. Two things should be written into 208(c) with it: the pair-loss check must be bracketed from before the move, not only around Remove Bad Wires, and Remove Bad Wires must run after `tunnel_use_default`.
