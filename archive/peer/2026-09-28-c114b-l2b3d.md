## Answer

# Review of the claim about failed gate D in stage L2-B3 (card 114-1)

**No, the claim does not hold as written. Its mechanism rests on a premise that the base graph contradicts.** Its conclusion is probably right anyway: the change is in wire IDs only, not in which terminals are connected. But it is right for a reason the claim does not give, and the one check that would settle it was never recorded.

## 1. Strongest reason the claim is wrong: the three wires were not source-only

The input graph B3 used (`tools/bench/graph_l2b2b_20260928.json:1`, the saved read of the B2b VI, md5 4f51fd4c) shows that each wire had live sinks when the stage started:

| wire | source terminal | existing sinks (outer terminal of a loop tunnel on frame 686) |
|---|---|---|
| w28392 | t27635 (SubVI #27605) | t28334 (LoopTunnel #28311, on a ForLoop) and t28348 (LoopTunnel #28343, on a WhileLoop) |
| w5174 | t5186 (FSIT #5183) | t5170 (LoopTunnel #5129, on a WhileLoop) |
| w5336 | t5671 (FSIT #5669) | t5333 (LoopTunnel #5328, on a WhileLoop) |

The wires that really have no sink are one step further downstream: the inner wires of those tunnels, w628, w1773 and w28338, on diagram 639.

- The "left with #1359/#2222" description fits these inner wires, not the three wires the stage connected to.
- w628 and w1773 both appear in the list of wires that Remove Bad Wires deleted on the scratch copy (`stage_d1_l2b3.log:142`).

So each connection in B3 joined an existing net that already had sinks. That is the second measured case in the connect-from-wire model (`tools/bench/opmodels/connect_from_wire.json:102-218`, sample `cfw_2`), not a new behaviour of source-only wires. The model already records the rule (`connect_from_wire.json:266`): **"The SOURCE's wire is RE-CREATED under a new uid … its 3 other sinks are re-wired, same (src, sink) pairs"**. Sample `cfw_2` measured the same outcome as B3: 2 new wires and the old one deleted (`:213-219`).

Two consequences:

1. **The error is not "the simulator's wire-ID model" in general.** The simulator ignored its own measured model. It treats the connection as a join (`connect_from_wire.json:4`, `"sourceless_sink": "join"`), so its final step `sim/l2b3/l2b3/step_09_wire.json` still carries 5174, 5336 and 28392. Gate D then compares sets of wire IDs (`tools/recipes/stage_d1_l2b3.py:56-59`).
   - Fix the simulator by modelling "the source's wire is re-created" for every connection to an already-wired source, taken from the model file.
   - Do **not** encode "source-only wire gives +2/−1". That rule would be keyed on the wrong condition.
2. **The real correctness risk is one the claim never names.** It is whether the four existing sinks (t28334, t28348, t5170, t5333) were re-attached to the re-created net. The log never states this. Three of the six new wires (25911, 26021, 26064) are not attributed anywhere:
   - they are absent from `stage_d1_l2b3.json` (searched: no match);
   - they are absent from the log, which attributes only the sink wires 25782, 25819 and 25833 (`:123`, `:139`).

## 2. Alternative explanations of the same evidence

- **A. The claim's version, with the corrected mechanism.** Each source net is re-created once. The source, the old sinks and the new tunnel's outer terminal sit on one new wire, and a second new wire runs from the tunnel's inner terminal to the sink: 3 × (+2, −1). This matches `cfw_2`.
- **B. The re-created source wire does not carry some or all of the old sinks.** For example, an old tunnel's outer terminal ends up on a separate stub, or is left unwired. The count of 6 new / 3 lost cannot tell A from B, because gate D only compares the count of new wires (`stage_d1_l2b3.py:59`, `len(new) == len(sim_new)`).

What argues against B:

- E1 compares, at every checkpoint, the set of (source terminal → sink terminal) pairs, joined by wire ID within one whole-VI read (`tools/stagexec.py:30-32`, `:438-442`, `:465-480`).
- The simulation keeps the pairs 27635→28334/28348, 5186→5170 and 5671→5333 (`step_09_wire.json`).
- If a pair were missing in the real graph it would appear as `only_sim_edges`. That is always classed as a failure, never downgraded to the "dangling only" warning (`stagexec.py:508`).
- E1 reported `bad: []` (`stage_d1_l2b3.log:100`).

**So E1 does exclude B, provided the checkpoint reads include diagram 686.** The log says they are whole-VI reads that touched diagrams [686, 23166] (`:37`, `:39`). This is the strongest support for the claim's conclusion. The claim itself cites E1 but never explains why E1 can see the sinks.

## 3. The wire-ID reuse is less predictable than the model says

- In step 2 the unwanted Invoke node took ID 5174, the ID of the wire that had just been deleted (`log:64`). That fits the model's "an ID freed by a deletion is re-issued at once" (`connect_from_wire.json:10`).
- In step 3 it took 5174 again, not the newly freed 5336 (`log:84`). In step 1 it took 10366, not 28392 (`log:44`).

So how IDs are re-issued is not predictable. The purge was safe here only because the class check and the zero-wired check run before the delete (`log:73`, `:93`).

A later stage in which a plan row names a wire by ID *after* a connection on that same wire could have that ID resolve to an Invoke node, or to nothing. B3 uses each wire once, so it is not affected, but a plan-level check should forbid this.

## 4. What would falsify the claim

In the saved VI `D1_l2_b3_20260928_032703.vi` (md5 1b5c12d7), any one of these:

- a source terminal (27635, 5186, 5671) whose wire does not also carry all of its old sinks and exactly one new tunnel outer terminal;
- any of 25911, 26021 or 26064 carrying a terminal outside that set;
- more than one wire per source on diagram 686.

## 5. Cheapest discriminating test

It cannot be done fully offline, because the end-state terminal rows were not saved (`stage_d1_l2b3.json` has no row for t28334 or w25911).

1. **One read-only terminal read of the saved B3 VI** (`AT.read_terms(..., AT.OP_ALLTERMS_V1)`, about 20 s, under bgrun, no edits).
2. For each of the three sources, check that the set of terminals on its wire equals {source} ∪ {old sinks from the base graph} ∪ {bound outer terminal: t25893, t26005 or t26044 according to the binding at `log:101`, or its pair}.
3. Check that {25911, 26021, 26064} are exactly those three wires.

If all three hold, the conclusion stands and gate D should be rebuilt to take the expected new and lost wires from `removes_rule` in the model file. If any one fails, B holds and the saved VI has a real connectivity defect that E1 missed.

## What would change my mind

**If the step-2 read above shows all four old sinks sharing the re-created wire with their source, I accept the claim's conclusion.** What would still stand is the correction that the trigger is "the source was already wired", not "source-only", and that the model had already recorded this behaviour.

The external check agrees with that correction:

- NI documents Connect Wire as a terminal method. It creates the tunnel at a structure border itself, and there is no documented way to "extend" an existing wire object in place ([NI: Connect Wire](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/terminal/connectwire.html), [NI forum: creating a tunnel with scripting](https://forums.ni.com/t5/LabVIEW/Programmatically-creating-a-tunnel-with-LV-scripting/td-p/1830745)).
- Existing wires cannot be targeted; the forum workaround is to delete a wire and re-create it ([NI forum: connecting loose wires to case tunnels](https://forums.ni.com/t5/LabVIEW/Script-connect-existing-loose-wires-to-case-tunnels/td-p/4195933)).
- That is consistent with the wire being re-created, but NI does not state it as fact.
