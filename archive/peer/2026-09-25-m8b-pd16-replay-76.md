## Answer

**Verdict: refuted.** One clause breaks. PD16(a), combined with PD16(b)'s stand-in, keys frames by a buffer number that starts from the live camera. The tracking kernel carries state from one frame to the next. So PD13(d)'s test, which joins the two runs on frame number and requires bit-identical X/Y/Z, can fail when nothing in the computation changed. It can also end up with fewer than 1,000 common frames. PD16(b) and (c) hold up, with caveats. PD16(e) has two predictions that can fail for reasons unrelated to the replay.

**1. The strongest reason: the frame number is not a stable key (PD16(a) with PD13(d)).**
- **The first buffer comes from the live camera.** `Buffer to extract` (#6810) is the shift register `LastBufferNumber` #5351 (`docs/wiki/subvi/D1_s1_copy.json:36644-36652`, wire 5416). That register is initialised outside the loop from the IMAQdx Property #250 `LastBufferNumber` on the live session (`D1_s1_copy.json:24115-24121`, `:24605-24611`, wire 1827). Each iteration it becomes either `current image number` (case frame d206, wire 817) or itself (d253), then goes through `x+1` #1978 (`:67175-67217`). With PD16(b)'s stand-in (Out = In), both case frames give "requested + 1". The requested sequence is therefore exactly S, S+1, S+2, …, where S is whatever the free-running camera reports when the loop starts. S differs between runs, because bead picking and calibration take a different amount of time each run.
- **Nothing is ever skipped.** PD13(d)'s reason for joining on frame number ("frames skipped under load differ by run") no longer applies, because the stand-in never skips. The only thing that differs between the two runs is the starting frame.
- **The kernel remembers earlier frames.** #5058 takes `x,y,z array` from #6016, `Bead is good? array in` from #5680, and `pos in cal image in` from the left shift register #2972 (`D1_s1_copy.json:69948-70351`, `:71544-71550`). So its result for frame n depends on every frame the run tracked before n. If the two runs start at different frames, their results at the same frame can differ with identical maths. That would be a false failed prediction, and PD13(d) says to answer it with a review, not a tolerance.
- **The `mod 10044` wrap** adds a jump in bead position at f10043 → f00000.
- Sorting itself is fine. The names are 5-digit zero-padded (maximum 11825), so string order equals numeric order, as long as `cal002` and `tra002-000` are filtered out. The folder is also valid for S1 vs S3 equivalence, since both runs use the same mapping.

**2. PD16(b) survives, but its wording overclaims.**
- `Missed frames?` feeds only two things: Tunnel #270, whose inner terminals on d206 and d253 are unwired (`:35425-35512`, most likely the case selector), and the indicator `Missing Frames?` #1924 (`:36714-36722`). With Out = In, both case frames produce the same next buffer number. A TRUE value does not skip tracking.
- It is not established that TRUE is "the normal real-camera value". The mode input comes from enum constant #581 (`get buff image-lost frames.json:301-310`), and its value has not been read. NI documents that `Buffer Number In` is ignored unless the mode is "Buffer Number" ([NI IMAQdx Get Image](https://documentation.help/NI-IMAQdx-VI/IMAQdx_Get_Image.html); [NI forum](https://forums.ni.com/t5/Machine-Vision/quot-buffer-number-in-quot-confusion-with-IMAQdx-get-image/td-p/688948)). This does not affect equivalence, but the justification sentence is unverified.
- `current image number` is wired from `Buffer Number Out` (wire 99, 2 sinks), not from `Buffer to extract`. The prediction still holds only because Out = In.

**3. PD16(c): the plan is sound, but the check is too weak.**
- Library ownership is not part of connector-pane matching. The ExecState 0 on the byte copy fits NI's documented error "VI claims to be part of a library, but that library does not claim it", and the documented fix is Disconnect from Library ([NI error page](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/errors/library-does-not-claim-vi.html); [NI KB](https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z0000019MnqSAE&l=en-US)). An unowned stand-in with the same pane should be swappable.
- The real risk is **type identity**. The IMAQdx session refnum, the IMAQ Image typedef and the mode enum on slot 7 must all be the same as in the vi.lib original. The measured pane is only names by slot (`replay_vis_76_measure.log:37`), so a "pane diff ∅" by name can pass while the types differ. The check must compare each terminal's type, not only its name.

**4. PD16(e): two predictions can fail for the wrong reason.**
- **"Pixel md5 == f00005's source file."** If this means the file's md5, it can never pass, because a TIFF file includes a header. It must be the md5 of the U8 1024×1280 pixel array. It also depends on the Image In type the test creates. The caller's IMAQ Create type comes from a ring constant whose value has not been read (result_76-1 fact 13).
- **The cal stand-in's call counter keeps its value while the VI stays in memory.** If the three test calls, or the S1 run, happen in the same LabVIEW instance as a later run, that run's calibration starts at k ≠ 0. The two calibration stacks then differ, which is another false failure.

**Alternative explanation:** a nonzero ΔX/Y/Z in PD13(d) would come from different starting frames S (the kernel state carried from earlier frames), not from the swap.

**What would falsify my objection:** the two runs' tra files show the same first frame number, or #5058's outputs turn out not to depend on the previous frame's `x,y,z` or `pos in cal image`.

**Cheapest discriminating test (no LabVIEW needed):**
1. Offline, trace `current image number` → #5119 → the tra frame column in `D1_s1_copy.json`, and read the first frame number of two earlier real-run tra files. If they differ, S is run-dependent.
2. For the fix, make the frame index `f((n − n₀) mod 10044)`, with n₀ latched at the first call and reset on each fresh LabVIEW launch. Run S1 and S3 in separate LabVIEW launches, and join on iteration index.
