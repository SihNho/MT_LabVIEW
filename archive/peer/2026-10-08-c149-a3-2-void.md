## Answer

**The census can't see Void at all, so "0 Void" from that check means nothing.** The throughput explanation for the COV FAIL holds, but the claim's Void result rests on a check that could never fire.

## 1. Strongest reason the claim is wrong
- The script flags a terminal as Void only when a type-descriptor name contains the text "void" (`tools/bench/diag_c149_a3_void.py:90`).
- Those names come from `TD_NAMES` (`tools/gscript.py:4585-4588`), which has no entry for code 0x00. An unknown code becomes the string `"0x%02x"` (`gscript.py:4606`), so a Void descriptor is named `"0x00"`. `"void" in "0x00"` is always false.
- The project's own measurement says Void reads back as "EMPTY (void, TD 0x0000)" (`docs/NAMES.md:1171`). LabVIEW's type-descriptor tables agree: typecode 0x00 is Void, and 0x37 is Tag ([LabVIEW Wiki](https://labviewwiki.org/wiki/Type_descriptor), [LAVA Data Storage](https://lavag.org/old_files/post-15-1073109843.pdf)).
- So `VOID 0` at log line 16 would have printed even if every terminal were Void.

**Partial rescue, which the claim did not make:** I searched the raw names in `diag_c149_a3_void_s06.json`:
- The name `"0x00"` appears 0 times.
- No `codes` list contains a 0.
- The only unnamed code is `"0x37"` (Tag, e.g. a VISA resource name).
- The script also counts Void-like failures separately: no bytes or a parse error would land as `err`, and the log shows 0 read errors.

So within the 1,112 terminals that were read, there is no code-0 descriptor and no empty or unparseable variant. That is real evidence, but it comes from reading the raw JSON, not from the script's Void check. The report must say "0 Void, checked from the raw codes", not "VOID 0".

**A second, smaller error in the claim:** it says w28684 and w29766 were not covered. Both are above the last wire read (w26932), and both are in the JSON (`"wire": 28684` twice, `"wire": 29766` three times). Only w10166 and w23807 among the session-6 new wires are uncovered.

## 2. Alternative explanation of the same evidence
- **Reader blind spot.** Covered above: the check cannot fire on code 0x00. It rules out nothing on its own.
- **Wrong place to look.** `Terminal.Data Type` returns the terminal's own type. A sink pin on a subVI or a typed primitive keeps its declared type even when its wire is broken or void. Only terminals that take their type from the wire (tunnels, Select / Build Array inputs, shift registers) would show Void. So even a fixed check over every wired terminal could miss a void *wire* whose ends are all fixed-type pins. The measurement doesn't separate "no void wires" from "void wires that only touch fixed-type pins".
- **Throughput.** I agree the FAIL is a rate limit, not a VI or LabVIEW fault. The rate was flat at 0.54–0.63 s/read with no climb, handles fell, and there were 0 errors. 4,379 × 0.54 s ≈ 39 min, which a 600 s cap can't reach. "No bulk type reader exists" rests only on a grep for `^def .*type`. That is weak evidence of absence: `allterms.read_terms` already walks every terminal in one op run and was never checked for a type field.

## 3. What would falsify the claim
- Any terminal in the JSON with code 0 or name `"0x00"` falsifies "0 Void in the read range".
- A known-Void terminal that the script reports as non-Void proves the blind spot is live. A test on one such terminal would prove it either way.
- On throughput: one bulk read covering all 4,379 terminals in under 600 s shows the cap was not "always going to cut it". It shows the per-terminal reader was the wrong choice, not a hard limit.

## 4. Cheapest discriminating test (offline first, no LabVIEW)
1. **No LabVIEW needed:** run `parse_type_descriptors(bytes.fromhex("26008000" "00000001" "0004" "0000" "0001" "0000"))`. That is a one-descriptor Void type string, assuming Void flattens with no label. It should return `name == "0x00"` and a Void flag of False, which proves the blind spot. The fix is to flag on `code == 0` and on a variant with zero descriptors, not on the name.
2. **Then one short LabVIEW read on a byte copy:** make a scratch VI with a tunnel whose source wire was deleted (a known Void), run `read_term_type` on it, and record its bytes. This calibrates what Void actually looks like through `OpTermDataType_v0`: code 0x00, zero descriptors, or an error. Until that is measured, nobody knows which case the fixed check must catch.
3. **Throughput:** before rerunning about 80 min of per-terminal reads, check whether `allterms.read_terms`' op can return `Data Type` alongside each row.

**Verdict:** the throughput part holds; I'd change my mind only if a bulk reader turns up. The "0 Void" part does not hold as written. The raw codes support it for wires w30418…w26932 only, which leaves 3,267 terminals unread, including w10166 and w23807. And the check that prints the count could never have found a Void.
