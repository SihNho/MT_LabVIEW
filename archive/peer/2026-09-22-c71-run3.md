## FAILURE 1 — "uid 9649 was freed and recycled, so the walk resolves to another wire"

### 1. Strongest reason it is wrong: the recycling event does not exist

NI's own rule is that when you delete an object, LabVIEW "might assign the UID for that deleted object **to a different object in the future**" ([GObject UID property, LabVIEW Wiki](https://labviewwiki.org/wiki/GObject_class/UID_property)). Recycling hands a freed uid to a **newly created** object. It does not repoint a freed uid at an object that already exists and already has its own uid.

Between the purge and the walk there is no creation:

- `build_d1_m3a1.log:1783` — delete Node #9649, census 633 → 632
- `:1786` — a FACT print
- `:1787` — the walk of 9649 returns wire 24009's terminals

The only mutation in that window is a **deletion**. Wire 24009 already existed with uid 24009 (`:1763-1766`). There is nothing for 9649 to have been recycled onto, so "recycling" cannot be what produced those rows. (The one route by which a creation could sneak in is the op minting its own junk — but that would mint an `Invoke` node, and an Invoke's terminals are not `LoopTunnel 24035` / `SelectorTunnel 9623`.)

### 2. Alternative: the reader's output is not a function of its input

Two queries of the same uid, under the same condition, 28 s apart in the same run:

| line | when | no Wire holds 9649? | result |
|---|---|---|---|
| `:1759` | after the write, junk Invoke #9649 alive | yes (UIDs are unique per VI) | **1 null row** |
| `:1787` | after the purge, nothing holds 9649 | yes | **wire 24009's three rows** |

Same query, same "no Wire has this uid" state, two different answers. A deterministic resolver cannot do that. And `:1788-1790` is field-for-field identical to `:1764-1766` — the immediately preceding `OpWireSource_v5` call — and the cycle-56 twin repeats it exactly (`:1074-1076` vs `:1096-1098`). Two runs where a dead uid "resolves" to precisely the wire the reader was last asked about.

The mechanism is available in the code: `wire_source_owner` (`tools/recipes/build_opconnectfromwire_v0.py:423-447`) calls `g._run(vi)` and then reads four indicators — **it reads no error output at all**, and `g.op()` returns a *cached* VI proxy, so indicators and any uninitialised shift register inside the op persist across calls. That function is structurally incapable of distinguishing "the op answered" from "the op did not answer."

### 3. This also voids the branch that PASSED — and the experiment underneath it

`build_d1_m3a1.py:148` cites `diag_c68_pd86.log` as *"outcome A: the reader NULLS on an unresolvable uid; it does not echo."* That log's own verdict line says the opposite:

> `diag_c68_pd86.log:35` — `*** PRE-DECIDED 86 OUTCOME: B-STALE-ECHO … EVERY identity conclusion of cycles 55/56 is VOID ***`

Neither reading is earned. PD86 ran **Q1 = ghost 24009** and **Q2 = max int** — *both unresolvable, both null* (`:17-20`) — then three live queries. "Q2 returned Q1's rows field-for-field" is equally predicted by "it echoes" and by "both nulled". The one ordering that discriminates — a **live** query followed by an unresolvable one — was never run. PD85 and PD86 both rest on a non-discriminating experiment, and run 3's gate rests on them.

So the real defect is not "the gate's dirty-walk branch." It is that **both** the null at `:1759` and the rows at `:1787` are unresolvable-uid queries, and the reader gave contradictory answers. `A3-ID [5](a)`'s **PASS must be withdrawn alongside [5](b)'s FAIL** — a wholly-null walk is exactly what a reader that wrote nothing produces, and every complete walk terminates on a null padding row, so the indicators are *already* holding `(False, '', 0, 0)` when the next call starts.

The proposed fix — extend outcome A to cover PD85-dirty walks — turns a FAIL into a PASS by widening the branch that is itself unsound. It makes the gate greener and less true.

### 4. What would falsify my position

A walk of a never-existed uid issued **immediately after a live, non-null walk** that returns a genuine null. That would show the reader answers from its input, restore outcome A, and leave "recycling" as the only explanation of `:1787` — which I would then have to accept.

### 5. Cheapest discriminating test

Read-only, one fresh LabVIEW, a plain copy, no edits, ~5 op runs, well under a minute — the ordering PD86 skipped:

1. walk live wire **L** → expect non-null rows
2. walk `2147483646` (never existed) → **null ⇒ input-determined; L's rows ⇒ history-determined**
3. walk a different live wire **M**
4. walk `2147483646` again → **M's rows clinches it**

And the durable fix is the reader, not the gate: have `wire_source_owner` read the op's error output, and have the op echo back the uid it actually matched. Three cycles (55, 56, 68) have now explained this class of failure by inference — CLAUDE.md's own rule says the next build is the reader.

## FAILURE 2 — "Ctrl+S raised a modal and gui_save's Esc cancelled it"

### 1. Strongest reason it is wrong: Ctrl+S was never sent

`lv_gui.ps1:631-641` writes the audit row **at dispatch, before the switch executes** — every `keys` and every `click` is logged whether or not it has any effect. `tools/gui_actions.log` ends at line 1800, **`2026-09-18 18:12:14`**. There is no row at `2026-09-21 23:42`, and the string `gui_save` appears **zero times in the entire file** — so neither the title-bar click nor `^s` nor `^e` was ever dispatched, in run 3 or in `build_d1_routeb_v7_run10` (`:1` — 2026-09-19 06:55, also after the log's last entry).

`gui_save` skips its whole body via `continue` when `focus` fails (`gscript.py:2033-2034`), then raises an error whose text asserts something the code does not guarantee — *"after Ctrl+S on every candidate window"* — and then names a cause: *"a modal dialog blocks the save."* **The error message pre-loaded H1.** The diagnosis was found by looking where the message pointed.

No Ctrl+S ⇒ no dialog raised by Ctrl+S ⇒ nothing for Esc to cancel. H1 is dead. H2 as stated ("the keystroke never reaches the VI window") is also dead: the keystroke was never *sent*, so delivery never arose.

### 2. Alternative: the `-Title` argument is mangled — and only in `gui_save`

Your own before-capture shows a window titled **`WORK_C68M3A1_20260921_234216.vi Front Panel`** (there is no Block Diagram window, so candidate 1 fails legitimately). `focus` matches by substring (`lv_gui.ps1:684-685`), so candidate 3 — the bare file name — *must* have matched a live window. It did not report `focused: …` (`:687`).

`_lv_gui` (`gscript.py:272-277`) joins args into one `powershell -Command` string and passes it through `subprocess.run(list)`, so Python's `list2cmdline` backslash-escapes embedded quotes, and `powershell.exe` handles `\"` badly. Every other `-Title`/`-Out` call site in gscript uses **single** quotes (`:1664, :1666, :1671, :1673, :379, :418`). `gui_save` is the **only** place using **double** quotes (`:2025, :2026, :2032, :2041`). That predicts `gui_save` has never once worked — which the audit log confirms across its entire recorded history.

The Getting Started window being foreground is not evidence for H1; it is the ordinary consequence of `open_panel(..., activate=False)` (`gscript.py:1264-1270`). And "the after-capture shows NO dialog" is equally predicted by "no dialog ever existed" — you are reading a null observation as support.

Separately, H1's dialog class is the wrong one: the *Save changes before closing* dialog fires when you **close** an unsaved VI, not when you save it ([NI: Unsaved Files / Explain Changes](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/dialog-boxes/unsaved-files-dialog-box.html)).

### 3. What would falsify my position

A `keys … Key=^s` row in `tools/gui_actions.log` timestamped inside the run-3 save window, or a `focus` call in that window returning `focused: …`. Either would put the failure back downstream of the keystroke and revive H1/H2.

### 4. Cheapest discriminating test — and why yours is not it

`diag_c68_guisave.py` copies a bed, breaks it, opens a panel and sends real keystrokes; it logs the focus output at `:112`, but its verdict line (`:143-144`) offers **only H1 and H2**, so if focus fails it will show no dialog at either read and be scored as "H2 confirmed" — the wrong conclusion, arrived at expensively.

Do this instead, with **no LabVIEW and no GUI action**:

```

print(_lv_gui("-Action", "focus", "-Title", '"LabVIEW"'))   # gui_save's double-quote form
print(_lv_gui("-Action", "focus", "-Title", "'LabVIEW'"))   # every other call site's form
```

Different outputs ⇒ the quoting is the bug, fix is four characters in `gscript.py:2025-2041`. Identical `focused: …` ⇒ quoting is exonerated, and the next step is `-Action windows` captured at the moment of the save.

Whatever the cause, add the missing assertion: **`gui_save` must fail loudly when it never dispatched a keystroke**, instead of raising an error that describes an action it did not take.
