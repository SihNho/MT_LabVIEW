## What the gate actually does (read it: `tools/bench/c60c_astcheck.py`, `SPEC_RE`, `_spec_count`, `percent_format_sites`)

  Each match consumes `1 + (width == '*') + (prec == '*')` arguments; `conv == '%'` consumes none;
  a `%(name)s` mapping key is collected and the site is then declared UNRESOLVED, never counted.
- RIGHT operand: a literal `ast.Tuple` without `Starred` is counted by `len(elts)` and a mismatch FAILS.
  A non-tuple right operand passes when exactly one spec is wanted, FAILS when zero are wanted, and is
  reported UNRESOLVED when two or more are wanted (it may be a tuple at run time).
- UNRESOLVED sites are printed with `file:line`, never silently passed, and never failed.

## 1. Strongest reason the claim is WRONG

**`c60c_astcheck.py:185-186` files a site under `n_ok` that it has not checked, and the gate's own contract says it does not do that.**

```python
elif want == 1:
    n_ok += 1    # one spec, one non-tuple expression: correct whatever its type
```

The comment is a false statement about Python. The docs: *"If format requires a single argument, values may be a single **non-tuple** object. Otherwise, values must be a tuple with the correct number of items for the format string, or a single mapping object."* ([docs.python.org/3.13, printf-style String Formatting](https://docs.python.org/3.13/library/stdtypes.html#printf-style-string-formatting)) So `"%s" % x` raises `TypeError: not all arguments converted during string formatting` for **every** tuple `x` whose length ≠ 1 — the sibling of the exception that killed the run. The gate cannot see the type of `x`; it guesses, and files the guess as a verified pass.

The asymmetry is the tell. The **identical** unknown with `want >= 2` is filed UNRESOLVED and printed (`:190-194`, "A bare name/call on the right MAY be a tuple of the right length at run time. Unknowable statically"). Same unknowability, opposite verdict — and the branch that inflates confidence is the silent one. Meanwhile `:44-48` and `STATUS.md:26` both assert **"a site it cannot resolve statically … is PRINTED under UNRESOLVED, never silently passed."** That assertion is false as written, in two documents.

This is not a corner. In the file under test the single-operand shape is dominant: a line grep of `build_d1_m3a2.py` finds **117** lines where a string literal is followed by `% <identifier>` against **63** followed by `% (`. And the hazard is live, not theoretical — `M.node_census(...)` and `safe(...)` both return 2-tuples and are interpolated all around these sites (`build_d1_m3a2.py:369`, `:475`). So "the 145 it passed are really correct" is not what the log says. The log says *145 sites landed in a bucket labelled OK*.

**Second, independent reason, since the brief asked for a concrete wrong shape — the counter is blind to the exact accident that caused the defect it is celebrating for catching:**

| source text | gate 10 | CPython |
|---|---|---|
| `"%d%" % (n,)` | want 1, got 1 → **PASS** | `ValueError: incomplete format` |
| `"50% (of rows): %s" % (x,)` | want 1 (only `%s`), got 1 → **PASS** | `ValueError: unsupported format character '('` |
| `b"%b" % (data,)` | want 0, got 1 → **FAIL** | correct code, runs fine |

Trace of row 2, since it is the least obvious: after `%` comes a space, so `SPEC_RE`'s key group is skipped, the space is eaten by `[-+ #0]*`, and `(` matches no width/precision/length/conversion — the regex fails at that `%` and `re.search` silently steps over it to `%s`. CPython follows the same component order (`%` → mapping key → flags → width → precision → length → **type**), so it too reaches `(` — but as the *conversion type*, which does not exist, and raises. Row 1: CPython raises `ValueError: incomplete format` on a format string ending in a lone `%`; the regex just finds no match and stops. That is not an invented risk — it is [CPython issue #85461](https://github.com/python/cpython/issues/85461), "`'%'` character in `help=` causes `ValueError: incomplete format`", i.e. prose containing a bare `%` inside a format string. **Which is precisely the edit that broke `:354`: prose was hand-appended to a format string.** The gate hardened the one mutation that shows up as arity and left the two that show up as validity wide open — and `ValueError` kills phase 1 exactly as `TypeError` did.

Row 3 is the other direction, a false FAIL that would block a *correct* recipe: for `bytes`, `b` is a supported conversion type (and `s` is a synonym for it) — [PEP 461](https://peps.python.org/pep-0461/) — but `b` is absent from `SPEC_RE`'s class `[diouxXeEfFgGcrsa%]`. That is the same defect shape this very file warns about at `:24` and again at `:47-48` (gate 7's old `move_in` count, the false positive that nearly fired the firefighter). The gate repeats, in a new place, the mistake its own docstring is a monument to.

And a third class the walk never reaches at all: **`:166-167` drops every non-literal format string with `continue` and no note** — contradicting `:44-46` explicitly. In this fleet that class is occupied: `tools/cycle_runner.py:423` (`FF_PROMPT % ff_recipe`), `tools/bench/handle_audit.py:58` and `:77` (`CHILD % (dirname, T, 20)` — a **3-argument** template, invisible), `tools/bench/selftest_guard_cycle_fixed.py:67` (`REVIEW % (...)`). So the third clause of the claim, *fit to stand as the fleet's pre-launch arity check*, fails on the fleet even if you grant everything about this one file.

## 2. Alternative explanation of the same evidence

The log's "145 checked OK, 0 unresolved" is fully explained without any of the 145 being verified. **`n_ok` is one counter over three populations:** (a) literal-tuple sites genuinely compared; (b) `want == 1` non-tuple sites *assumed*; (c) — for other targets — sites never visited, because the left operand is not a `Constant`. "0 unresolved" then means "the unresolvable class is invisible to this classifier", not "everything resolved". The run is equally consistent with "the gate works" and with "the gate mostly counted sites it declined to check", and the printed output cannot distinguish them, because the split is never printed.

A second, smaller alternative for why the one MISMATCH looks so clean: it is the only site in the file where a **five**-spec format meets a literal tuple. A detector that fires once on the one case you already knew about, in a file you wrote, is weak evidence of a detector.
