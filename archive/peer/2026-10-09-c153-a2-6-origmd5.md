Every later mention of `c39f36e0` repeats an old citation (cycle27-plan, motor-call-site-census, ucbench answers). - The project did load this exact file in LabVIEW 2026 many times on 09-18: census, D0 runs, fstunnel diagnostics, and "ExecState 1 … once the ORIGINAL had been opened read-only" (`docs/cycle27-plan.md:154-155`). But "no save on record" is not "no project save", and `gui_save` Ctrl+S presses on 09-22 and 09-23 (`tools/gui_actions.log:1801-1933`) went to whichever window was in front.
- The md5 cannot say who saved the file. Both sides now use LabVIEW 2026 (memory note: rig standardised on 2026 from 08-31), so the version bytes `26 00 80 00` would look the same either way. **The version-byte test you proposed in (c) will not discriminate here.**

## 2. Alternative explanation of the same evidence
A resave that changed nothing in the graph. When a subVI changes, LabVIEW recompiles the callers and wants to save them, even with no edit. Unless compiled code is separated from source, that recompiled code is stored inside the VI file ([NI forum: LabVIEW re-saves VIs I haven't changed](https://forums.ni.com/t5/LabVIEW/LabVIEW-re-saves-vi-files-even-though-I-haven-t-changed-them/td-p/4205819), [Hampel: separate compiled code](https://hampel-soft.com/blog/separate-compiled-code-from-source/), [NI doc mirror](https://rajsite.github.io/unofficial-lvdocs/lvhowto/separate_compiled_code.html)). Saved front-panel default values or window positions would do the same. Whoever saved it, **a changed md5 does not mean a changed block diagram**. Claim 1's real-world consequence ("the census can't be trusted") is a separate question from its stated one ("who saved it"), and neither is shown yet.

A smaller possibility: another file was copied over this path. Weak evidence it was a save in place: if Glob lists oldest first (I inferred this from the version order, it is not documented), the 4.5 file is now the newest `.vi` in `2. Tracking\`. It is newer than V6 (09-01) and 4.6. LabVIEW autosave writes to `LVAutoSave` and never overwrites the source ([NI forum](https://forums.ni.com/t5/LabVIEW/Autosave-file-location/td-p/1445524), [LAVA](https://lavag.org/topic/11472-where-does-labview-store-auto-recovery-vis/)), so that cause is excluded.

## (b) Can a byte-copy read in claudeDev mislead?
Yes. The census was read from the original in its own folder. A copy in `user.lib\claudeDev` resolves relative subVI paths from a different place. The repo already records this effect for byte-identical copies: "ExecState 0 opened cold … ExecState 1 once the ORIGINAL had been opened" (`docs/cycle27-plan.md:154`, `archive/peer/2026-09-18-execstate-linkage.md:19`). If subVIs fail to link, some nodes can come up with different terminal sets. Whether the census uids (from `gscript.node_terms_uid`, `tools/bench/sweep_nodeterms_3state.py:130`) stay stable across a fresh load is not proven here either. So a mismatch between the copy read and the census would not separate "the file changed" from "the copy linked differently".

1. **Run the stat script that was already written and never run**, `tools/bench/diag_c153_a2_1_origstat.py`. It gives size against the census-time 471,257 B (`docs/cycle27-plan.md:154`), plus mtime and version-byte counts.

If it still hashes to `c39f36e0`, compare the two files' resource blocks, both being LabVIEW resource-format files.
