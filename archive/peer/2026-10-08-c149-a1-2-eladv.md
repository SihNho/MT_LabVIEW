## 1. Strongest reason the claim is wrong
"A faithful evaluation of the recipe's own rule" is true of the function, but not of the recipe's mode as it would have been launched.

Running `py tools/recipes/stage_d1_ring_p4_s06v18_scratch.py --el-advisory <json>` first runs import-time code before it ever reaches `el_advisory`:
- `import stagekit as K, stagexec as SX` (`:28`)
- `import stage_d1_ring_p4_s06v18 as R` (`:29`)
- `SX.check_sink_gates(...)` plus an `assert` (`:31-32`)
- the monkey-patch of `K.Stage` (`:62`)

An uncaught exception in any of these also exits Python with rc 1. So the copy proves what `el_advisory()` returns on this read. It does not prove the recipe's offline mode would have exited the same way.

Within the function itself, I checked every line against the recipe:

| plan md5 | plain `hashlib.md5(...).hexdigest()` over the whole file (`diag_c149_a1_2_eladv.py:26`) | `K.md5` reads the file in 1 MiB chunks into the same hexdigest (`tools/stagekit.py:186-192`) | identical |

## 2. Could rc 1 be an artefact of the copy? No
rc is 1 only when a class is unseen or the total differs by more than 3 (`:59`, the same as recipe `:121`). Here `unseen` is empty, so rc comes only from `len(items) - predicted_total`, which is 51 − 55 = −4. The classifier and `elrule` never touch that subtraction.

**Alternative explanation of the same evidence:** rc 1 is decided entirely by the reader's OCR of the window header. The read json has `n_reported: 51` taken from the text "51 errors and warnings" (`errorlist_…_181243.json:60-61`), and the reader stops stepping at that number. If the header was misread, `len(items)` is wrong by the same amount, and both the copy and the recipe would still say rc 1.

el51 called this alternative "B" and judged it unlikely but **never checked** (`archive/peer/2026-10-08-c149-a1-2-el51.md:63-64`, step 3 at `:80`). The eladv log neither strengthens nor weakens it.

**A pin nobody checks:** the pred records `elrule` md5 `a5ee7d5c…` (`plan_ring_p4_s06v18_pred.json:185`). Neither the recipe nor the copy checks it at run time. A changed `elrule.py` could move items between classes. It could not change rc here, unless it produced a class name that appears in neither `start_read` nor `predicted`.
