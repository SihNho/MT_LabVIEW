## Answer

**Short answer:** you're right about why L4 fails, but fixing only the fixture is not enough. On the question you asked: yes, there are two real paths where a failed run from after the records gets skipped. Both are small, and one of them the old gate already missed too.

### 1. Strongest reason the claim is wrong: the time filter treats the wrong cause
Both false positives are failed **pre-runs**, not failed stage runs:
- fp-1: `stage_d1_l2r2_prerun.log:1` is `BGRUN START 2026-09-28 07:54:30 … py -u tools/stage_prerun.py --prerun tools/recipes/stage_d1_l2r2.py`, and `:133` is `BGRUN END rc=1 after 27s`.
- fp-6: `gate_fp_queue.jsonl:6` names `diag_c120_fs_prerun.log`.

`last_failed_run_after` only checks `base not in line` (`stage_prerun.py:2194`). A `--prerun <stage>` or `--dry <stage>` START line contains the stage's name, so the gate reads a pre-run's own failure as a failed stage run under decision 4. That is the root defect.

The time filter fixes both queue entries only as a side effect. It also changes how real LabVIEW failures are handled: in an appended stage log, a real failure that ended before the records now no longer counts.

That extra effect is mostly harmless, because the old gate already ignored such failures whenever the log was not appended again. But it is a wider change than the evidence supports, and it is why L4 broke.

### 2. Alternative explanation of the same evidence
Decision 4 was not tripped by time ordering. It was tripped because the gate counts pre-run segments as stage runs. Excluding segments whose START command is `tools/stage_prerun.py` would clear fp-1 and fp-6 and leave L4 passing as written.

### 3. Real paths where a newer failure gets skipped
- **Rounding window (real, under 0.5 s).** The START stamp is floored to the second (`bgrun.py:200`), and `after Ns` is rounded from `t0` (`bgrun.py:181,337`). So `segment_ended_by` can come out as much as 0.5 s before the real end, and `+1` does not fully cover it. A pre-run record written in the last half-second of a failing run of the same script would be skipped. In practice this is negligible, but `+2` would close it.
- **Backward clock step (real, narrow).** On a standalone machine, W32Time sets the clock directly for any offset over 1 s instead of adjusting it gradually ([KomuraSoft](https://comcomponent.com/en/blog/windows-time-sync-w32time-guide/), [Microsoft JP](https://jpwinsup.github.io/blog/2021/11/26/ActiveDirectory/WindowsTimeService/SlewAndStep/)). Suppose the clock steps back by more than the run's duration + 1 s between the records and a failing run. The segment's computed end is then ≤ t_min.
  - The old gate was equally blind to this, since mtime runs on the same clock.
  - It only caught it if the log was appended again after real time passed t_min. In that one case the old gate refuses and the new one skips. Rare, but it is a real widening.
- **Timezone/DST: not a path.** Both sides use local time (`strftime`, and `mktime` at `protocol.py:277`), and Korea has had no DST since 1988 ([timeanddate](https://www.timeanddate.com/time/change/south-korea)).
- **Two bgrun processes appending to one log: fails safe.** When runs interleave, the earlier segment has no END line, so it can't be proven to have ended and it is counted.
- **Externally killed runs (`BGRUN KILLED` from the cleanup script): fails safe.** `SEG_AFTER_RE` doesn't match that line, so the segment is counted.
- **Records written with a stale `t`: no production path found.** `write_record` uses `time.time()` (`stage_prerun.py:2015`). Backdated `t` exists only in the self-tests.

### 4. A fixture problem the claim missed: L4b
L4b (`selftest_launch_gate.py:86-89`) uses the same old stamp. It now passes even if the script-name filter were broken, because the time filter alone skips its failure. **Put the current time in L4b's stamp as well**, or L4b stops testing anything.

### Cheapest test that separates the two explanations
1. Grep the START command of the failing segment in fp-1 and fp-6 (already done: both are `stage_prerun.py --prerun`).
2. Grep the gate_fp queue and past refusal logs for any decision-4 false positive whose failing segment is a real stage launch. If there are none, the pre-run exclusion alone covers all the evidence.

### Recommendation
Keep the time filter only if the self-tests also get:
- current-time stamps in L4 and L4b;
- `+2` instead of `+1` in `segment_ended_by`;
- a new test showing that a failed `--prerun` segment is not counted as a stage run.

The cleaner fix is to exclude pre-run and dry-run segments (the root cause) and leave decision 4's time rule as it was. I don't think the widening is dangerous. But the current evidence doesn't justify it, and it hides a regression in L4b.
