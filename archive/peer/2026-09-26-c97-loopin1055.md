## Answer

The claim is probably right about what happened, but it has not been shown. Two failures that fit it are not a measurement of it, and the "same failure recorded before" does not isolate the cause either.

**1. Strongest reason the claim is wrong: the error does not say which cast failed, and the op has more than one.**
- `OpForLoopIn_v0` has at least two casts that can fail with 1055. One is TMSC 788, which turns `Class Name 2`/`index 2` into the Diagram ref (`tools/recipes/build_oploopin.py:9`, `tools/bench/build_oploopin.log:12`). The other is the node-A source path, which feeds Get Outputs from `Class Name`/`index`/`Names` (`build_oploopin.py:3,8`).
- The logged message, `error 1055: To More Specific Class in OpForLoopIn_v0.vi` (`diag_c97_tools_t124b.log:14`), names the VI, not the node. So "the source Traverse was empty" is inferred, not read from the machine.
- The earlier "same failure" does not settle it either. `build_opstopfromnode_v0.log:51-54` is `loop_in("while", SCRATCH, 0, ...)` on a clean EMPTY_v0 copy, with Diagram index 0 and no structures on the diagram. Nobody measured whether `Traverse('Diagram')` on EMPTY_v0 has any member at all. If it excludes the top-level diagram, which is exactly what t124 left as an open fact (`diag_c97_tools_t124.py:135`, never reached), both casts had nothing to cast. That record does not tell the two causes apart.
- So the recipe comment at `build_opstopfromnode_v0.py:406-411` is an explanation someone wrote down, not a measurement.

**What the record does support:**
- **Pattern:** the SubVI story fits every case we have.
  - `test_oploopin.log:8-9`: T2 called `loop_in("while", S, body_now, ...)` with the default `src_cls="SubVI"`, index 0 and no names. IMAQ Copy existed (SubVI index 0, `test_oploopin.log:2`), and it passed.
  - Both failures had zero SubVIs, and both successes had one.
- **Index space:** the "wrong Diagram index" alternative is weakened.
  - `test_oploopin.py:52,59` fed `report_all('Diagram')` indices into `loop_in`, and the new loop landed in the right body (`test_oploopin.log:3-5`). The two index spaces matched on that VI.
  - In t124, `didx` found DW (it would have raised `ValueError` otherwise), so the index was in range for `report_all`'s traversal.
- **Remaining gap:** `loop_in` never calls `ensure_loaded`, while `while_loop`/`for_loop` do (`tools/gscript.py:1249-1274` vs `:1291`). It probably doesn't matter here because `while_loop` ran just before, but it is a difference between the paths.

**2. Alternative explanation of the same evidence.** The Diagram-side TMSC failed instead. Possible reasons:
- On a VI whose only non-top-level Diagram is minutes old, OpForLoopIn's own `Traverse('Diagram')` may order or filter differently from OpReportAll's, for example including or excluding the top-level diagram. That would shift the index by one: index 0 turns into 1, which is out of range, which gives a Not-a-Refnum and then 1055.
- `test_oploopin` passed on HARNESS_copyloop, where the outer body was already saved to disk. That shows the two index spaces agree on that VI, not on a freshly built one.

Background: NI documents 1055 as "Object reference is invalid", and forum reports tie it to casting a bad or empty ref after Traverse ([NI KB 1055](https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z0000019L75SAE), [NI forum: 1055 at To More Specific Class](https://forums.ni.com/t5/LabVIEW/Error-1055-occurred-at-To-More-Specific-Class/td-p/2025860), [Traverse → TMSC thread](https://forums.ni.com/t5/LabVIEW/Get-an-invalid-GObject-refnum-class/td-p/4419170)). `docs/NAMES.md:619-620` records the same mechanism locally: an out-of-range Index Array gives an invalid refnum, and TMSC then raises 1055. That mechanism fits either cast, so it does not help choose between them.

**3. What would falsify the claim** (and the `docs/toolkit-capabilities.md:34` capability): on the same fixture, with a valid top-level SubVI at index 0 and `diagram_index = didx(FIX, DW)`, `loop_in("for", ...)` still returns 1055 or puts the For somewhere other than DW.

**4. Cheapest discriminating test.** Both arms are on the t124 fixture, with no card-97-3 fixture needed:
- **Arm A:**
  1. Copy EMPTY_v0.
  2. Run `while_loop`.
  3. Run `drop_subvi` onto the top-level diagram. Its index is not in `report_all('Diagram')`'s index space, so call `drop_subvi` on the top level through `for_loop`/`drop_subvi`'s top-level path, or drop the SubVI before the While exists.
  4. Run `loop_in("for", FIX, didx(FIX, DW), (40,40))` with the defaults.
  5. Read the result: a For owned by DW means the claim holds; 1055 again means the claim is falsified and the Diagram-side cast is the cause.
- **Arm B:** no SubVI, and pass `src_cls="WhileLoop", src_index=0, src_names=[]`. This only helps if node A's TMSC accepts a structure as its source class. That is unverified, so run A first.
- **Cost:** about one LabVIEW run of roughly 60 s.

**Does 97-3 make it moot?** For card 97-2, yes: `loop_in` is no longer called. As a toolkit fact, no. If the claim is right, `loop_in` cannot build a loop without a source on any VI that has no SubVI, and `docs/toolkit-capabilities.md:34` says "a loop on ANY diagram" without stating that precondition. That gap stays open whichever explanation wins.
