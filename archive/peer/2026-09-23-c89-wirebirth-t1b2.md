## 1. The single strongest reason the claim is WRONG

**(A) answers "which enumeration lists a panel terminal?" when the gate asked "what is w106's source?" — and this project already had the right reader, wired into the very module the diagnostic imports.**

A wire's source is a property **of the wire**, not of any diagram's object list. NI's own page for `Wire.Terminals[]` (6371003) states the ordering rule: *the first reference in `Terminals[]` is the source if a source exists; if more than one source is on the list, the wire is broken* ([NI, Wire → Terminals[]](https://www.ni.com/docs/en-US/bundle/labview-api-ref/page/properties-and-methods/vi-server/generic/gobject/wire/terminals.html); property id and read-only status confirmed at [LabVIEW Wiki, Wire class](https://labviewwiki.org/wiki/Wire_class)). The property is class-agnostic — "the terminals connected by this wire" — so it does not care whether the owner is a `Function`, a `LoopTunnel`, a `RightShiftRegister` or a `ControlTerminal`.

That reader is **built, repaired the day before this run, and already in `stagekit`**:

- `tools/stagekit.py:364-367` — `Stage.net_sources(wire_uid)`: *"THE OWNER-IDENTITY READING … `OpWireSource_v5` is WIRE-addressed — **a terminal is named by the wire it carries** — and every row carries its own error columns."*
- `tools/recipes/build_opconnectfromwire_v0.py:423-435` — `wire_source_owner(target, wire_uid, n=6)`, uid-echo-checked, indicators scrubbed per call, all eight error outs read; acceptance `tools/bench/diag_c68_echo_accept.log` 8/0.
- It has **already been measured on a `ControlTerminal` source**: `docs/d1-route-b-plan.md:607-609` — *"`wire_source_owner` HAS been measured on a `ControlTerminal` source … `tools/bench/diag_hierarchy_a3.log:106` and `:110` (2026-09-16) each return exactly one reciprocal source terminal, `source=True owner 'Diagram' uid 639`."*

`diag_c89_wirebirth.py` opens with `import stagekit as K` and calls itself *"its inputs only"* (`:5-6`). `s.net_sources(106, target=pc)` was one line on an object it already held, and it would have returned **exactly one source terminal** — which is literally what gate T1b2 demanded.

So the generalisation now in `STATUS.md:27` — *"`wmap`/`Diagram.Nodes[]` does not enumerate a panel control's terminal at all … `g.panel_wiring` does"* — teaches the next session the inference **"NODE route empty ⇒ the source is a panel control."** That disjunction is false, and this project's own files list at least four other causes:

The last one is the sharp edge: the same log that established (A) also established that half-wires — wires with a sink and no source — are the resident failure mode of this VI family. A session applying (A) to one of the 11 will conclude "panel control" and go looking in `panel_wiring` for a source that does not exist.

**Answering your question 1 directly: yes, a route exists.** Route (i), wire-side — `Wire.Terms[]` 6371003 → `Is Source?` 634A003 → `Generic.Owner` 6327806 — is **built and measured**. Route (ii), diagram-side — `Traverse('ControlTerminal')` → `Terminal.Connected Wire` 634A000 (`docs/main-vi-panel-map.md:242`) — is documented but flagged there as blocked by the class-cast gap; I found no evidence it was ever built, so I do not claim it works.

One honest limit on my own refutation: for a control-terminal source the wire route reports `owner 'Diagram' #<uid>`, because a ControlTerminal's owner *is* its diagram (`docs/d1-build-plan.md:866` — "use `ControlTerminal.Control` 6353000").
