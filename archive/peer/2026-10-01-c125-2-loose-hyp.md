## Answer

**Verdict:** the explanation is probably right about what kind of error this is. It is wrong about what to do next. A tool for this already exists, and the failed prediction never tested anything.

## 1. Strongest reason the claim is wrong

The claim says "no terminal-row diff can single the new one out", and steps from there to the GUI double-click. That skips a measured, read-only reader this project already has: `OpWireJoints_v1` / `gscript.wire_joints` (`tools/gscript.py:4541-4566`). It reads `Wire.Joints[]`, the wire's segments and their end points. Its hygiene record is `tools/bench/op_hygiene/OpWireJoints_v1.json`: 2,066 calls, 0 errors, handles flat (`docs/d1-loop12-17-split-plan.md:2153`). It was built for exactly this class of fault: loose ends sitting on nets that still have a source and sinks (`d1-loop12-17-split-plan.md:2101-2104`). The brief's "no new op" condition is already met.

The precedent the claim leans on is not a measurement either. PD230's location is "LOCATION IS INFERRED, not measured" (`errorlist_expected_D1_ring_p3a_20261001_180540.json:100`). This would be the second time a loose-ends location is guessed when it could be read. CLAUDE.md's rule for that case: build or use the reader.

The prediction was also wrong before it ran, so its failure tells us nothing new:
- **What the Error List holds.** P3a has 24 "loose ends" items, 20 "not connected to anything" and 11 others, 55 in total. P2b has 23 + 20 + 11 = 54.
- **What the 28 are.** The 20 "not connected" items are the wires with no terminals at all (expected file `:76,:84`). So the reader's 28 is roughly 20 of those, 1 with no source, and about 7 with one side missing.
- **What that leaves.** At least 17 of the 24 loose-ends items already sat on nets that have both a source and a sink. A terminal-row criterion was never going to find the new one. That was knowable from files that already existed.

The pinned "identity" of the new item is also an OCR artefact. `plan_ring_p3a_pin.json` keys it on the text `wirewirehaslooseends` (the "Wire:Wire" reading). But P2b's list has 4 items in that form (lines 2013, 2138, 2263, 2306) and P3a's has only 3 (2140, 2265, 2349). What does hold up:
- the class total went from 23 to 24;
- every other class stayed the same;
- LabVIEW's own header says "55 errors and warnings".

## 2. Alternative explanations of the same evidence

- **(A) An existing net, not a new wire.** w3747 (BufNum) is the only P2b wire that changed. It gained two branches: row 06 `wire_sr RightIn` (`stage_d1_ring_p3a.log:95`) and row 08 `connect_from_wire` (`:118`). If w3747 already had a dangling piece, a branch can split it so LabVIEW reports one more item. Precedent: items #13/#19 were "unmasked" before (expected file `:100`). That gives +1 with no new loose net.
- **(B) A dangling piece left by the cross-border writes.** Candidates are `connect_term_uid` (wires 27331/27378 and 27404/27337) or the `case_frame_wire` branch on w27331. Those two calls took 29.9 s and 17.9 s (`:206`, `:231`), much longer than any other row, which may mean retried path routing.
- **(C) The reader's blind spot is mostly ruled out.** All 11 new wires have both ends, the inner faces of the selector tunnels are read (27347, 27353), and the wire census changes by exactly +11/−0. A fully detached piece inside one Wire object would still be invisible, though, so this is not fully excluded.

The claim's basic premise, that the item is about a segment, is supported by LabVIEW's own text for the item: "This wire segment is not connected to anything" (`errorlist_D1_ring_p3a_20261001_180540_20261001_181801.json:591`). A web search found no NI page for this message, so that on-machine text is the only primary source.

## 3. What would falsify the claim

Read the segment table (`Wire.Joints[]`) of the 12 touched nets (the 11 new wires plus w3747) on both versions. The claim is falsified if:
- none of those nets in P3a has a new end point that is not on a terminal, and
- w3747's segments differ from P2b's only by the two new branches that end at 27084 and 27161.

The extra item would then be on a net P3a never touched. That points to alternative (A), or to LabVIEW re-evaluating the error list.

## 4. Cheapest test that separates them

Run `gscript.wire_joints` on 12 wires × 2 files: byte copies of the P2b bed and the P3a bed. That is 24 read-only calls with the existing op. Compare, net by net, the end points that connect to one segment only and carry no terminal flag (0x1).

- **Exactly one new dangling end, on one net:** the claim is confirmed and the carrier is named. Step A.3 (the GUI double-click) is not needed.
- **None:** the claim is refuted. Widen to a full sweep of about 1,956 wires on both files. That is about 2,000 calls, already shown to be fine.

Do not use the 0x100 "LOOSE" flag on its own. Card 117-1 dropped it as not 1:1 with Error List items (44 flagged wires vs 45 items, `d1-loop12-17-split-plan.md:2157`). In `diag_c117a_hyg.log:20-33` it is set on almost every joint. Only the P3a-vs-P2b difference is meaningful.

**What would change my mind:** evidence that `Wire.Joints[]` cannot see the kind of piece LabVIEW calls a "loose end". That would show up as the joint diff finding nothing while a whole-file sweep also finds nothing. Then the Error List screenshots are the only route left.
