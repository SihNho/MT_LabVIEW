## Answer

**The claim is half right.** The unpurged Invoke from `connect_from_wire` is real, and it fully explains F5a and F5c. It is enough on its own to explain F6a. What the claim cannot show is that it is the *only* cause: nothing in this run could have seen a second break.

What I'm conceding, because the machine recorded it:
- **The stray node exists.** The node count went 628 → 629 around `connect_from_wire` with no purge line after it (`fgate_97_stage.log:207-210`). The Invoke count ended at 1 → 2 (`log:378`), and cdiff lists `(10261,'Invoke')` as the only unexpected addition (`log:389`).
- **It is enough to break the VI.** It was measured before: one junk Invoke takes ExecState 1 → 0, and deleting it gives 1 back (`docs/NAMES.md:1105-1113`, `diag_c64_junkpurge.log`). NI's own error for this shape is "Invoke Node: contains unwired or bad terminal" when no method is selected or the reference is unwired ([rajsite lvdocs: Invoke Node](https://rajsite.github.io/unofficial-lvdocs/glang/Invoke_Node.html), [Tektronix FAQ](https://www.tek.com/en/support/faqs/after-installing-labview-driver-tktla-driver-examples-and-vis-have-broken-arrow-and-sev)).
- **The proposed fix is already in the recipe**, at `stage_d1_fgate.py:63`. So there is nothing left to approve; the next run is the test.

## 1. Strongest reason the claim is wrong: "everything else is correct" was never measured

- **ExecState was read only twice:** once before any edit (t=56.7, F0) and once at F6a (t=272.1) (`fgate_97_stage.json:10-31`). About 25 edits happened in between with no reading.
- **The per-op ExecState values carry no information.** Each connect op reads ExecState while its own junk Invoke is still on the diagram (`build_opconnectfromwire_v0.py:420`, `build_opconnectnested_v1.py:453`), so they always return 0. `connect_from_wire` itself returned `(0, 0, "", …)` (`json:186-197`).
- **A single 0/1 flag that one known break already sets to 0 cannot show a second break.** The gates that passed (F3b–F4d) check ownership, edge tables, tunnel counts and UseDefault. None of them detects a broken VI.

So the break is known to be sufficient, but not known to be the only one.

## 2. Other explanations for the same evidence, most likely first

1. **Case A may have an unassigned output tunnel.** `move_into_frame A` created 4 tunnels: 10092, 23880, 23910 and 24041 (`json:379-384`). UseDefault is set only on 24041, the tunnel feeding #11363 (`recipe:84-87`, F4c). Nobody read the direction of the other three.
   - If any of them is an output, the ' False ' frame leaves it unwired, and that alone breaks the VI ("missing assignment to tunnel", [NI forum](https://forums.ni.com/t5/LabVIEW/Block-Diagram-Errors-Tunnel-missing-assignment-to-tunnel/td-p/323435), [NI forum 2](https://forums.ni.com/t5/LabVIEW/Do-you-use-output-tunnel-default-values/td-p/947691)).
   - The F4 edge table collapses new tunnels (`log:345`), so it cannot see this.
   - My guess is that all three are inputs, one each for #8643, #31053 and #31152. That is inference, not a reading.
2. **Case B has the same gap.** Its tunnels 24059 and 24091 (`json:777-780`) have no direction or UseDefault check at all. Both are expected to be inputs (#11614, #11369).
3. **The Q&R.y and Eq0.x inputs were never read back.**
   - The `connect_nested_v1` readbacks all show `'UID 2': 0` (`log:217,236,255`).
   - `wire_control` returned only `1900`.
   - F3c proves only the Eq0 *output* and the two selectors.
   - An unwired primitive input breaks the VI. This is unlikely but unmeasured.
4. **Low likelihood:** the non-indexed tunnel #23856 on #1359, the moved terminals #8476 and #8323 (moving a terminal into a frame is legal), and the I32 `N` against `i` (Q&R is polymorphic, so at worst a coercion, not a break).
