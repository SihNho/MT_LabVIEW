## Answer

**The claim is wrong about where most of the excess comes from.** Of the 97 extra counts, 82 come from the test harness: it ran stage_prerun twice inside one Python process, and the recorder state carried over and was wrapped twice. Only 15 are the regex over-count the claim names, from `wire_remove_loose_ends`. The other two parts of the claim do not hold for the dry trace: read-backs are not counted, and no op issues several helper calls. The counter-reading in question (1), "123 real wiring edits", is also wrong.

**1. Strongest reason the claim is wrong: it does not add up to 123.**
- In a dry run, `DryPlanBE._apply` records exactly one verb per compiled op (`tools/stagexec.py:3448-3450`).
- Every `SimBackend` method (create, connect_term_uid, rle, wire_sr, …) calls `_apply` exactly once (`stagexec.py:3174`, `:3387`, `:3405`, `:3227`, `:3237`).
- Read-backs never go through `Stage._op` in a dry run.
- The loop that sends one `wire_remove_loose_ends` call per wire (`stagexec.py:2896`) belongs to `LVBackend`, the real backend, which is not used here.
- So one pass of the 63-action plan records:
  - 26 × `wire_connect_term_uid` (the `wire_` prefix is added because `connect_term_uid` is in `REC_WIRING`, `stagexec.py:3430-3431`, `:3449`);
  - 15 × `wire_remove_loose_ends` (not prefixed, but the name contains "wire");
  - 22 × `create`.
- The regex therefore matches **41 per pass**, and **123 = 3 × 41** exactly.
- The same recipe pattern recorded one verb per wiring op when run in its own process: `stage_d1_ring_p3a_prerun.log:94`, "ops 10 vs … stageplan wiring real ops 10".

**2. Alternative explanation: one process ran the recipe twice, and the recorder was wrapped twice on the second run.**
- `diag_c128_1_checks.py:17` imports `stage_prerun` as SP. Lines `:69-72` then call `SP.main(["--dry", REC])` and `SP.main(["--prerun", REC])` in the same process.
- Each call runs `dry()` → `install()` → `patch_stagekit()` (`stage_prerun.py:813`, `:622`).
- `patch_stagekit` saves whatever `Stage._op` currently is (`:657`) and replaces it with the recorder (`:732`). The second time, what it saves is the first call's recorder, so every op is appended twice (`:684` → `:687`).
- `D` is a single module-level object (`:365`) that nothing resets, and `dry()` returns `"ops": D.ops`, a reference to the same list (`:860`).
- Total: 41 from the `--dry` call + 2 × 41 from the `--prerun` call = **123**.

Two side effects of this:
- The `--prerun` call also inherited `D.reached_end`, `D.mutated`, `D.unverified` and `D.addresses` from the first call. So C4's "X1 dry PASS" and its "first mutation" line are not independent evidence.
- C4 called `SP.main` without `--no-record`, so it most likely wrote a contaminated FAIL record (`prerun_records.jsonl:529` matches; I did not open the whole line).

The framing also compares two different checks. "The plan passes `--prerun`" (log `:21-23`) went through the stageplan branch (`stage_prerun.py:3187-3227`), which never calls `x5_count` and never calls `install()`. It says nothing about X5.

**3. What would falsify the claim, and what the gate actually reports.**
- If a **fresh-process** `--prerun` on the recipe still reports `ops 123`, my account is wrong and the claim's "read-backs / helpers" mechanism needs looking at.
- My prediction is that it reports **`ops 41 vs … 26` and still FAILS.** The gate is therefore not a pure harness false positive. `wire_remove_loose_ends` really is counted as wire-making by `WIRE_VERB_RE` (`stage_prerun.py:109`, `:1796`) while `SP_WIRING` leaves it out of the expected count (`:901-902`).
- Fixing only the harness leaves 41 ≠ 26. Excluding RLE from the count while keeping the in-process harness leaves 78 ≠ 26. Both have to be fixed.
- Whether RLE should leave the count, or be counted one-for-one against the plan's 15 RLE actions (the way delete ops were handled by card 115-3, `:1785-1798`), is a judgement call. I am not deciding it here.

**4. Cheapest test that separates the two (offline, no LabVIEW).**
1. Run `py tools/stage_prerun.py --dry tools/recipes/stage_d1_ring_p3b.py --no-record --json-out <scratch>.json` in a new process and count the `ops` list. Predicted: `create` 22, `wire_connect_term_uid` 26, `wire_remove_loose_ends` 15, so 41 regex matches. I did not check that `--json-out` writes the ops; if it does not, step 2 alone is enough.
2. Run `py tools/stage_prerun.py --prerun tools/recipes/stage_d1_ring_p3b.py --no-record`, also in a new process. Predicted X5 line: `ops 41 vs plan wire rows 0 + stageplan wiring real ops 26` → FAIL.

**Settled vs not settled.** The 123 = 41 + 82 breakdown comes from reading the code, not from a measurement; step 2 above measures it. No external API fact is involved, so web search could not settle this. The one outside fact is Python's module cache: a second import or `runpy` run reuses the same `stagekit` class object and the same `D` (https://docs.python.org/3/reference/import.html#the-module-cache).
