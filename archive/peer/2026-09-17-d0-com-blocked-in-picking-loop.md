## Answer

## 1. Strongest reason the claim is wrong

The experiment never issued the post-`Run` COM calls.

There is exactly one worker thread. It removes one command from `self.q`, executes it to completion, and only then removes the next command ([drive_original_copy.py](<G:/Codes/LabVIEW_Codes/MinLab/zz_LabView VI/AAA_UNIST/2. Tracking/V6_ParallelLoop/tools/bench/drive_original_copy.py:174>)). That worker entered `vi.Run(False)` at line 204 and never returned. Subsequent `set`, `abort`, and `closepanel` requests were merely appended to the Python queue at line 235 while their calling threads timed out waiting at line 236.

Therefore these log messages do **not** show that LabVIEW blocked:

- `SetControlValue`
- `Abort`
- `CloseFrontPanel`
- any post-run `GetControlValue`

They show that those commands never reached the worker, hence never crossed COM. The exception text “LabVIEW is blocked” is an unsupported diagnosis generated by the harness itself. The sequential 15 + 15 + 20 + 30 second pattern in [drive_original_copy_run2.log](<G:/Codes/LabVIEW_Codes/MinLab/zz_LabView VI/AAA_UNIST/2. Tracking/V6_ParallelLoop/tools/bench/drive_original_copy_run2.log:7>) is exactly what the client-side queue predicts.

Consequently, this run contains no evidence that `GetControlValue`, `SetControlValue`, or `Abort` are serialized by LabVIEW’s UI thread. There is historical NI documentation saying LabVIEW handles ActiveX communication through its UI execution system, but I found no LabVIEW 2026 documentation establishing that every one of these methods must wait behind a locked event case. Current NI documentation only identifies particular operations—for example, loading a VI from disk—as explicitly waiting for UI idleness. [NI TestStand/LabVIEW manual](https://download.ni.com/support/manuals/375070a.pdf), [current VI Server documentation](https://www.ni.com/docs/tr-CY/csh?context=lvcore_lvhowto_vi_server).

There is also direct evidence against the specific “Lock front panel until the event completes” theory: NI says a locked event case defers front-panel activity and buffers the interactions until the case completes. Your bead clicks were processed immediately and visibly planted markers. [NI’s description of locked-panel behavior](https://forums.ni.com/t5/LabVIEW/non-responsive-user-interface/td-p/49854).

## 2. Alternative explanation fitting all evidence

The `Run(False)` automation invocation did not actually behave as “Wait Until Done = FALSE”—whether because of dynamic-dispatch argument binding, an ActiveX invocation peculiarity, or blocking inside the Run invocation before its asynchronous-return point.

That produces exactly the observation:

1. LabVIEW starts the VI.
2. The VI and its panel remain alive and responsive.
3. The COM worker remains inside `vi.Run(False)`.
4. Mouse interaction proceeds independently.
5. Every later driver request waits in Python’s queue.
6. Because calibration/experiment execution continues, `Run` still has not returned.

NI’s intended semantics are that Run VI with `Wait Until Done = FALSE` starts a separately running top-level VI and lets the caller continue; NI also explicitly describes Run VI as permitting interaction with the target while it is running. Thus the non-return of this particular invocation is itself the anomaly to isolate—it is not evidence about later calls. [NI Run VI comparison](https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z0000019MqkSAE&l=en-US), [NI example using Wait Until Done = FALSE](https://forums.ni.com/t5/LabVIEW/Dr-Damien-s-Development-Running-Top-Level-VIs-The-Basics/td-p/974512).

A second plausible serializer is application/root-loop ActiveX handling during the Run invocation. But the present harness cannot distinguish that from bad argument binding or from a UI-thread blockage, because it deliberately prevents any concurrent COM probe.

## 3. Observation that would falsify the proposed explanation

Either of these would falsify it:

- While the first apartment remains stuck inside `Run(False)`, a second independently initialized COM apartment successfully executes `Application.Version`, obtains the running VI reference, and performs `GetControlValue` or `SetControlValue`. That proves LabVIEW’s UI/ActiveX service is available and the apparent global blockage was confined to the first client worker.
- Instrumentation shows a post-run command actually entered COM, remained blocked, and then returned immediately when the bead-picking mouse event occurred. That would support your explanation; currently the command never reaches that point.

More narrowly, immediate processing of marker clicks already argues strongly against “Lock front panel until the event case completes,” because NI documents that such clicks are buffered while the panel is locked. It does not rule out some different root-loop or ActiveX serializer.

## 4. Non-GUI control mechanisms

`SetControlValue` is useful only if the running diagram reads the control value directly or polls it. It does **not** generate a Value Change event, so it cannot substitute for a physical click when the bead-picking logic is waiting on that event. NI explicitly says ordinary programmatic changes, including VI Server changes, do not generate Value Change events. [NI event documentation](https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z0000019N6xSAE).

`Value (Signaling)` does set the value and generate a Value Change event as though the user operated the control. Its preconditions are:

- You must obtain a usable reference to the actual control and write its `Value (Signaling)` property; `VI.SetControlValue(name, value)` has no signaling equivalent.
- The Boolean must use a switching mechanical action. Value and Value (Signaling) are unsupported for latch-action Booleans because of the read/reset race. [NI Value (Signaling) documentation](https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z0000004BKFSA2&l=en-US), [NI latch-action restriction](https://knowledge.ni.com/KnowledgeArticleDetails?id=kA00Z000000P8WLSA0&l=en-US).
- The event structure must actually handle that control’s Value Change event.
- The property call must itself be able to reach LabVIEW. A second client thread only removes your Python-side serializer; it cannot overcome a genuine application-wide ActiveX/UI-thread blockage.

For a VI designed for automation, the documented robust alternative is to pass a queue, notifier, or user-event reference before launching the top-level VI and have its diagram receive commands independently of front-panel events. [NI top-level VI guidance](https://forums.ni.com/t5/LabVIEW/Dr-Damien-s-Development-Running-Top-Level-VIs-The-Basics/td-p/974512).

## 5. Cheapest discriminating test

Add an `entered[sid]` event or one log statement immediately after `sid, kind, args = self.q.get()` and another immediately before each COM invocation. After `Run(False)` times out, enqueue one harmless `Application.Version` request.

If no “dequeued/entering COM” message appears for that request—and with the present code it cannot—the supposed post-run COM blockage is conclusively client-side queueing. Only after replacing that single worker with a second independently initialized COM apartment is there a valid test of whether LabVIEW 2026 itself serializes VI Server calls behind the running VI.
