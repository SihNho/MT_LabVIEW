## Answer

**The claim is not established. Its "noise" premise contradicts this run's own readings. But the connect-writer leak it wants to rule out is not supported either. Our record points to a third cause: the T2 window measured the one-time cost of loading op VIs for the first time, mixed in with any per-call behaviour.**

**1. Strongest reason the claim is wrong: the noise it relies on is not in the data.**
- The claim says +113 is about 0.75 handles per op run, "inside the noise". But the windows in this run where every op had already been called once are nearly flat:
  - T1H moved −5 over 20 editing `case_in` calls (`selftest_c97_tools.log:51`).
  - T5 moved −1 over 20 writes (`:154`).
- So the noise between two readings with no first-time op calls is about ±5, not about ±100. +113 is roughly 20× that.
- Spreading +113 over "~150 op runs" does not help. T1H also ran build_case, OpMoveIn_v0 and OpOwnerChain_v1 20 times and stayed flat.
- The same rule cuts the other way: the ±100 gate cannot show "not a reference leak" at all.
  - `HandleCount` is `Get-Process … .HandleCount` (`tools/bench/bench_prep.py:64-67`), i.e. Windows kernel object handles only, not GDI/USER ([GetProcessHandleCount](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesshandlecount?redirectedfrom=MSDN), [kernel handle table](https://www.oreilly.com/library/view/windows-via-cc/9780735639904/ch03s02.html)).
  - Our own code says this count "cannot see VI Server refnums at all" (`tools/gscript.py:238-239`; `docs/toolkit-capabilities.md:542-543`).
  - "Python opened 21 / closed 21" (log `:164`) counts only `vi_ref()`. The per-op `_cache` references from `GetVIReference` (`gscript.py:221-226`) are not in it.

**2. Alternative that fits all five readings: first-load cost.**
`g.op()` opens and caches one VI reference per op VI the first time that op is used (`gscript.py:224-225`). That loads the op VI and its subVIs into LabVIEW. Now line up each handle window by whether its ops were warmed (called once) before the first reading:

| window | ops warmed before the first reading? | Δ |
|---|---|---|
| T1H | yes: `case_in` already ran in T1 A and T1 B (`selftest_c97_tools.py:109` before `:124`) | −5 |
| T5 | yes: `first = tunnel_use_default(...)` runs before `h3` (`:157-158`) | −1 |
| T4 | no: `set_control_label` is first called inside `h5…h6` (`:181`) | **+18** |
| T3 | partly: OpTunOuterWire_v1 and OpCtlSinkWire_v1 are first used here | **+36** |
| T2 | no: `move_into_frame` runs for the first time, so OpConnectNested_v1, OpConstWire_v1, OpWireCtl_v0, OpConnectFromWire_v0, OpNodeTerms_v0, OpNodeLabels_v0 and OpWireSource_v5 all load cold inside `ha…hb` (`:135`) | **+113** |

- The gaps between windows grow the same way: +22 from T3's end to T5's start, +24 from T5 to T4. Both gaps contain first calls (tunnel_use_default, tunnel_use_default_at, panel_wiring).
- Every window that grew contained a first load. Every window that stayed flat was warmed first.
- The idea that "one of the connect writers leaks 4–7 per call" also fits T2 and T3. Two equations, T2 = 2a + 16e and T3 = 2a + 3e, give e ≈ 6 per edge write and a ≈ 9 per OpAllTerms_v0 read. But the reads grow with the member count too, so these two readings cannot separate the two explanations.
- What our record says about the ops you named:
  - `handle_audit.py` has no entry for OpAllTerms_v0, OpConstWire_v1, OpConnectNested_v1 or OpConnectFromWire_v0 (grep: no matches).
  - The capability docs describe only whether these ops work (`docs/d1-route-b-plan.md:84,94`; `docs/d1-loop12-17-split-plan.md:894`). None of them has a flat-handle measurement.
  - So "never handle-audited" is correct. That is missing evidence, not evidence of a leak.
- One check that is still unconfirmed: a single op load may not cost ~10–15 kernel handles. That is plausible (file handles, sync objects) but unmeasured. It is exactly what the first block of the test below reads.
- A side note on scale: handles fell from 54,402 after load (log `:5`) to 51,560 before T1H. A swing of −2,842 with no restart shows this count is shaped by the process's own allocation behaviour, not only by our ops.

**3. What would prove the claim wrong:** a second `move_into_frame` in the same session, with every op already warm, that still grows by about +100. Or any single op showing a steady per-call climb over 20 warm calls.

**4. Cheapest test that separates the explanations (about 5–8 LabVIEW minutes, same scratch copy, handles read between blocks):**
- **Block 0:** call each suspect once and discard the reading: OpConnectNested_v1, OpConnectFromWire_v0, OpConstWire_v1, OpAllTerms_v0, OpNodeLabels_v0, OpWireSource_v5. Record Δ per op. This is the first-load cost.
- **Blocks 1–3:** 20 warm, idempotent calls each (the same scratch file supports all three):
  - OpConnectNested_v1 re-connecting an edge that already exists;
  - OpConnectFromWire_v0 the same way;
  - OpAllTerms_v0 reads. Each takes about 21 s (log `:6`), so use 5 calls, or accept ~7 min.
- **Block 4:** run T2 again on a fresh set of members in the same session.
- **How to read it:**
  - Block 0 about +100 total, blocks 1–4 within ±10: the first-load explanation holds, and the T2 gate should be fixed by warming the ops before `ha`. The claim's noise argument is still wrong.
  - Any warm block growing by more than about 60 over 20 calls: that op leaks.
- Also log `ref_counts()`, and private bytes alongside the handle count, because kernel handles cannot see refnums.

**What would change my mind:** a warm re-run of T2 that is flat. That would make the +113 harmless, but the reason would be first-load cost, not the claim's noise argument.
