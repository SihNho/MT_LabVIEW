## Answer

**Verdict:** the core claim holds. `DonorRingConst_v0.vi` is the intended file, at the intended path, and is not a stray scratch copy. Two parts of the framing are overstated, though, and H6 cannot support the conclusion that nothing else changed.

**1. Strongest reason the claim is wrong (in part).** The donor's checks were all made in LabVIEW memory before the save. The file on disk was never checked against them.
- The value read-back and `ExecState` 1 happen at `diag_c122_hyg.py:43-46`. `g.save(DON)` comes after, at line 47.
- The md5 was taken right after that save, and the same run wrote it into `diag_c122_donor.json` (line 50). So the md5 match in "already ruled out" only shows the file did not change after the save. It says nothing about whether the save wrote the right content.
- Only constant #249 was ever confirmed from disk, indirectly: 21 byte copies of the donor were loaded, `const_class_index` found #249, and the calls echoed 249 (log:32, 96).
- The DBL[20] #101 and I32[20] #130 values, and `ExecState` after a cold load, were never read from the saved file. "Read back equal" in PD243(a) (`docs/d1-loop12-17-split-plan.md:2352`) describes the VI before the save, not the accepted file.

**2. Alternative explanation of the same evidence.** The donor was intended, and another `claudeDev` file was also rewritten, but H6 cannot see it. H6 compares file names only, for top-level `*.vi` files only (`stagekit.py:1159`, `333-334`).
- It cannot see a pre-existing VI overwritten under the same name. Only 5 pins, the input and the kernel are md5-checked (log:7, 31, 107-112). The other ~300 VIs and the 13 cached operation VIs are not.
- It cannot see non-`.vi` files or anything in subfolders. A recursive listing of `claudeDev` holds over 500 files, including `.json`, `.ctl` and `.bak`.
- "added [donor], removed []" is not the same as "nothing else changed". One file is cleared: the md5 of `OpConstInd_v0.vi`, which ran 2,005 times, still equals the card's input (`op_hygiene/OpConstInd_v0.json:5` = `fd4be498…`). I did not check what `g.save` saves beyond the one VI. That is unmeasured, not ruled out.

**What I checked and found clean:**
- **Intended:** the card's pass list requires a donor (`task_122-4.json:22`). The path matches `DON` (`diag_c122_hyg.py:19`).
- **Not a stray scratch:** all 22 scratch copies were deleted (log:34-94, 105). A search for `*c122*` in `claudeDev` finds nothing.
- **No collision with a later script:** `diag_c122_route.py:4` now reuses this donor rather than rebuilding it.

**One weak point in the "script premise" framing.** The script had no way to declare the donor:
- `K.run` calls `stage.close()` with no `expect_files` (`stagekit.py:1382`).
- `discard_work`'s own contract says a diagnostic must leave no artefact behind (`stagekit.py:498-500`).
- So H6 did its job: this was a build step run as a diagnostic.
- The RESULT line still reports `"artefacts":[]` (log:120), so anything that reads that line does not know the donor exists.
- PD243's "later scripts declare their saved donors" needs a real way to do it (`close(expect_files=…)` or a Stage field). Until one exists it is a promise, not a fix.

**3. What would falsify the claim:**
- any `claudeDev` file other than `DonorRingConst_v0.vi`, in any subfolder or extension, last modified during the run (13:01:57–13:05:24 on 2026-10-01); or
- a cold load of the donor showing #101 ≠ 20×0.0, #130 ≠ 20×−1, or `ExecState` ≠ 1.

**4. Cheapest test that separates the claim from the alternative (offline, about one second, no LabVIEW):**

The claim predicts exactly one file, `DonorRingConst_v0.vi`. Any other file there means the alternative is right.

For the content gap: card 122-5 loads the donor anyway, so it should first read #101, #130, #249 and `ExecState` from the saved file. That needs LabVIEW, so it is not offline.
