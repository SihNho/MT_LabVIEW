## Answer

**Verdict:** H1's diagnosis is partly right, but its main claim is wrong. This is a model error in our own simulator, not just a gap in the reader, and the project has already measured how to reach a case-tunnel sink.

## 1. The strongest reason H1 is wrong

H1 says this is "not a plan or model error." It is a model error.
- **What the machine does:** a tunnel's terminal is reached through its **owning structure's `Terminals[]`**, not as a `Diagram.Nodes[]` entry of its own. The project wrote this down in `docs/cycle27-plan.md:2883-2885` and measured it working.
- **The earlier successful wire:** SelectorTunnel #12673 was addressed as *"CaseStructure #12589, Diagram idx 48 Nodes[47], t1"*. `connect_from_wire(sink_diag=48, sink_node=47, sink_term=1)` then left #12673 as a sink on wire 9113 with `Is Broken? False` (`tools/bench/build_d1_m3a1.log:1145-1154`).
- **Where the dry run went wrong:** the SimReader lists each tunnel as its own node (`tools/stagexec.py:782-792`). That is an address the machine does not have, which is why the dry run and X1-X7 passed.
- **What H1's framing would lead to:** making the real reader "list border tunnels" would copy the simulator's mistake into the real reader. The fix goes the other way:
  - `Addr._triple` maps a tunnel row to its owner structure, then finds the terminal in that structure's `Terminals[]`.
  - The shift-register branch already does this for loops (`stagexec.py:348-373`, `loop_of`).
  - The simulator must model tunnels the same way.

The external sources agree that case tunnels are reached through the structure (`Tunnels[]` and the case's terminals), not through `Nodes[]` ([NI forum](https://forums.ni.com/t5/LabVIEW/LabvVIEW-Scripting-wiring-a-pass-through-tunnel-inside-a-case/td-p/3945608)). I only saw that thread through a summariser, so treat it as moderate support. The local measurement above is the stronger evidence.

## 2. Alternative explanation: H1 treats two different problems as one

- **Which ends are which class:**
  - #2886 and #5818 are **FlatSequenceInnerTunnels** (`tools/bench/l2a1_facts_80.log:328,334`).
  - #10750 is a SelectorTunnel (`:341`).
  - #5825 is a SelectorTunnel on case structure #5540.
- **Why the FlatSequence ends need their own route:** a FlatSequenceInnerTunnel is not a `Tunnel` and is in no `Nodes[]`. Its faces are reachable only through `Left/Right Terminal` 1C3A9000/1C3A9001 (`docs/NAMES.md:1245-1255`), and it is not known to appear in its owner's `Terminals[]` (`docs/cycle27-plan.md:3398`).
- **Why ops 1-17 still passed:** #2886 and #5818 are **sources**, and connect sends a wired source through its wire (`stagexec.py:701-703`). So they never needed a `Nodes[]` index; being "unprovable" at PRIME was harmless for them.
- **Consequence:** H1 predicts one failure mode for "every border-tunnel sink". In fact SelectorTunnel sinks and FlatSequence ends each need a different route. A fix for one will not cover the other.
- **The failure was visible before any edit:** PRIME logged 4 unprovable ends at `stage_d1_l2a1.log:36`, and the run carried on for 17 ops. A failed PRIME should stop the run before the first mutation.

## 3. What would falsify H1 and my alternative

- **H1 is falsified** if #5540's live `Terminals[]` contains the SelectorTunnel's outer face, i.e. a row whose (name, direction, wire) matches #5883. Then the terminal was always reachable and only the mapping from tunnel to owner is missing.
- **My alternative is falsified** if #5540's `Terminals[]` does not expose #5883, e.g. only the selector terminal shows. H1's "the op cannot reach it" would then stand, and `OpWireSR_LeftIn` would need a new route.

One risk for the fix. If #5883 is unwired at op 18, several unwired tunnel faces on #5540 may share the key `('', dir, 0)`. The unique-match step (`stagexec.py:394-397`) would then be ambiguous, so it needs the order-proof route or the uid-by-wire route from Pre-decided 74 (`docs/cycle27-plan.md:2925-2928`).

## 4. Cheapest discriminating test, with no second stage run

1. Offline, read `tools/bench/prerun_l2a1_81c.log` and step_00 in the finalized plan. Find the rows owned by #5540 and check whether #5883 is wired in the state before op 18. This costs no LabVIEW.
2. Then run one read-only diagnostic on a fresh scratch copy of the bed D1_k. It is not a stage run, so the retry cap does not apply.
   - `node_terms_uid(didx(#639), Nodes.index(#5540))` gives #5540's terminal table.
   - Check it contains exactly one row that matches #5883's (name, is_source, wire).
   - Check #5702 on the same structure, and #10750 on its owner.

This one read decides between H1 and the alternative. It also tests the `wire_sr` op directly: `OpWireSR_LeftIn` looks up `Nodes[node_index].Terminals[term_index]` on the loop body (`tools/gscript.py:752`), so a structure index plus a tunnel-face index is exactly the pair it accepts.

**What would change my mind:** if #5540's `Terminals[]` shows no face for #5883.
