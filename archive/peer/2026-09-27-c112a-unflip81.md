## Answer

The claim holds as far as it goes: the 6 pass / 2 fail result is the pinned-count failure and nothing else. But the passing U-gates do not show that card 112-1's new code is safe, because none of them runs it.

**1. Strongest reason the claim is incomplete: the passing U-gates never touch `seed_base_flips`.**
- U1 builds a synthetic state and calls `_flip_orphaned_output_tunnels` and `op_wire` directly (`tools/bench/selftest_stagesim_unflip_81.py:27-38`).
- U2 builds its state with `S.base_state` and replays `op_move_in` / `op_wire` (`:42-55`).
- Neither calls `simulate()`, which is where 112-1 seeds the saved flips (`tools/stagesim.py:1241`), nor the stagexec dry-run code that also seeds them (`tools/stagexec.py:2367, 2483`). `selftest_stagesim_l2a1_80.py:66` doesn't either.
- So U1/U2 passing, with FACT lines identical to cycle 101 (`_c112a.log:7-8` vs `_c101-4.log:7-8`), only shows that the same-session un-flip rule from card 81-5 did not regress. It says nothing about the new code.
- The new code is tested only by stagesim's own toy gates G63–G65 (`stagesim.py:1867-1890`). Those check one hand-built B2-11-shaped graph.

**2. Alternative explanation for the same evidence:** 112-1 could be wrong on real graphs and every one of these self-tests would still pass.
- The measured `move_in` model has `unflip_on_source` switched on (`_c112a.log:5`). So on any real graph, `simulate()` now seeds every loop, generic or case-structure tunnel whose terminals all read as sinks (`stagesim.py:454-477`).
- If LabVIEW reports a tunnel that is simply unwired on both sides as all-sink, that tunnel gets seeded wrongly. A later wire would then flip its other side to a source.
- The pinned count cannot see this, because nothing that runs `simulate()` on real data is in the test.

**What I checked that supports the claim:**
- The stagesim self-test grew only by adding gates. The c109c log lists G01–G62 as 66 PASS lines (G43 repeats six times, G53 is absent). The c112e log has the same lines plus G63–G67, making 71. No gate was dropped or renamed (`selftest_stagesim_c109c.log:3-68` vs `selftest_stagesim_c112e.log:3-73`).
- The one failure in `selftest_stagesim_l2a1_80` is its own pinned E1 check (42/0), both in c101-4 and c112a (`selftest_stagesim_l2a1_80_c101-4.log:16`, `_c112a.log:16`).
- One cosmetic difference: in c112a, E1's detail field quotes the G67 line. That line passes; its detail text just contains the word "FAIL". It is not a failure.

**3. What would prove the claim wrong:** run `seed_base_flips_modelled` on U2's base state (`l2a1_graph_k_80.json` plus owners). If it seeds anything, and a U2-style replay with that seeding no longer matches `l2a1_unflip_81.json` `after_move` / `after_wire`, then 112-1 broke the one case that was measured on the real VI.

**4. Cheapest test to tell the two apart:** a pure-Python run of about 5 lines, no LabVIEW. Take U2's `st` right after `base_state` (`unflip_81.py:43`) and call `S.seed_base_flips_modelled(st, S.load_models())`.
- If it returns `[]`: 112-1 cannot change the M1 case. The claim stands, and the only fix needed is to replace the pinned counts with "fail == 0 and pass ≥ the old count" in U3 and E1.
- If it returns anything: repeat U2b/U2c on that seeded state. A mismatch means a real regression.

As a follow-up, run the same seeding call on the L2-B1 bed graph that the next stage will actually simulate, and count the tunnels it seeds. That shows whether the all-sink rule catches only #9087/#29911 or others as well.

In short: "pre-existing pinned-count failure" is supported by the logs. "Not a regression of card 112-1" is not shown by this test, because its passing gates don't reach the new code.
