## Answer

**Refuted as argued.** The ExecState 0 is a setup difference, but not the one you named. The chain that feeds the selectors (your `upd` chain versus #11639) is not what separates the two runs. The measured difference is that the self-test left behind the empty Invoke Nodes that our ops create, and the stage deletes them.

**1. Strongest reason the claim is wrong**
- The self-test calls `g.case_in` twice and `CN.connect_nested_v1` twice directly (`tools/bench/selftest_c98_move.py:60,90`). It never runs stagekit's `junk_purge`.
- Each of those ops leaves one Invoke Node on the target diagram with its `reference` input unwired. Evidence: `diag_c98_fgate.log:117,141` (case_in A/B; `case_in`'s own purge at `gscript.py:3392-3396` only catches `build_case`'s Invoke, not the one from `move_in`) and `diag_c98_fgate.log:235,254` (connect_nested_v1).
- The stage deletes every one of them, because every op there goes through `_op` then `s.junk_purge` (`tools/recipes/stage_d1_fgate.py:27`).
- The stage has already recorded this exact failure: "its junk Invoke was never purged (F5a 1->2, ExecState 0)" (`stage_d1_fgate.py:65`).
- The break is visible earlier than E1. `connect_nested_v1` returns `(wire delta, ExecState, err)` (`build_opconnectnested_v1.py:453`), so the log's `(1, 0, '')` at `selftest_c98_move.log:14` means ExecState was already 0 right after selector A.
- `wire_health` counts wires only (`gscript.py:3497-3505`). It cannot see a leftover node, which is why "0 termless" said nothing here.
- NI's docs back the mechanism: an unwired `reference` defaults only on the VI/Application classes, and "Invoke Node … contains unwired or bad terminal" is a known cause of the broken run arrow ([Invoke Node doc](https://rajsite.github.io/unofficial-lvdocs/glang/Invoke_Node.html), [Tektronix FAQ](https://www.tek.com/en/support/faqs/after-installing-labview-driver-tktla-driver-examples-and-vis-have-broken-arrow-and-sev)). That the scripted junk node breaks the VI is strongly supported by our own measured history (`stage_d1_fgate.py:65`) but was not measured in this run.

**2. Alternative explanations**
- **(a) Leftover Invoke Nodes, the favourite.** Up to 4 of them: one on diagram 7911, three on 639.
- **(b) A dataflow cycle.** #11639 is the stop OR for loop #637. Its inputs come through #12581 ← #11577 ← #11289/#11721, the chain from case #10407 (`allterms_bed_20260923_wires.json:5696-5921`). If For #1359 is upstream of anything in that chain, feeding #11639 into a selector inside #1359 closes a cycle. The bed graph I read does not settle this either way.
- **(c) The existing wire was disturbed.** Selector B returned wire delta 0, meaning it branched the existing wire w3457 (#11639 → terminal 648). If that branch re-routed w3457, loop #637's stop terminal is unwired, and `wire_health` cannot see that either.

**3. What would falsify the claim**
The claim, as reframed here, is false if the scratch still reads ExecState 0 after every Invoke uid that appeared after load has been deleted. Note that (b) and (c) would also be setup-only, since the stage never wires #11639.

The claim's action (import `stage_d1_fgate.body` unchanged) survives any of the three causes. The stage path has read E1 = 1 twice, and its `junk_purge` covers (a). What does not survive is the diagnosis. Two things follow:
- The `selector()` helper from `selftest_c97_tools` has never been measured at ExecState 1. The c97 self-test's T1 passed on frame names only (`selftest_c97_tools.log:17-29`), and helpers built on it inherit the same hole.
- Any future caller of `case_in` or `connect_nested_v1` outside stagekit will break the VI the same way.

**4. Cheapest discriminating test**
One run of about 2 minutes, stopping after S4, no moves:
1. Record the set of Invoke uids and the ExecState after each of `case_in` A and B and `selector` A and B.
2. Delete the Invoke uids that appeared after load, then read ExecState again.
3. If it reads 1, the cause is (a).
4. If it reads 0, read terminal 648's wire on loop #637 to check (c), then rerun without selector A to check (b).

The fix the result points to either way: route `selector()` through the same purge, or make `wire_health` report nodes that appeared after load, so a gate cannot miss this again.
